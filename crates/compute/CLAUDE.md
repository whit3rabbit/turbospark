# turbospark-compute

CPU reference kernels and compute strategy marker type (`ComputeStrategy`). These reference implementations serve as numerical ground truth against which `crates/gpu` Metal kernels are validated.

## Safety

- `#![forbid(unsafe_code)]` is enforced in this crate.

## Key Modules

- `attention.rs`: Reference CPU causal attention, plus `causal_attention_with_sinks` (ROADMAP M5): one learned logit per query head joining the softmax DENOMINATOR and nothing else. A sink has no VALUE row, so it takes probability mass from the real keys and contributes nothing to the output; adding it to the numerator is the plausible wrong version and makes it an ordinary extra key with a zero value. From ggml's `ggml_soft_max_add_sinks`.
- `gdn.rs`: `GdnReference`, the straight-line model of Qwen 3.6's gated-DeltaNet chain (conv + SiLU, per-head q/k norm with folded delta scales, the FP32 delta recurrence, the gated output norm) that `crates/gpu/tests/gdn_parity.rs` checks the eight `gdn.metal` kernels against.
- `gating.rs`: `sigmoid_gate_mul`, `sigmoid_scalar_mul`, `split_q_gate`.
- `moe.rs`: CPU reference MoE FFN logic (`run_ffn`) used to bridge gated FFN activations.
- `quant.rs`: INT4 and INT8 affine (MLX-layout) quantization/dequantization and GEMV math used by repackers and CPU fallbacks.
- `quant_1bit.rs`: the 1-bit affine reference (MLX `bits: 1`, the `prism-ml/Bonsai-27B-mlx-1bit` layout). Same CONTAINER as `quant.rs` (a packed plane beside per-group scales and biases, `w = q * scale + bias`) and a separate module because three things differ at once and each is a silent wrong answer rather than a failure: the group size is 128 where `quant.rs` pins 64 and every affine GEMV specializes on it, the companions are FP16 where `quant.rs` carries BF16 bit patterns, and a byte holds 8 elements rather than 2. **The convention was measured, not read off a doc**: `scripts/mlx_1bit_oracle.py` ranged-reads one real tensor and has MLX decode it, and LSB-first reproduces `mx.dequantize` on all 245,760 elements while MSB-first matches none. That oracle is load-bearing in a way the others' are not -- at one bit there is no arithmetic to sanity-check an unpacker against, since a wrong bit order gives weights of exactly the right magnitude and the wrong sign. The checkpoint's `bias == -scale/2` symmetry (all 1,920 probed groups) is what makes a `+/-1` accumulate-then-scale GEMV possible and is deliberately MEASURED (`is_symmetric`) rather than assumed, because the container permits any pair and nothing in the file declares it; `dequant_int1_gemv_symmetric` states what that kernel computes and panics on a row that does not qualify. **The type's FOOTING is a GEMV plus an embedding lookup and no routed-expert pair**, and that was read off the checkpoint's safetensors header rather than inferred: 498 tensors carry `.scales`, all with F16 companions, and two of them are `language_model.model.embed_tokens` and `language_model.lm_head` (both `U32 [248320, 160]`, i.e. 5120 elements a row). So `embed_lookup_int1` is a kernel the one real file genuinely needs -- the head is just another matrix through the GEMV, but the table is not -- while nothing needs a routed pair, because the model is dense. That is AGENTS.md Gotcha 29's per-type rule decided by the file, and it corrects a plan that had named two kernels. There IS a quantizer here, unlike `quant_gguf_iq.rs`, because a fixture needs one -- and it applies the SIGN rule, not the min/max rule the INT4 one uses: at one bit min/max degenerates to rounding every weight to one of the group's two extremes, which is both worse and not the convention any real file carries.
- `quant_2bit.rs`: the 2-bit affine reference (MLX `bits: 2`, the `prism-ml/Ternary-Bonsai-27B-mlx-2bit` layout, ROADMAP's ternary entry). Shares `quant_1bit.rs`'s CONTAINER and its two structural properties -- the group size is a parameter (128 here) and the companions are FP16 -- and differs below that in three ways: four elements per byte, `q` over `{0, 1, 2, 3}` so there is no sign shortcut, and a TERNARY grid. **Measured off the real file, not read off a doc** (`scripts/mlx_2bit_oracle.py`, upstream mlx, no fork needed since only `bits=1` is refused at the API level): the LSB-first field order reproduces `mx.dequantize` on all 245,760 elements of the probed tensor, `bias == -scale` in all 1,920 groups, and the level histogram is `{0: 93895, 1: 57398, 2: 94467}` -- **level 3 never occurs**, so the three levels in use are `-s`, `0`, `+s`. Note ROADMAP predicted that grid with a ZERO bias and that is wrong: `q = 0` has to reach `-s`. **The level histogram proves NOTHING about field order** -- permuting the fields inside a word permutes the multiset without changing it, which is the 2-bit form of the popcount trap at one bit, so `the_level_histogram_cannot_see_field_order` states it as a test. Both checkpoint properties are MEASURED (`is_ternary_symmetric`, `uses_fourth_level`) rather than baked in, and they are INDEPENDENT: `bias == -scale` alone still permits a `+2s` fourth level, which `the_fourth_level_is_permitted_and_reported` decodes correctly. **There is deliberately no `+/-1`-style fast path**: the ternary analogue reassociates the sum exactly as the 1-bit one does (AGENTS.md Gotcha 27), and the 1-bit fast path is already reachable from no decode flow, so a second dead kernel buys nothing. The quantizer applies the ternary rule (`scale = 0.7 * mean|w|`, dead band at `scale / 2`, `bias = -scale`) for `quant_1bit.rs`'s reason: min/max at two bits puts the single interior level off-centre and matches no real file. `f16_to_f32` / `f32_to_f16` are re-exported from `quant_1bit` rather than restated.
- `quant_gguf/`: the GGUF block-quant reference (Q8_0, Q4_K, Q5_K, Q6_K, and `pearson`). A separate module from `quant.rs` because the layout is not a variant of the affine one: interleaved rather than planar, and Q8_0 is signed and symmetric with no bias. Q4_K is a second shape again, not a wider Q8_0: a 256-element superblock with two f16 super-scales and eight 32-element sub-blocks whose 6-bit scales and 6-bit mins are packed into 12 bytes, split across two bytes for sub-blocks 4..8, reconstructing as `w = d*sc*q - dmin*m` with UNSIGNED quants. Q6_K is a third shape again: 256 elements with one f16 super-scale and SIXTEEN signed int8 sub-block scales stored as plain bytes, and an element's six bits split across two runs (four low bits in `ql`, two high bits in `qh`) with a fixed bias of 32 subtracted rather than a per-sub-block min. Q5_K (ROADMAP Phase M2, for Mixtral's `attn_output`) is Q4_K plus a fifth bit, and it reuses Q4_K's 6-bit scale/min unpacker byte for byte; what is new is a separate 32-byte `qh` run indexed by the element's position WITHIN a sub-block, at a bit that advances with the 64-element group, so one `qh` byte is read eight times at eight bit positions. It has NO `quantize_q5_k` sibling, because its test does not need one: `scripts/ggml_q5_k_oracle.c` has ggml produce both the bytes and the expected floats, so the decoder is the only side under test and the comparison is exact rather than a round trip that passes whenever encoder and decoder share a misreading. Also carries `pearson`, which is what settles `FUSED_GATE_FIRST` over in `crates/repack`.
- `quant_gguf_iq.rs`: the GGUF IQ-codebook reference (IQ4_NL, IQ4_XS, IQ3_XXS -- ROADMAP Phase S). Separate from `quant_gguf.rs` for the reason that module is separate from `quant.rs`: every type there reconstructs a weight ARITHMETICALLY from its bits, and these three do not. They store an index into a fixed table that ships with the format, so a decoder either has the table or it produces plausible garbage. There is deliberately no `quantize_*` sibling here (an IQ encoder means a codebook nearest-neighbour search nothing in this port calls; tests pick valid indices and scales directly instead).
- `quant_gguf_mxfp4.rs`: the GGUF MXFP4 reference (ROADMAP M5, `gpt-oss`). A THIRD quantization family beside the two above, not a variant of either. Like an IQ type it stores an index into a fixed 16-entry table; unlike anything else here its per-block scale is not a float but a bare 8-bit EXPONENT (OCP Microscaling's E8M0), so every scale is an exact power of two and nothing rounds -- which is why the oracle test compares with `==` rather than a tolerance. One block is 32 elements in 17 bytes, and the nibbles of a byte are 16 elements apart, not adjacent. No `quantize_mxfp4`, for `quant_gguf_iq.rs`'s reason. **The oracle earned its place immediately**: the first `MXFP4_VALUES` carried `-0.0` at index 8, read off the FP4 E2M1 sign bit, and ggml's `kvalues_mxfp4` is an `int8` array with no signed zero. Nothing arithmetic can tell those apart, which is exactly why the codebook is compared by `to_bits`.
- `quant_gguf_iq_tables.rs`: GENERATED by `scripts/ggml_tables.c`, which recovers `IQ4NL_VALUES` and `IQ3XXS_GRID` by PROBING libggml's `to_float` rather than transcribing them. Regenerate, do not hand-edit. The generator pins its own probe scale by ratio before printing a row, because the first version of it left `db` at 1.5 and dumped a table uniformly 1.5x too large -- which decodes to correctly-signed, correctly-ordered, wrong weights.
- `rms_norm.rs`: Reference RMSNorm implementation.
- `steering.rs`: the directional-steering edit on a residual stream row, and the only definition of what `steer_direction_fp16` computes (PORT-LOCAL; the Swift engine has no steering surface). Four modes off one reduction pass: `ablate` (`x -= alpha * c_hat * d_hat`), `add` (`x += alpha * d`), `clamp` (`x += (target - c_hat) * d_hat`), and `renorm` (`ablate`, then rescale the row back to its original `||x||`). **`renorm` needs no second reduction and no second pass, which is the non-obvious part**: `||x||^2` fuses into the loop that already computes `c` (the row element is in register for the dot product, so it costs one fma and no memory traffic), and the POST-edit norm is ANALYTIC -- `||x'||^2 = ||x||^2 - alpha*(2 - alpha)*c_hat^2` exactly, since the projection is orthogonal, which at `alpha = 1` is Pythagoras. Do not "simplify" it into a reduction over the written row. Its rescale factor is exactly `1.0` in the other three modes and `1.0 * v == v` in IEEE-754, so all four share ONE write loop and the older three stay bit-identical rather than merely close. `renorm_gamma` is the factor, `pub` because the parity fixtures have to assert they DISCRIMINATE before comparing it against `ablate` -- as the coefficient goes to zero the two converge, and the default fixture reads 1.006, measured. **`ablate` at `alpha = 1` is exactly the operation the abliteration weight edit `W - d_hat d_hat^T W` precomputes**, so applying it at runtime gives up no fidelity and gains two things: it writes no weight byte (requantizing an edited weight is exactly the damage `quality_sensitivity.rs` measures at +10.5% perplexity for 0.0122% of expert bytes), and it can be turned off between two generations in one process, which is what makes a steered-vs-unsteered A/B possible at all. Every function takes `inv_norm = 1 / ||d||` rather than deriving it: it is a property of the DIRECTION, constant across every layer and token, so a per-token kernel recomputing it would reduce over `d` to learn what the loader already knows. **Passing it rather than pre-normalizing `d` is what lets one buffer serve all four modes** -- `add` reads `d`'s magnitude, because a llama.cpp control vector carries its strength IN the vector, while `ablate` and `clamp` are defined against the unit direction. `inv_norm` returns `0.0` on a zero direction rather than an infinity, which makes every mode the identity there instead of propagating the one wrong value no downstream instrument reports as wrong (AGENTS.md Gotcha 59). Note **`ablate` at `alpha = 1` and `clamp` at `target = 0` are the SAME function**, which is stated as a test rather than left as a trap: it is why the GPU ablate parity case runs at a FRACTIONAL alpha, a mutation swapping the two mode codes in the shader having passed that case at 1.0.
- `rope.rs`: Reference RoPE implementations, plus `yarn_frequencies` (ROADMAP M5), which reduces YaRN to the two things a kernel needs: a per-pair frequency table and one magnitude scale. It exists because the three rope kernels take a SCALAR theta and YaRN interpolates per dimension along a ramp, which no single number expresses; the result is still position-independent, so it is built once at open. **`mscale` is 1.3465736, not 1.0** -- llama.cpp computes `1 + 0.1*ln(factor)` and divides by the same quantity, which reads as a cancellation and is there to stop `rope_yarn` applying it twice. A second trap: the correction dims come out in ELEMENT units and are compared against `i0/2`, so gpt-oss's ramp runs over PAIRS 8..18 of 32.
- `tolerance.rs`: Relative error metric (`RelError`) used in parity testing across CPU and GPU pipelines.

## Crate Gotchas

1. **BF16 vs FP16**: `crates/compute` contains hand-rolled bit-shift helpers for BF16 (`bf16_to_f32`/`f32_to_bf16`), exploiting the fact that BF16 is the upper 16 bits of an FP32 word. FP16 (binary16) storage elsewhere in the workspace uses the `half` crate. Do not mix up the two or hand-roll FP16 logic.
2. **`gdn.rs`'s FP16 rounding points are part of the contract.** The GPU kernels store `conv_out`, the normed q/k slices, the raw conv tail rows, and `y` as `half`; the reference rounds at exactly those four places and nowhere else (the recurrence and the gated norm stay FP32). Moving one makes the parity test's tolerance meaningless. It rounds through `foundation::LogitValue` (`half::f16` by its public path) rather than adding a `half` dependency to this crate -- Gotcha 3 in AGENTS.md forbids hand-rolling binary16.
3. **Ground Truth Baseline**: Kernels in this crate are designed for exactness and reference correctness rather than maximum CPU throughput. Metal kernels in `crates/gpu` validate parity against these routines.
