# minimax_music3

MiniMax Music 3: hierarchical autoregressive music generation with a
flow-matching latent decoder and a stereo 44.1 kHz vocoder.

  [feb25a37b07923bae556e59111995071d66afa0d](https://github.com/Blaizzy/mlx-audio/tree/feb25a37b07923bae556e59111995071d66afa0d/mlx_audio/music/models/minimax_music3).

## Checkpoints

- Official modular tree (five component directories):
  `Model::load_official_tree` flattens the component configs, fuses
  vocoder `weight_g`/`weight_v` pairs, and remaps the PyTorch conv
  layouts (`[out, in, K]` and `[in, out, K]`) into the MLX
  `[out, K, in]` convention this crate's kernels convert from.
- Converted MLX trees (`mlx-community/MiniMax-Music3-*` layout:
  `config.json` plus safetensors shards, optionally sharded through
  `model.safetensors.index.json`): `Model::load_converted`. Affine
  2/3/4/5/6/8-bit linears use the shared dequantizer. MXFP4, MXFP8, and
  NVFP4 grouped packed linears have format-specific CPU decoding and strict
  shape/dtype checks. MXFP8 is the recommended profile; MXFP4 and NVFP4 are
  experimental upstream profiles.
- The official repos (`MiniMaxAI/MiniMax-Music3`, and the
  `mlx-community` bf16/8bit/6bit/4bit/mxfp8/mxfp4/nvfp4 conversions)
  are catalogued at immutable revisions and installed under audio aliases;
  no file digests or general profile qualification are claimed. The MXFP8
  real-checkpoint smoke and controlled precision parity run are described below.

## Text frontend

`Model::generate_text` accepts a caption and lyrics, applies the upstream
prompt cleanup, loads `tokenizer/tokenizer.json`, and uses the checkpoint's
Qwen tokenizer. It defaults to 60 seconds, 30 flow steps, and seed 0, and
validates duration through 360 seconds and the 1..=30 step range. The
existing `Model::generate` accepts pre-tokenized conditional ids as a
low-level reference path. Tiny fixture configs may use the deterministic
local encoder when tokenizer files are absent; full-size models fail closed.

## Verification

Fixtures live in `testdata/minimax_music3/` and are regenerated by
`tools/gen_minimax_music3_fixtures.py` from the pinned checkout (run
inside `../mlx-audio`; the conversion step fetches tokenizer metadata
from the hub). The manifest records SHA-256 digests and the generating
device, and lists only the files it digests. Regeneration was run
twice into clean trees on the same device: all content digests
reproduced byte-identically, and equal the checked-in fixtures.
`tools/gen_minimax_music3_bench_tree.py` generates the enlarged
synthetic trees used by the stress ceiling and the timing profiles
(see that script for variants and disk cost).

Gates (see `tests.rs`, `stress.rs`, `timing.rs`, and the
`qwen3::bench` micro-bench):

- RNG: threefry keys, split chains, uniforms, and categorical tokens
  are bit-exact against recorded MLX 0.32.3 draws across word-layout
  shapes; recorded decision margins prove no draw sits on a rounding
  knife-edge.
- Prompt: caption cleaning, lyric normalization, assembly, and the
  tiny text pair match the reference.
- AR: prefill hidden states and logits, per-frame sampled codebooks
  (token-exact over the recorded short and long traces), depth decoder
  step outputs, and feedback embeddings match.
- Flow: DiT velocities at fixed sigmas, per-chunk Euler latents with
  overlap carry (both chunks of a two-chunk schedule), the vocoder on
  long input, and the crop-stitched waveform match.
- End to end: the short scenario's full stereo waveform and a
  201-frame two-chunk scenario (tiled hiddens, recorded spots) match;
  the official-tree conversion path and an affine 8-bit tree load and
  generate.
- Contract: chunk scheduling, sigma schedule, crop constants, quant
  predicate, and the conv-transpose key matcher. All seven upstream
  quantization declarations are checked; synthetic packed safetensors
  exercise MXFP4, MXFP8, and NVFP4 decoding and reject affine-only tensors.
- Stress (`stress.rs`): valid boundaries (steps 1 and 30, a prompt at
  exactly MAX_PROMPT_TOKENS), empty-prompt refusal, chunk windows at
  200/201/300/301 (three chunks start at 301, two at 300),
  deterministic multi-chunk flow at all four, the end-token-first-frame
  zero-frames error (forced by patching the end-token lm_head row in a
  throwaway tree copy), `generate()` completing when the end token
  stops the AR stage early, and `#[ignore]`d release-only runs to the
  9000-frame ceiling over the committed `tiny_long` bench tree.
- Timing (`timing.rs`, `qwen3::bench`): reporting only, release only,
  one test thread. Tiny end-to-end RTF, AR scaling to the frame
  ceiling, multi-chunk flow, a per-piece frame anatomy, real-width AR
  and real-DiTs flow profiles over the synthetic bench trees, and the
  rope/KV/attention micro-bench. Rows are recorded in `MODELS.md`;
  CPU numbers are never Metal or quality claims.
- Mutation checks were applied to the subtle guards (the time-major
  KV append, per-channel stitch, per-channel overlap capture, DiT
  input transpose, short-chunk crop guard, remap dims, sigma divisor,
  RNG word layout) and every mutation was caught. The KV-append check
  was re-run after the layout change: dropping the unconditional
  row's append fails the AR parity gate immediately.

## Divergences

- `rng::normal` evaluates `erfinv` through an f64 Acklam inverse-normal
  approximation rather than Metal's `erfinv`; the uniform stream is
  bit-exact and draws agree to f32 rounding, but `mx.random.normal`
  values are not guaranteed bit-identical. The flow stage's initial
  noise therefore matches distributionally, not bitwise; parity tests
  replay recorded noise where exactness matters.
- The official-tree loader accepts optional token-contract fields
  (`audio_code_offset`, `audio_end_token_id`, `audio_cfg_token_id`,
  `semantic_vocab_size`) in the language-model config. The reference
  pins these to official constants that assume a 200k vocab; a small
  vocab needs explicit values to stay self-consistent, so the fixture
  tree carries them.

## Metal runtime

`runtime::Music3Runner::open` loads converted checkpoints through the portable
pipeline's `ComputeBackend` interface. Dense F32/F16/BF16 embeddings and
projections stay resident at checkpoint precision. Affine 2/3/4/5/6/8-bit,
MXFP4, MXFP8, and NVFP4 matrices retain their packing and decode inside Metal
projection and embedding kernels. Convolution weights are uploaded once in
the portable layout. Batched f32 attention handles the AR time-major CFG cache,
the causal depth sequence, and the DiT's partial rotary sequence. Sampling,
norms, rotary tables, flow integration, and stitching retain the CPU reference
implementation. Outside the depth step, activations and caches cross the
host/device seam at operation boundaries. This implementation does not claim
fused or real-time execution.

The AR stage and the DiT blocks avoid that seam (see "LM head window and AR
command buffers" and "DiT block command buffers and float-packed GEMV kernels"
below). The LM head keeps only a 64-aligned window of rows on the device. Each
depth decoder step, each LM decode step, and each DiT block with BF16 stages
runs as one command buffer through `backend::Sequence`, and the LM KV cache
stays on the device between decode steps. Traced runs, F32 precision, and any non-BF16 stage keep
the per-operation path.

Each request creates fresh KV and overlap state. Every device dispatch drains
an autorelease pool, checks command-buffer completion before reading outputs,
and rejects non-finite results. A depth step command buffer scans every
operation output, read or not, before readback. Resident weight bytes are
observable through `Music3Runner::resident_weight_bytes`.

Run the focused device gates serially:

```sh
cargo test -p turbospark-gpu --test music3_parity -- --test-threads=1
cargo test -p turbospark-runtime --test music3_metal -- --test-threads=1
TURBOSPARK_MUSIC3_INSTALL_DIR=/path/to/pinned/profile \
  cargo test -p turbospark-runtime --test music3_metal --release \
  music3_real_checkpoint_generates_stereo_waveform -- --ignored --nocapture
```

The kernel gates cover known packed float values, affine values that span U32
word boundaries, nonuniform groups, convolution/transpose edges, and independent
GQA attention with both KV layouts and offset causal windows. Runtime fixtures
check exact sampled codebooks, hiddens/waveforms within 2e-4, repeated-request
state, and two-chunk overlap/stereo stitching. The real-checkpoint smoke checks
finite, non-silent stereo output with the official tokenizer. These checks do
not establish song quality, equivalence of every quantization profile, long
request memory ceilings, or a real-time threshold.

Full-checkpoint verification used `mlx-community/MiniMax-Music3-mxfp8` at
`d00a12c3c7f80eb66379dd02dd0f30ed0ce2d96e` on a Metal device. The one-second
caption-and-lyrics CLI smoke (seed 7, two flow steps) emitted 25 frames and
44,032 non-silent, finite stereo samples. Uploaded weights occupy
13,964,639,150 bytes. This is resident weight accounting, not a sustained
process-memory ceiling.

The independent stage probe requires the pinned source above and MLX 0.32.3.
With floating reference parameters converted to f32, three emitted AR
codebooks and all warmup decisions match exactly. The 98,304 hidden values
have maximum absolute error 1.44e-4; the 10,240 waveform values have maximum
error 1.67e-7. These are controlled f32 comparisons,
not BF16 activation parity. A preliminary run with MLX 0.31.2 produced
different residual codes despite close first-step logits; the probe refuses
that version rather than treating it as the frozen RNG contract.

To reproduce the independent full-checkpoint gate:

```sh
# Run in an environment with MLX 0.32.3 and the pinned mlx-audio source.
python crates/audio/tools/probe_minimax_music3_reference.py \
  --model /path/to/pinned/profile --output /tmp/music3-reference --float32
TURBOSPARK_MUSIC3_INSTALL_DIR=/path/to/pinned/profile \
TURBOSPARK_MUSIC3_REFERENCE_DIR=/tmp/music3-reference \
  cargo test -p turbospark-runtime --test music3_metal --release \
  music3_real_checkpoint_matches_controlled_float32_reference -- --ignored
```

`runtime/examples/music3_backend_probe.rs` also dumps warmup keys, logits,
hiddens, own-AR waveforms and fixed-reference-hiddens waveforms. This lets a
failed comparison be localized before changing tolerances. Device kernels use
f32 activations; sampling keeps the pinned MLX 0.32.3 RNG behavior.

The same one-second prompt with the reference's native BF16 activations also
completed under MLX 0.32.3, but its waveform differs from the Rust CLI WAV:
correlation 0.470 and RMSE 0.00363 across 44,032 stereo samples. That comparison
does not pass native-precision parity. The CLI WAV introduces integer PCM
rounding, which does not explain the larger divergence. Do not promote the
controlled f32 gate into BF16 equivalence or a song-quality claim.

Every WAV above is byte-identical to the output of the unmodified code at the
start of this work (SHA-256 of the 1 s file `29c340d1...`; the 8 s file
`16c5db73...` was checked against a separate pristine build). The optimizations
are bit-preserving by construction and by test: no tolerance was widened.

Where the time goes (8 s, 1 step, after): depth decoder 31.1 s, LM decode 24.5 s,
LM head 3.7 s, DiT 8.4 s, vocoder 6.3 s, prefill 0.8 s, sampling 0.4 s. The AR
stage costs about 0.30 s per frame against the 0.04 s that real time needs, so
it is roughly 7x too slow on its own. DiT cost scales with flow steps: one step
is two forwards over the 690-latent chunk, about 4.2 s each, so a default
30-step chunk projects to about 250 s (arithmetic on the 1-step measurement,
not a measurement). The default 60 s request is far from real time.

What changed, all verified bit-identical against the previous kernels:

- `music3_linear_wide`: the affine "wide" GEMV branch used 8 of 128 threads per
  output and decoded one element at a time. It now packs 16 outputs per
  threadgroup and decodes eight four-bit codes per 32-bit load. This was
  93 percent of the original runtime (124 of 133 s in the 1 s scenario).
- `music3_linear_tiled` and `music3_conv_tiled`: the 8x8-tile MMA kernels now
  stage a 32-wide K chunk once per threadgroup and keep 2x2 accumulators per
  simdgroup. Every output keeps the same K-ordered chain of 8x8x8 products and
  split-K folding. DiT-sized linears about 3x, vocoder convolutions 3x to 4x.
- Affine scales and offsets that are exactly representable in bf16 are stored
  at 16 bits and widened by a shift in the kernel (-621 MB resident on the
  4-bit profile). Any weight with a non-bf16 scale stays on f32.

Verification instruments, kept in the tree:

- `crates/gpu/examples/music3_linear_bench.rs`: `hashes` and `conv_hashes`
  print an FNV-1a hash of kernel output bits over 913 linear/embedding and 20
  convolution configurations (bit widths, groups, row counts, dtypes, ragged
  tile tails, split-K, and every row count from 2 to 12 on the packed wide
  kernel at a ragged width and the real depth shapes). Diff the output before and after a kernel change; any
  difference means the arithmetic changed. `timing` and `conv_timing` use the
  real checkpoint shapes.
- `crates/runtime/examples/music3_bench.rs`: per-stage timings, the runtime
  dispatch table (`Music3Runner::dispatch_profile`, per-op and per-shape wall
  time), output statistics, and `--flow-only` to time DiT and vocoder without
  the slow AR stage (synthetic conditioning; not music).

Tried and not kept (no demonstrated gain on a busy host, so no code):

- Pooling the per-dispatch scratch buffers, and spin-waiting on command-buffer
  completion instead of the condvar: the 64x64 linear floor moved from about
  0.29 to 0.21 ms but end-to-end timing did not separate from noise.
- A 64x32 tile for tall inputs, and remapping the weight-tile write to avoid
  threadgroup bank conflicts: no measurable difference.
- Skipping the zero-padded taps of transposed convolution: it can flip the sign
  of a zero accumulator, which is observable in the output, so it is not
  bit-preserving.
- Replacing the two full-vocab sorts in sampling with a partial selection:
  exact, but sampling is under 1 percent of the 8 s run. Candidate, not done.
- Decoding each 4-bit weight once for up to eight rows in
  `music3_linear_wide` (one running total per row per thread, same lane and
  chunk order): bit-identical (all 913 oracle lines), but slower in an
  interleaved kernel A/B on a quiet host. Two rows, 4096 to 12288: 0.82 to
  0.85 ms before, 1.19 ms after; twelve rows, 4096 to 6144: 1.21 to 1.24 ms
  before, 1.43 to 1.45 ms after. These GEMVs reach about 30 GB/s of 4-bit
  weight traffic, so they are latency-bound, not bandwidth-bound, and the
  row-per-threadgroup layout keeps more loads in flight. Reverted.
- Loading each lane's eight 4-bit words of a group as two 16-byte vector
  loads in `music3_linear_wide`, then the same chunks in the same order:
  bit-identical, but slower in GPU time per call (`music3_linear_bench
  sequence_timing`, quiet repeats): two rows 4096 to 4096, 0.08 ms before and
  0.10 ms after; twelve rows 4096 to 6144, 0.48 ms before and 0.59 ms after.
  Reverted. Without GPU counter profiling, further restructuring of this
  kernel is guesswork.
- Decoding MXFP8 codes once per threadgroup (see below) instead of an `exp2`
  per weight: kept because it is exact and cheap, but it moved the 8 s MXFP8
  depth stage only from about 47.6 s to 45.0 s. MXFP8 GEMVs read twice the
  bytes of 4-bit and are not decode-bound.

### DiT projection kernel: hoisted 4-bit decode

`music3_linear_tiled` decodes each four-bit weight tile in the threadgroup
before the 8x8 MMAs. Ablating it on the three real 691-row DiT shapes (quiet
host, `music3_linear_bench sequence_timing`, 691 x 2048 x 16384 shown, 18.3 ms)
located the time: removing the decode left 10.2 ms, removing the activation
staging left 15.3 ms, removing the MMAs left 15.6 ms, and removing all three
left 4.2 ms of barriers and epilogue. The matrix unit was about 15 percent of
the kernel, so this projection was decode-bound, not MMA-bound (about 2.5
TFLOPS).

The fast four-bit path now reads the 32-bit word, the scale and the offset once
per lane and reuses them for all eight codes, instead of recomputing the 64-bit
group index and reloading them for each code. Each weight is still
`float(code) * scale + offset` rounded the same way, and the MMA chain is
untouched. Interleaved on the same quiet host, before to after: 2048x2048
2.45 to 1.85 ms, 2048x16384 18.3 to 13.3 ms, 8192x2048 9.5 to 7.5 ms, so the
six projections of a block go from about 36.6 to about 28 ms.

End to end on the real 4-bit checkpoint (8 s, medians of three interleaved runs
per arm, release builds of the commit before and after, AC power, CPU about 87
percent idle but a 1-minute load average of 8, so not a benchmark row): 1 step
32.9 s to 30.1 s (RTF 4.11 to 3.76); 30 steps 130.0 s to 109.4 s (RTF 16.25 to
13.68), with the DiT stage 100.3 s to 78.7 s. The depth stage also fell (15.8
to 13.9 s at 1 step) because its row-14 and row-16 steps use the same tiled
kernel. Both arms wrote byte-identical WAVs (`16c5db73...` for 8 s, 1 step and
`361ad4d6...` for 8 s, 30 steps, the hashes recorded above).

Exactness: `music3_linear_bench hashes` (1,021 lines) and the new `dit_hashes`
mode (192 lines: 4- and 8-bit, groups 32 and 64, F16 and BF16, the real
691-row DiT shapes plus 690 and 129 rows and a ragged 2200-wide output, with and
without bias) are identical before and after. A mutation that perturbs the
hoisted weight changes 92 and 96 of those lines, so the oracle does run the new
path. The `music3_sequence`, `music3_parity`, `music3_precision` and
`music3_metal` gates pass.

A second exact change in the same kernel: the activation tile is staged with
four-wide loads (`packed_float4`, so no alignment beyond a float is assumed)
when the row length and K chunk start are multiples of four and the chunk is
full, and falls back to the scalar loop otherwise. It moves the same values.
Kernel level (`sequence_timing`, quiet GPU, three repeats): 691 x 2048 x 2048
1.84 to 1.48 ms, 691 x 2048 x 16384 12.9 to 10.3 ms, 691 x 8192 x 2048 7.25 to
5.1 ms. End to end, interleaved against the build with only the decode hoist
(medians of three, byte-identical WAVs `16c5db73...` and `361ad4d6...`, host
busier than the run above so absolute times are higher): 1 step 35.3 s to
34.2 s, 30 steps 113.6 s to 99.4 s, DiT stage 81.5 s to 68.2 s. The oracles
(`hashes`, `dit_hashes`) are unchanged, and a mutation that swaps two lanes of
the vector store changes 321 of 1,021 and all 192 lines.

After both changes, a second ablation of the 691 x 2048 x 16384 projection
(10.7 ms) puts the four-bit decode at about 2.7 ms and the MMAs at about 3.4 ms
(roughly 14 TFLOPS on their own, near the f32 ALU rate), with about 4.5 ms of
staging, barriers and epilogue. Further exact gains would need those stages to
overlap the MMAs; not attempted.

Tried and not kept, with the same oracle and timing:

- Taller or wider tiles (64x32, 32x64, 64x64 with the same 128 threads and MMA
  chain). The decode is then shared by more rows, but 64x32 gained 8 percent on
  ff_in and lost 18 percent on ff_out, and 64x64 was 2.3x slower, so none was
  kept.
- Making the K word the fastest lane index so neighbouring lanes read
  contiguous words: no gain over the hoist alone.
- A bf16 operand MMA would only speed up the part that is not the limit.
- Aliasing the result tile onto the activation and weight tiles (12 KB to 8 KB
  of threadgroup memory per group): about 1.5 percent, inside the noise.

### LM head window and AR command buffers

These changes keep the default output byte-identical by construction, and the
WAV hashes confirm it (`29c340d1...` and `16c5db73...`, every sample).

- LM head window. Sampling reads only the end token and the semantic codes.
  Every other id was already exactly -1e9 in both the conditional and the
  guided row. The device keeps rows [151616, 168064) of the head (16,448 rows,
  64-aligned) and `semantic_guided` scatters them into a -1e9 vector, so the
  sampler still sees the full vocabulary. The window starts on a multiple of
  64 because `music3_linear_tiled_16x64` places output `o` at tile column
  `o mod 64`: an aligned window gives every tile the same weight rows as the
  full head. A gather of only the allowed rows would move logits between tile
  columns, so its exactness would rest on the hardware. Metal no longer
  uploads the 200k-row head (1,503,657,984 bytes less resident). The CPU path
  keeps the full head for `Qwen3::logits`.
- One command buffer per depth step. `crates/gpu/src/music3.rs` splits
  projections, norms, and attention into `*_plan` (validation and kernel
  choice) and `encode_*`, so the synchronous call and `Music3Sequence` share
  one kernel selection (kernel hash oracle unchanged). The host steps between
  projections become `music3_add_round_bf16` (one f32 add, then the shared bf16
  rounding) and `music3_swiglu_bf16`, which indexes a 64K table of the host
  `DType::Bf16.silu` by the gate's bf16 bits instead of evaluating a Metal
  `exp`. The device may flush denormals, so a subnormal operand or result sets
  an `inexact` flag and that step is recomputed on the per-operation path.
  The two head projections stay rows=1 each, as in the per-operation path
  (rows=2 would select the tiled kernel). The profile records one
  `depth_step` row per step instead of about 43 operations.
- One command buffer per LM decode step. All 36 layers and the final norm of
  a one-position step run the per-operation path's device kernels in the same
  order (norms, projections, q/k norms, `music3_rope` with the synchronous
  parameters, time-major attention), plus the same BF16 residual add and
  SwiGLU. The KV cache moves to per-layer device buffers sized for the prompt
  plus every decode step of the request, and each step bit-copies its k and v
  rows into place (a one-position step is already in the time-major row
  layout). A step that cannot use the sequence (a trace observer, an `inexact`
  flag, a full cache) reads the history back to the host and runs per
  operation; offsets advance only after a successful submission. Prefill stays
  per operation. The device cache is allocated at full request size on the
  first decode step: 576 KB per position across the 36 layers, about 0.9 GB
  for a default 60 s request and about 8 GB at the 360 s, 5000-token ceiling.
  The host cache used to reach the same size by the end of the request.
- No depth decoder KV cache. Linear kernel choice depends on the row count:
  the recompute runs 2 x seq_len rows (4 to 16), and on M4 rows 14 and 16 take
  the split-K tiled kernels while a cache would always run 2. That changes the
  arithmetic, and MLX also recomputes.

norm, three attention kernels, add rounding over 1M pairs, SwiGLU over every
finite bf16 gate, the non-finite scan, rope and the KV row copy into a bound
cache with attention over it, bit-exact copies of NaN and subnormal patterns,

Both 30-step runs wrote the same WAV (`361ad4d6...`), which extends the
byte-identity check to the default step count. For scale, the mlx-audio
reference measured about 56 s for the same 8 s, 30-step request in an earlier
session on this host (MLX 0.31.2, BF16 activations, also not a frozen row).

The pinned MXFP8 profile (`d00a12c3...`) also reproduces the unmodified
build's WAVs byte for byte (`ec2c4a6c...` for 1 s and `0dd4ef5a...` for 8 s)
with every change, and its resident weights fall from 13.96 GB to 12.46 GB.
Its 8 s, 1-step request went from 219 s to about 77 s (single runs on a busy
host, a direction only). MXFP8 is still about twice as slow as 4-bit: its
8-bit GEMVs read twice the bytes per weight.

The depth step's time grows with the sequence (about 6 ms at length 3 to
19 ms at length 8 for both CFG rows). Sharing decoded weights across rows did
not help (see "Tried and not kept"): the affine GEMVs are latency-bound. A
faster depth step needs a kernel that keeps each output's lane and chunk order
while improving memory access (for example staging weight tiles through
threadgroup memory), or the DiT and vocoder first, which now cost more.

### DiT block command buffers and float-packed GEMV kernels

- One command buffer per DiT block. Each of the 36 blocks of a flow forward
  runs as one submission: the layer norms with their biases, the q, k, v, and
  output projections, the typed partial rotary as `music3_partial_rope_bf16`
  (the host formula `round(round(a * c) - round(b * s))` and its pair, with the
  tables rounded to BF16), attention, the feed-forward projections with their
  biases in the kernel, the gated activation as `music3_gated_silu_bf16` (the
  host SiLU table), and both residual adds. A bias goes into the sequence only
  when its dtype matches the projection's, which is when the per-operation
  path also adds it in the kernel. The same `inexact` fallback applies. The
  input conv, timestep MLP, input and output projections, and output conv stay
  per operation (once per forward). The profile records one `dit_block` row
  per block.
- Float-packed GEMVs (MXFP4, MXFP8, NVFP4). The two GEMV branches of
  `music3_linear` for these formats ran one (row, output) pair per 128-thread
  threadgroup with 16 or 32 lanes working. `music3_linear_fp_wide` (eight pairs
  of sixteen lanes) and `music3_linear_fp_vector` (four pairs of thirty-two
  lanes) keep each pair's lanes, loop order, float4 `dot`, and reduction
  verbatim; only the pairs per threadgroup change. MXFP8 codes are decoded once
  per threadgroup into threadgroup memory by `music_e4m3` itself.

Gates: the kernel hash oracle now has 1,021 lines (108 float-packed cases at a
ragged and the real width, rows 1 to 16, both dtypes, with and without bias),
identical before and after. These kernels run only at BF16, where final
rounding hides most single-ulp f32 changes, so the oracle is a backstop there:
a reordered reduction changed 9 of its lines, a halved result changed exactly
the six one-row lines. `mxfp8_gemv_decodes_every_code_exactly` pushes all 254
non-NaN MXFP8 codes through one-hot GEMVs at 1, 2, and 5 rows and requires the
exact E4M3 value of each, before and after the decode table.
`dit_block_ops_match_synchronous_and_host_bitwise` covers the DiT operations
at the real shapes (691 positions, 32 heads of 64, rotary 32, feed-forward
8192), `dit_elementwise_ops_flag_cases_the_device_may_round_differently` the
`inexact` cases, and the runtime test
`dit_block_sequences_match_the_per_op_flow_bitwise` the whole flow stage on
the seven tiny native profiles. Every guard was mutation-checked.

## Default flow profile

`Music3Runner` (the app, server, FFI and `turbospark-music` all use it) opens in
`FlowProfile::Fast`: Adams-Bashforth 2, the unconditional guidance branch
reused at interval 3 after a warmup of 2, and 21 steps when a request names no
count. That is 30 DiT forwards instead of 60. An explicit step count is always
honored, so a client that sends 30 (the Swift default) gets AB2 with reuse at 30
steps. `FlowProfile::Exact` restores the reference: Euler, both branches every
step, 30 steps by default.

This default does **not** follow MLX's trajectory. The audio differs from the
exact output (the measured drift is in the AB2 section: correlation 0.974 and
1.30 dB log-band L1 for the 21-step fast profile against the exact 30-step
WAV, one prompt, one seed, no listening test). Everything that compares against
MLX or a CPU reference pins the exact profile.

- `turbospark-music generate --flow-profile exact` (or `fast`); the
  `--flow-uncond-interval`, `--flow-uncond-warmup` and `--flow-solver` flags
  override that part of either profile.
- `Music3Runner::set_flow_profile(FlowProfile::Exact)` and
  `Model::set_flow_profile`. `Model` itself still opens in `Exact`, so library
  users and the fixture tests see the reference path.
- `music3_bench` and `ab_music3_flow.py` default to `exact` so the WAV hashes in
  this file stay reproducible; pass `--flow-profile fast` to measure the default.

## Flow guidance reuse

At the default 30 steps the DiT dominates a request: each Euler step runs the
conditional and the unconditional (CFG) forward, and the 1-step table above
hides that. `FlowGuidance { uncond_interval, uncond_warmup }` runs the
unconditional forward only on the first `uncond_warmup` steps and then every
`uncond_interval`-th step, and between those adds the last guidance correction
(`guided - conditional`) to the fresh conditional velocity. Interval 3 with
warmup 2 runs 12 unconditional forwards per 30-step chunk instead of 30, so
42 forwards instead of 60. The idea comes from the audio.cpp MiniMax Music 3
port (`flow_uncond_interval`); the numbers below are ours.

Enable it with `Model::set_flow_guidance` / `Music3Runner::set_flow_guidance`,
or `turbospark-music generate --flow-uncond-interval 3 [--flow-uncond-warmup 2]`.
`FlowGuidance::EXACT` (interval 1) is the reference trajectory, with the 1 s,
2-step, seed 7 WAV at SHA-256 `29c340d1...` (the `Model` and `exact` profile
behavior). The runner's default fast profile turns reuse on; see "Default flow
profile". Reuse changes the output.

Measured 2026-10-08 on Apple M4 Max, AC power, release build, the pinned
`mlx-community/MiniMax-Music3-4bit` snapshot (`c7ea32923b24`), caption "upbeat
acoustic folk with warm guitar", lyrics `[instrumental]`, seed 7, 8 s (one
200-frame chunk), 30 steps, interleaved by
`crates/audio/scripts/ab_music3_flow.py`. The host was **not quiet** (load
average 5 to 12 from unrelated applications), so these are not benchmark rows.

| Variant | DiT, run 0 | DiT, run 1 | Forwards |
|---|---|---|---|
| exact, 30 steps | 388 s | 273 s | 60 |
| reuse, interval 3, warmup 2, 30 steps | 228 s (0.59x) | 192 s (0.70x) | 42 |
| exact, 21 steps (cost-matched control) | 184 s | | 42 |

Run 1 had the lower load and matches the forward-count arithmetic (42 / 60 =
0.70); run 0 is noisier. Output is deterministic per variant (identical
`output_stats` across both runs). Distance to the exact 30-step WAV, from
`crates/audio/scripts/spectral_distance.py` (waveform correlation and
log-spaced band log-magnitude L1; a drift check, not a quality score):

| Candidate vs exact 30 steps | Correlation | Log-band L1 |
|---|---|---|
| reuse, interval 3, 30 steps | 0.9947 | 1.13 dB |
| exact, 21 steps (same 42 forwards) | 0.9548 | 1.48 dB |

At equal DiT cost, reuse stays closer to the 30-step reference than spending
the same forwards on fewer steps. One prompt and one seed, no listening test;
audio.cpp reports about 0.3 dB mel-L1 for the same idea on its stack with a
different metric. Treat it as a speed option, and listen before relying on it.
It is a flow-stage saving only: the AR stage and vocoder are unchanged, and a
60 s request is still far from real time.

### Flow solver: Adams-Bashforth 2

`FlowSolver::AdamsBashforth2` integrates the flow with `x += dt * (1.5 v - 0.5
v_prev)` instead of Euler's `x += dt * v`. It is second order on the uniform
sigma schedule and costs no extra DiT forward, so it is meant to be paired with
fewer steps. `v` is the final guided velocity, so it composes with
`FlowGuidance` reuse. The first step of every chunk has no history and is
Euler, and history never crosses a chunk, so a one-step request is identical to
Euler.

Enable it with `Model::set_flow_solver` / `Music3Runner::set_flow_solver`, or
`turbospark-music generate --flow-solver ab2` (`music3_bench` takes the same
flag). `FlowSolver::Euler` is the reference trajectory and the `Model` and `exact`
profile default, so the WAV hashes above are unchanged there. The runner's
default fast profile selects AB2; see "Default flow profile".

Verified in tests: the combiner is second order on `dx/dt = -x` (halving the
step quarters the error where Euler's halves), a one-step request is bit-equal
to Euler across a multi-chunk fixture, and the default path passes every pinned
flow test.

Measured 2026-10-17 on Apple M4 Max, AC power, release build, the pinned 4-bit
snapshot (`c7ea32923b24`), caption "upbeat acoustic folk with warm guitar",
lyrics `[instrumental]`, seed 7, 8 s (one chunk), one run per variant through
`ab_music3_flow.py`, scored against the exact 30-step WAV with
`spectral_distance.py`. The 1-minute load average was 8 but the CPU was about
87 percent idle and the GPU idle, so DiT times are single runs and indicative,
not benchmark rows. The `e21` and `reuse30` rows reproduce the figures above
to the digit.

| Variant (steps, solver, reuse) | DiT forwards | DiT | Correlation | Log-band L1 |
|---|---|---|---|---|
| exact: 30, Euler (reference) | 60 | 77.3 s | 1.0000 | 0 |
| 30, AB2 | 60 | 76.1 s | 0.9911 | 1.60 dB |
| 30, Euler, reuse 3/2 | 42 | 53.8 s | 0.9947 | 1.13 dB |
| 21, Euler | 42 | 54.2 s | 0.9548 | 1.48 dB |
| 21, AB2 | 42 | 55.2 s | 0.9730 | 1.33 dB |
| 21, Euler, reuse 3/2 | 30 | 37.6 s | 0.9605 | 1.50 dB |
| 21, AB2, reuse 3/2 | 30 | 36.5 s | 0.9742 | 1.30 dB |
| 15, Euler | 30 | 39.0 s | 0.7249 | 2.93 dB |
| 15, AB2 | 30 | 38.1 s | 0.7831 | 2.01 dB |
| 15, AB2, reuse 3/2 | 22 | 28.9 s | 0.7988 | 1.90 dB |

What it shows:

- At equal steps AB2 is closer to the 30-step reference than Euler (21 steps:
  0.973 vs 0.955; 15 steps: 0.783 vs 0.725). The gain is modest.
- Fifteen steps is not enough for either solver here (about 0.78), so the
  "15 AB2 steps matches 30 Euler steps" result reported for an external CUDA
  port does not reproduce on this stack.
- At equal cost, 42 forwards: Euler 30 with reuse (0.9947) beats AB2 21
  (0.9730). At 30 forwards: AB2 21 with reuse (0.9742, 1.30 dB) beats Euler 21
  with reuse (0.9605, 1.50 dB), both far above 15 steps. So the useful
  combination is AB2 with reuse and about 21 steps, at roughly half the DiT time
  of the exact path.
- Euler 30 and AB2 30 agree at 0.9911 against each other, so the Euler
  reference is not penalizing the more accurate solver much.

Limits: one prompt, one seed, one run each, a drift metric and not a quality
score, and no listening test (intelligibility, transients, chunk seams over a
full song). Treat AB2 and reuse as speed options to listen to before relying on
them.

### Evaluated against audio.cpp, not adopted

- Flow chunk hop 150 (audio.cpp `flow_chunk_hop_frames`): not implemented.
  Our chunk geometry (`CHUNK_HOP`, `OVERLAP_LATENT_LENGTH`, `CROP_*`) is derived
  for a 100-frame hop with a 172-latent carry taken from the interior of the
  previous window. At hop 150 the carry would come from the window edge, the
  hop is a non-integer 516.75 latents, and the current `chunk_starts` formula
  leaves the last frames uncovered (a 1500-frame request needs 10 chunks, not
  9). There is no objective metric here that could validate that change.
- Quantizing the depth decoder harder: audio.cpp finds it weight-bandwidth
  bound on CUDA. Ours was dispatch-bound (about 830 synchronous dispatches per
  AR frame) when this was evaluated, so it would not help. The depth step now
  runs as one command buffer. Revisit only with a measurement.
- Candidates still open and unmeasured: batching several takes through one AR
  pass (extra rows are nearly free when dispatch-bound), overlapping AR with
  flow (needs a `Send` backend), and a full on-device depth frame (needs a
  bit-exact on-device MLX threefry top-k).

Re-read 2026-10-17 against `fspecii/audio.cpp-lowend-gpu` (`cc8d599`) and the
upstream `0xShug0/audio.cpp` Music 3 docs:

- AR guidance truncation (`MM3_AR_CFG_FRAMES=50`, `MM3_DEPTH_B1=1`): full CFG
  for the first 50 frames (2 s), conditional only afterwards, which halves the
  rows of the LM decode and depth steps (LM 36.5 to 28 ms per frame on their
  CUDA stack). Our depth GEMVs cost roughly in proportion to rows, so this is
  the largest remaining AR lever here; by arithmetic on the profile it could save
  up to half of the depth stage on an 8 s clip. Not implemented: it changes the
  AR trajectory, and the fork's own rule is that anything touching the AR
  trajectory, chunking or context has to be judged by ear on a full song. Open.
- Their negative results line up with ours and are not worth repeating: a fused
  depth graph (zero gain), AR/flow pipelining on one GPU (net negative), a q4_0
  depth decoder (vocal-band energy 87 to 61 percent), an F16 vocoder (15x
  slower), and a third-order solver (worse than AB2). Their AB2 claim, 15 steps
  matching 30 Euler steps, did not reproduce on this stack (see the AB2 table).
- Flow chunk hop 150: the fork found it audibly broke songs although every
  spectral metric passed, while the upstream doc advertises it as a 35 percent
  flow saving. The two disagree; keep it unadopted.
- Upstream `MM3_DEPTH_GPU_SAMPLE` and `MM3_DEPTH_GPU_FRAME` (device top-k sampler
  and full device depth frame) are documented as byte-exact and perf-neutral,
  which supports leaving the on-device depth frame deferred.
- An F16 KV cache halves the decode allocation (about 50 percent longer songs on
  a 12 GB card). Ours is f32 at 576 KB per position (about 0.9 GB for 60 s,
  about 8 GB at the 360 s ceiling); F16 would change attention arithmetic.
- `ensemble_takes` (K takes through one batched AR pass) and
  `pipeline_overlap` (a second CUDA stream) are throughput features; neither
  fits our row-proportional GEMVs or single-queue backend without new work.

## Rust API

`Model::generate_text` stays the simple entry point. Callers that need more use:

- `generate_text_timed`: the same audio plus a `StageTimings` (tokenize,
  prefill, LM head, sampling, depth, LM decode, condition, DiT, vocoder,
  stitch). The timing code is always on and costs a few `Instant::now()` calls
  per frame, so the timed and plain paths run identical arithmetic.
- `generate_text_with_progress`: a callback receives `Progress::Tokenized`,
  one `ArFrame` per emitted frame, and one `FlowChunk` before each chunk, and
  answers `Control::Continue` or `Control::Cancel`. A cancelled request returns
  `Ok(None)` and the model is immediately reusable (each request builds fresh
  KV and overlap state). `runtime::Music3Runner` forwards both.
- `output_stats`: finite, peak, RMS, clip and silence ratios, DC offset, and
  left/right correlation of an interleaved stereo waveform. These catch broken
  output (NaN, silence, a duplicated channel); they say nothing about quality.

The model is single-threaded (`Rc` backend) and not `Send`. Open and use it on
one thread. `crates/runtime/examples/music3_generate.rs` is the minimal
library example; `turbospark-music generate --timings --wav-format float32`
exposes the same data on the command line.

## Open gates

Checkpoint-native BF16 activation parity, song quality, quiet-host frozen
performance rows, durations beyond the 16 s memory probe, the other pinned
profiles (8-bit, MXFP8, and the rest), real-time performance, and FFI/Swift
integration require separate qualification.

Native 4-bit comparison against MLX 0.32.3, measured 2026-10-17 on an Apple M4
Max (`applegpu_g16s`) with the pinned `mlx-audio` `feb25a37` and the installed
4-bit snapshot (`c7ea32923b24`), 3 AR frames, 2 flow steps, seed 7, the exact
flow profile. Frame 0 warmup, ours against MLX, per sampled codebook, on the
reference's own draws:

| Codebook | Hidden max abs error | Guided logits max abs error |
|---|---|---|
| 0 (semantic) | 0 (8,192 values) | 0 (200,000 values) |
| 1 to 3 | 0.063 to 0.094 | 0.094 to 0.125 |
| 4 to 7 | 0.89 to 1.09 | 2.70 to 5.22 |

The codebook 4 to 7 rows are not a kernel gap. The two runs draw different
codes at codebook 3 (ours 585, MLX 594, same key): the guided logits differ by
up to one bf16 step (0.094 to 0.125), which is enough to flip a top-k
categorical draw, and every later depth step then embeds a different code. The
10-row step (sequence 5) is where the inputs first differ, not where the
arithmetic does. Forcing MLX to our frame 0 draws
(`probe_minimax_music3_reference.py --force-warmup-codes
'[152575,147,505,585,967,508,981,573]'`, the semantic token first) gives:

| Codebook | Hidden max abs error | Guided logits max abs error |
|---|---|---|
| 0 | 0 | 0 |
| 1 to 7 | 0.063 to 0.094 | 0.094 to 0.125 |

Per operation (`--trace --trace-max-calls 7`, layer 0, the seven warmup depth
calls, 4 to 16 rows) the same forced run shows q/k/v at most 0.0078, attention
at most 0.0078, the post-attention residual at most 0.016, gate/up at most
0.031, down at most 0.0625 (0.25 once at call 5), the layer output at most
0.125 and the final norm at most 0.125, with a mean absolute error under 5e-4
in layer 0 (0.0035 after the final norm). Rows 10 to 16 behave like rows 4 to 8, so the qmv/qmm row
threshold, the packed GEMV, the depth attention kernel choice, and split-K are
not the cause. The residual one-step noise starts at the first depth
projection (one element of `depth.position` differs by 2e-5 at call 0) and is
rounding order, not a systematic error.

`native_gate` in `crates/runtime/tests/music3_metal.rs` used to compare
codebooks 4 to 7 after the draws had diverged, which is why the ignored test
`real_music3_pinned_4bit_native_matches_mlx_and_resets` failed with 3.8203125
against 3.0 (identically before the kernel work in this section). It now
compares a codebook's hiddens and logits only while every earlier draw matches
the reference, with the tolerance unchanged, and bounds the sampled codes by
the semantic and residual vocabularies (the old `0..256` bound was wrong for
both). With `--force-warmup-codes` all eight codebooks are compared; without it
only the codebooks up to the first flipped draw are. Both pass here. Mutating
the match tracking brings back the 3.8203125 failure. The probe does not write
the `encoding` field the test's tolerance table reads; set `"encoding":
"affine4"` in `request.json` to reach the 4-bit tolerances. No exact kernel
change is needed or possible: a one-ulp difference in the guided logits flips
draws at some rate against any MLX build, so sampled codes stay an
inexact-parity quantity for 4-bit.

The AR stage now runs about nine command buffers per frame (seven depth steps,
one LM decode step, the head) plus the depth projections between steps, and a
DiT forward runs 36 block command buffers. The remaining costs are kernel time:
the DiT's tiled projections (about 2.5 TFLOPS on the 691 x 2048 x 16384 shape,
about 37 ms of each 51 ms block), the latency-bound affine GEMVs of the depth
steps, the vocoder's convolutions, and on MXFP8 the 8-bit GEMV traffic. Each
needs GPU counter profiling before another exact restructuring is tried. A depth decoder KV cache cannot be bit-exact (see
"LM head window and AR command buffers"). The standalone command now routes full-size converted checkpoints through Metal on
macOS and keeps the CPU reference path for tiny fixtures. Existing CPU timing
rows in `MODELS.md` remain CPU evidence only.
