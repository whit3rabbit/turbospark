# OPENCODE2_COMPARISON.md

OpenCode desktop vs the TurboSpark Swift app: a feature-by-feature comparison.

- OpenCode reference: https://github.com/anomalyco/opencode (default branch `dev`),
  desktop app in `packages/desktop`, shared app UI in `packages/app`,
  `packages/session-ui`, `packages/ui`, GUI plugins in `packages/gui-plugins`.
  A shallow clone of the reference was reviewed at `/tmp/opencode-desktop-ref`
  at upstream commit `7ce35879b8` (2026-10-31).
- TurboSpark side: `swift/TurboSparkApp/Sources/TurboSparkApp/` (the macOS app)
  and `swift/TurboSpark/Sources/TurboSpark/` (the Swift wrapper over the Rust FFI).
- Status vocabulary:
  - **Aligned**: TurboSpark has a comparable feature with comparable behavior.
  - **Partial**: TurboSpark has some of it, with material gaps.
  - **Different**: both sides have the feature, but the design or scope differs.
  - **Missing in Swift**: OpenCode desktop has it, TurboSpark does not.
  - **Swift-only**: the reverse direction, collected in the last section.
- Each finding links OpenCode source files (GitHub `dev` branch), the merged PRs
  and branches that built the feature, and the TurboSwift files involved.

Method: nine investigation passes (three subagents per wave, three waves) plus a tenth verification sweep, each
pass reading the OpenCode sources and PR history for its feature domains and the
corresponding Swift sources, then reporting findings that were folded into this
document. Audited 2026-10-31.

## 1. Desktop shell, windowing, storage, and app lifecycle

OpenCode desktop is an Electron app split into a main process
([packages/desktop/src/main/index.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/index.ts)), a sandboxed preload bridge
([packages/desktop/src/preload/index.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/preload/index.ts)), and a SolidJS renderer
([packages/desktop/src/renderer/desktop-app.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/renderer/desktop-app.tsx)). The main process is built from Effect layers wired in
[packages/desktop/src/main/desktop.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/desktop.ts), and the renderer talks to it over a MessagePort RPC server
([packages/desktop/src/main/ipc.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/ipc.ts)) with typed handler groups for app, storage, files, window, menu, events, and plugins. All UI state, prompt drafts, and draft media live in one SQLite database per install
([packages/desktop/src/main/storage/index.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/storage/index.ts)), and packaging, channel, and update feeds are configured in
[electron-builder.config.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/electron-builder.config.ts).

### Multi-window model, single instance, and background lifecycle - Missing in Swift
OpenCode supports N peer main windows: a persisted window-id list in SQLite drives `restoreWindows()`, each window gets its own state file and IPC port, and closing one window never quits the app
([packages/desktop/src/main/windows/index.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/windows/index.ts),
[packages/desktop/src/main/windows/registry.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/windows/registry.ts)). Multi-window landed in [PR 17155](https://github.com/anomalyco/opencode/pull/17155), and [PR 60458](https://github.com/anomalyco/opencode/pull/60458) later fixed renderer permission handlers being clobbered across shared-session windows. A single-instance lock scoped to userData focuses the existing window on second launch
([packages/desktop/src/main/lifecycle/configure.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/lifecycle/configure.ts)), and there is no tray or global shortcut anywhere in `packages/desktop/src`. TurboSpark Swift: the App struct declares exactly one `Window("TurboSpark", id: "main")` plus Settings and MenuBarExtra scenes in
[swift/TurboSparkApp/Sources/TurboSparkApp/App/TurboSparkApp.swift](swift/TurboSparkApp/Sources/TurboSparkApp/App/TurboSparkApp.swift), with `applicationShouldHandleReopen` re-fronting the sole window and `applicationShouldTerminateAfterLastWindowClosed` reading `keepServerRunningInBackground` from
[swift/TurboSparkApp/Sources/TurboSparkApp/State/MacAppSettings.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/MacAppSettings.swift). It does have what OpenCode lacks: a MenuBarExtra server dashboard with a bolt icon tied to server state. **Verdict:** TurboSpark is deliberately single-window (so no window registry, per-window state, or Cmd+Shift+N), but it exceeds OpenCode on background presence; the gaps are multi-window support and an explicit single-instance/second-launch focus path.

### Window bounds persistence and multi-display restore - Partial
OpenCode writes per-window JSON state files (`window-state-<id>.json`, atomic tmp-rename) recording normal bounds, maximized and fullscreen flags, and the display's bounds, and validates saved bounds against currently connected displays before use
([packages/desktop/src/main/windows/window-state.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/windows/window-state.ts), built on the `brendan/electron-window-state` [branch](https://github.com/anomalyco/opencode/tree/brendan/electron-window-state)). [PR 60482](https://github.com/anomalyco/opencode/pull/60482) added the subtle case of re-centering a maximized window onto its saved display when the normal bounds no longer fit, and [PR 49869](https://github.com/anomalyco/opencode/pull/49869) made the first window appear at its restored frame before the main bundle even loads. TurboSpark Swift:
[swift/TurboSparkApp/Sources/TurboSparkApp/App/TurboSparkApp.swift](swift/TurboSparkApp/Sources/TurboSparkApp/App/TurboSparkApp.swift) does a one-time `adoptMaximizedDefaultFrameOnce()` and then relies on AppKit frame autosave for the main window, while
[swift/TurboSparkApp/Sources/TurboSparkApp/App/SettingsWindowFrame.swift](swift/TurboSparkApp/Sources/TurboSparkApp/App/SettingsWindowFrame.swift) gives the Settings scene a first-open default size and autosaved frame, and
[swift/TurboSparkApp/Sources/TurboSparkApp/App/MainWindowMinimumSize.swift](swift/TurboSparkApp/Sources/TurboSparkApp/App/MainWindowMinimumSize.swift) clamps restored minimums to the screen. **Verdict:** restoration exists but is delegated to AppKit autosave, so there is no explicit display-bound validation; a frame saved on a since-disconnected monitor is handled only by whatever AppKit does, not by TurboSpark's own fallback logic.

### App state storage: SQLite with write-behind vs JSON file stores - Different
OpenCode keeps all renderer state in one `drafts.sqlite` (WAL, `synchronous=NORMAL`) opened with node:sqlite plus drizzle, with tables `state`, `document`, `blobs`, and `plugin`, drizzle-generated migrations, and a one-time import of legacy electron-store JSON files
([packages/desktop/src/main/storage/database.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/storage/database.ts),
[packages/desktop/src/main/storage/schema.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/storage/schema.ts),
[packages/desktop/src/main/storage/legacy.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/storage/legacy.ts)). The move off electron-store was [PR 47695](https://github.com/anomalyco/opencode/pull/47695) (it froze the main thread 3-5 s per write on Windows), built on the `effect-drizzle-sqlite` [branch](https://github.com/anomalyco/opencode/tree/effect-drizzle-sqlite), and writes are coalesced by a 250 ms write-behind queue that batches upserts into one transaction
([packages/desktop/src/main/storage/state.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/storage/state.ts),
[packages/desktop/src/main/storage/write-behind.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/storage/write-behind.ts)). Storage changes broadcast `StorageChanged` to other windows via
[packages/desktop/src/main/ipc-handlers/storage.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/ipc-handlers/storage.ts). TurboSpark Swift: persistence is per-domain Codable archives written whole and atomically through `AppJSONStore`
([swift/TurboSparkApp/Sources/TurboSparkApp/State/AppStorageRoot.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppStorageRoot.swift)), with debounced chat saves in
[swift/TurboSparkApp/Sources/TurboSparkApp/State/AppModel+Persistence.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppModel+Persistence.swift) that quarantine corrupt files and surface latched read/write errors as toasts; the one SQLite usage is the encrypted per-profile `ProfileDatabase` (SQLCipher) for assets, audio index, and workflows in
[swift/TurboSparkApp/Sources/TurboSparkApp/State/ProfileDatabase.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/ProfileDatabase.swift). **Verdict:** the architectures differ by design (OpenCode general-purpose KV in SQLite, TurboSpark typed JSON plus an encrypted SQLCipher profile DB), and TurboSpark's whole-archive rewrite per keystroke burst is the same scaling wall PR 47695 tore out on the Electron side.

### Draft persistence and content-addressed blobs - Different
Drafts and conversation history go through a dedicated `document` table with a 500 ms write-behind flush, and embedded images/text chunks are stored once as sha256-addressed rows in `blobs`; a strict write refuses a document whose blob references are missing, and a JSON `json_tree` query garbage-collects orphaned blobs after a 15-minute grace
([packages/desktop/src/main/storage/drafts.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/storage/drafts.ts),
[packages/desktop/src/main/storage/migration/20260906234153_drafts/migration.sql](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/storage/migration/20260906234153_drafts/migration.sql)). [PR 40207](https://github.com/anomalyco/opencode/pull/40207) introduced this buffered blob draft store to kill composer typing lag, and [PR 59104](https://github.com/anomalyco/opencode/pull/59104) kept draft media bytes local under the experimental media URI flag. TurboSpark Swift: per-chat drafts are fields on `AppChat` saved with the 300 ms `persistChatsDebounced()` path in
[swift/TurboSparkApp/Sources/TurboSparkApp/State/AppModel+Persistence.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppModel+Persistence.swift), while attachments live in `ManagedAssetStore` and encrypted profile assets rather than a draft-local blob table. **Verdict:** TurboSpark has the debounce half (draft typing does not rewrite disk every keystroke) but nothing like the blob reference-counting and orphan GC; pasted images are re-serialized inside the whole-chat archive on every flush.

### Startup ordering: early window and first-launch onboarding - Different
OpenCode's entry module configures userData, the single-instance lock, and the scheme before `ready`, then creates an "early window" the moment Electron fires so the user sees a window while the rest of the main bundle, Effect layers, and storage load in the background; a `marks` object timestamps each stage
([packages/desktop/src/main/index.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/index.ts),
[packages/desktop/src/main/windows/early.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/windows/early.ts),
[PR 49869](https://github.com/anomalyco/opencode/pull/49869),
[PR 49872](https://github.com/anomalyco/opencode/pull/49872)). First-launch detection inspects the userData directory contents before any storage file exists, and a fresh install routes to an onboarding flow with an animated splash that preloads draft and model data before revealing the home screen
([packages/desktop/src/main/lifecycle/onboarding.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/lifecycle/onboarding.ts),
[PR 49408](https://github.com/anomalyco/opencode/pull/49408), `console-onboarding` [branch](https://github.com/anomalyco/opencode/tree/console-onboarding)). TurboSpark Swift: startup is SwiftUI-native, with `AppFontRegistrar`, activation policy, and the one-time maximized frame in the app delegate, then the scene immediately gates on `ProfileVaultCoordinator` showing
[swift/TurboSparkApp/Sources/TurboSparkApp/App/ProfileUnlockView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/App/ProfileUnlockView.swift) before any content, and shutdown ordering centralized in `AppShutdownCoordinator` in
[swift/TurboSparkApp/Sources/TurboSparkApp/State/AppModel+Persistence.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppModel+Persistence.swift). **Verdict:** no staged boot or startup marks exist on the Swift side (AppKit has no equivalent need for the window-first trick), but there is also no first-run onboarding or animated splash; the vault unlock prompt is the de facto first-launch experience.

### Renderer crash, hang, and load-failure recovery - Missing in Swift
Every OpenCode window wires `did-fail-load`, `render-process-gone`, `unresponsive`/`responsive`, and `preload-error` handlers that show a native, localized recovery dialog offering relaunch, export logs, keep waiting, or quit, with an unresponsive-time sampler attached
([packages/desktop/src/main/windows/recovery.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/windows/recovery.ts),
[packages/desktop/src/main/windows/unresponsive.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/windows/unresponsive.ts)). Main-process relaunch runs a shutdown sequence with a 10-second timeout so a hung step cannot wedge quit
([packages/desktop/src/main/lifecycle/index.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/lifecycle/index.ts)). TurboSpark Swift: nothing equivalent exists;
[swift/TurboSparkApp/Sources/TurboSparkApp/App/RootView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/App/RootView.swift) has stream-recovery presentation for agent turns
([swift/TurboSparkApp/Sources/TurboSparkApp/State/AppStreamRecovery.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppStreamRecovery.swift)) but no watchdog for a wedged UI and no self-relaunch path. **Verdict:** an AppKit app cannot lose its "renderer" the way Electron can, so the exact feature is platform-moot, but TurboSpark also lacks any hang detection, diagnostics export, or guarded relaunch on the quit path.

### Native menu bar - Partial
OpenCode builds the real macOS menu bar from a shared, platform-tagged `DESKTOP_MENU` template, translating labels natively, attaching accelerators per platform, merging GUI-plugin menu contributions, and refreshing plugin item enabled state on `menu-will-show`
([packages/desktop/src/main/native/menu.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/native/menu.ts),
[PR 46773](https://github.com/anomalyco/opencode/pull/46773),
[PR 57150](https://github.com/anomalyco/opencode/pull/57150)). Menu commands are forwarded to the focused window's renderer over IPC, and Ctrl+R is exempted from menu shortcuts so it can rename a session
([packages/desktop/src/main/ipc.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/ipc.ts)). TurboSpark Swift: a rich native menu exists as SwiftUI `Commands` in
[swift/TurboSparkApp/Sources/TurboSparkApp/App/TurboSparkApp.swift](swift/TurboSparkApp/Sources/TurboSparkApp/App/TurboSparkApp.swift), localized through bundled `Text(_:bundle:)`, with nav sections derived from `AppNavigationSection` so menus, sidebar, and shortcuts pane cannot disagree, plus hidden alternate chords in
[swift/TurboSparkApp/Sources/TurboSparkApp/App/AlternateShortcutBridge.swift](swift/TurboSparkApp/Sources/TurboSparkApp/App/AlternateShortcutBridge.swift). **Verdict:** capability is aligned (real native menus, localized, shortcut-driven); the differences are OpenCode's plugin menu contributions and cross-platform templates versus TurboSpark's static SwiftUI commands, plus OpenCode's per-window command routing that TurboSpark does not need with one window.

### Native text settings: zoom and spellcheck - Different
OpenCode persists a zoom level and optional pinch-zoom in its store, applies it at window creation so the first paint is already scaled, and clamps to 0.2-10
([packages/desktop/src/main/windows/appearance.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/windows/appearance.ts),
[PR 59277](https://github.com/anomalyco/opencode/pull/59277)). Spellcheck is a native checkbox plus a dictionary picker on Windows/Linux, with macOS left to the system spellchecker
([packages/desktop/src/main/native/spellcheck.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/native/spellcheck.ts),
[PR 59129](https://github.com/anomalyco/opencode/pull/59129)). TurboSpark Swift: text scaling is a discrete `AppearanceManager` text size (`Make Text Bigger/Smaller/Default` menu items in
[swift/TurboSparkApp/Sources/TurboSparkApp/App/TurboSparkApp.swift](swift/TurboSparkApp/Sources/TurboSparkApp/App/TurboSparkApp.swift)) driving SwiftUI dynamic type rather than a zoom factor, and there is no spellcheck configuration anywhere in the app sources (grep for spellCheck/NSChecker finds nothing), so text fields use system defaults with no toggle or dictionary picker. **Verdict:** TurboSpark covers zoom-equivalent scaling but not fractional zoom persisted per window, and has no spellcheck management at all; both gaps are visible in the Keyboard/Appearance settings surface.

### Deep link protocol handler - Missing in Swift
OpenCode registers the `opencode://` scheme in its builder config for all channels
([electron-builder.config.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/electron-builder.config.ts)), routes both `open-url` and second-instance argv into a pending deep-link queue, focuses the window named by a `console/authorized?window=` return URL, and emits `DeepLinksOpened` to the renderer
([packages/desktop/src/main/lifecycle/deep-link.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/lifecycle/deep-link.ts),
[packages/desktop/src/main/lifecycle/index.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/lifecycle/index.ts)); the renderer replays initial and runtime links into the app
([packages/desktop/src/renderer/startup/deep-links.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/renderer/startup/deep-links.ts), `console-onboarding` [branch](https://github.com/anomalyco/opencode/tree/console-onboarding)). TurboSpark Swift: no URL scheme exists, as no `onOpenURL` handler or `CFBundleURLTypes` entry is present in the app sources or
[swift/TurboSparkApp/Localization/Info.plist](swift/TurboSparkApp/Localization/Info.plist); external links are only outbound via `NSWorkspace.shared.open` in the Help menu. **Verdict:** TurboSpark cannot be driven by or return to a URL, which matters for any future OAuth/console round-trip the server or TypeSafe flows might need.

### Auto-update - Aligned
OpenCode ships electron-updater with per-channel generic feeds (`dev`, `beta`, `latest`) pointing at `opencode.ai/update/api/...`, per-channel app IDs and product names, and icons that are explicitly copied post-pack
([electron-builder.config.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/electron-builder.config.ts)); the updater itself lives in a GUI plugin that checks on launch, stages the update, and restarts through the lifecycle with a persisted "ready" marker
([packages/gui-plugins/src/updater/main.ts](https://github.com/anomalyco/opencode/blob/dev/packages/gui-plugins/src/updater/main.ts),
[packages/gui-plugins/src/updater/platform.ts](https://github.com/anomalyco/opencode/blob/dev/packages/gui-plugins/src/updater/platform.ts)), with dev builds published on every commit in [PR 59507](https://github.com/anomalyco/opencode/pull/59507), manifest sha512 integrity in [PR 53309](https://github.com/anomalyco/opencode/pull/53309), the app-update.yml fix in [PR 59529](https://github.com/anomalyco/opencode/pull/59529), and lock/signature work on the `desktop-update-lock` and `desktop-update-signature` [branches](https://github.com/anomalyco/opencode/tree/desktop-update-signature). TurboSpark Swift: Sparkle 2 with an EdDSA public key, the GitHub Releases `appcast.xml` as the feed, a guard against starting in bare `swift run` builds, a debug feed override for the two-version smoke test, and a silent auto-install driver in
[swift/TurboSparkApp/Sources/TurboSparkApp/App/Updates/SparkleUpdateController.swift](swift/TurboSparkApp/Sources/TurboSparkApp/App/Updates/SparkleUpdateController.swift), exposed via a Check for Updates menu item kept outside the vault gate in
[swift/TurboSparkApp/Sources/TurboSparkApp/App/TurboSparkApp.swift](swift/TurboSparkApp/Sources/TurboSparkApp/App/TurboSparkApp.swift). **Verdict:** both have real, signature-verified auto-update with channel thinking; the concrete differences are OpenCode's three installable channels and per-commit dev publishing versus TurboSpark's single release channel, and OpenCode's staged install-on-restart versus Sparkle's standard driver.

## 2. Chat and session core UI

OpenCode's session UI is a SolidJS app split between `packages/app` (routing, state, composer, session commands) and `packages/session-ui` (a shared rendering package for timelines, markdown, tools, and diffs used by both the desktop app and web/console). The session screen composes a virtualized message timeline, an overlaid composer region with attached "docks" (questions, permissions, queue), and plugin-hostable side/bottom panes; all session data is server-driven through the `@opencode/client` SDK, so the UI is largely a projection of server session/message/inbox state. Key surfaces:
[packages/app/src/session/screen.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/session/screen.tsx),
[packages/session-ui/src/timeline/session-timeline.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/session-ui/src/timeline/session-timeline.tsx),
[packages/app/src/session/composer/queue.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/session/composer/queue.ts),
[packages/app/src/composer/submit.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/composer/submit.ts),
[packages/session-ui/src/components/markdown.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/session-ui/src/components/markdown.tsx).

### Session screen shell, panels, and composer docks - Different
OpenCode's [session screen](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/session/screen.tsx) is a three-region layout: chat panel, an animated side region for plugin panes (review/files/terminal) with a resize handle and spring motion, and a bottom pane, with the composer floating over the timeline in a zero-height row. Question, permission, websearch, and queue docks "grow out of" the composer card as one morphing surface ([PR 57559](https://github.com/anomalyco/opencode/pull/57559), branch [composer-docks-motion](https://github.com/anomalyco/opencode/tree/composer-docks-motion)), and panel open/close uses measured spring motion with content-visibility caching ([PR 57944](https://github.com/anomalyco/opencode/pull/57944)). TurboSpark Swift renders a single [ConversationPaneView](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/ConversationPaneView.swift) per chat with a [ChatTranscriptView](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/ChatTranscriptView.swift) plus composer, and supports split chat panes ([SplitChatPanes](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/SplitChatPanes.swift)) and an artifact panel ([ArtifactPanelView](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/ArtifactPanelView.swift)), but has no plugin-hostable side/bottom pane system and no dock-morphing composer. **Verdict:** Swift covers split panes and a right artifact panel, but lacks OpenCode's resizable multi-pane session layout and unified composer-dock surface.

### Timeline projection, virtualization, and in-timeline search/quote - Partial
OpenCode projects messages into typed timeline rows via a reactive projection ([projection.ts](https://github.com/anomalyco/opencode/blob/dev/packages/session-ui/src/timeline/projection.ts)) rendered through a windowed [virtualizer](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/session/timeline/virtualizer.tsx) with cached per-session timelines, scroll pinning, reveal-by-message-id, and a timeline search bar plus quote-from-transcript ([search-bar.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/session/timeline/search-bar.tsx), [quote.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/session/timeline/quote.tsx)); the virtualizer came out of branch [brendan/message-timeline-scroll-virtualiser](https://github.com/anomalyco/opencode/tree/brendan/message-timeline-scroll-virtualiser) and prioritization of first pages in [PR 57741](https://github.com/anomalyco/opencode/pull/57741). User-message rows got a footer actions menu in [PR 60208](https://github.com/anomalyco/opencode/pull/60208). TurboSpark Swift uses a `LazyVStack` in [ChatTranscriptView](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/ChatTranscriptView.swift) with its own turn-collapse model ([TurnCollapseModel](swift/TurboSparkApp/Sources/TurboSparkApp/State/TurnCollapseModel.swift)), compaction dividers, accessibility rotor, and turn navigation, and has a separate whole-app [ChatSearchOverlayView](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/ChatSearchOverlayView.swift) with snippet highlighting, but no windowed virtualizer and no in-transcript find bar or select-to-quote affordance. **Verdict:** feature parity on collapse/search is close, but Swift's LazyVStack will degrade on very long transcripts and it lacks OpenCode's quote-back and reveal-part primitives.

### Streaming output display and turn status - Partial
OpenCode renders the running turn as projected assistant part rows inside the same timeline (grouping tool parts, compact reasoning modes per [current-tool-state.ts](https://github.com/anomalyco/opencode/blob/dev/packages/session-ui/src/message/current-tool-state.ts)), with a working indicator in the header ([session-working-indicator.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/session/header/session-working-indicator.tsx)) and an auto-retry status card with countdown ([session-retry.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/session-ui/src/components/session-retry.tsx)); streamed markdown only re-renders changed blocks ([PR 60562](https://github.com/anomalyco/opencode/pull/60562), [PR 60549](https://github.com/anomalyco/opencode/pull/60549)). TurboSpark Swift streams into a dedicated last row, [ActiveStreamingRowView](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/ActiveStreamingRowView.swift), which shows an activity line with elapsed time, collapsible live reasoning, pending tool card, live subagent cards, and streaming markdown, backed by [QueuedGenerationStream](swift/TurboSpark/Sources/TurboSpark/QueuedGenerationStream.swift) and prefill progress. **Verdict:** Swift's single growing streaming row with rich status is comparable day to day, but it re-renders full markdown per delta and has no server-style retry-with-backoff presentation.

### Message queue and steering - Partial
OpenCode queues prompts server-side in a session inbox: [queue.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/session/composer/queue.ts) manages an editable, drag-reorderable queue strip above the composer ([queue-panel.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/session/composer/queue-panel.tsx)) with optimistic edit handling ([PR 57569](https://github.com/anomalyco/opencode/pull/57569)), queued/steered grouping in session-ui ([PR 57561](https://github.com/anomalyco/opencode/pull/57561), [PR 53338](https://github.com/anomalyco/opencode/pull/53338)), and a steer moves blocking shells/subagents to background at admission ([PR 57142](https://github.com/anomalyco/opencode/pull/57142), [PR 58984](https://github.com/anomalyco/opencode/pull/58984)). TurboSpark Swift implements both delivery modes locally in [AppModel+Queue](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppModel+Queue.swift): tail drain through `run()` and mid-turn boundary delivery (`deliverSteersAtBoundary`) with hook verdicts, cancel-safe re-parking, and a composer pill ([QueuedPromptsSection](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/PromptComposerView.swift)) whose entries restore into the draft for editing. **Verdict:** semantics match closely (queue vs steer, edit-before-delivery, ordering guarantees), but Swift's queue is in-memory only per launch and lacks drag reordering and the steer-to-background move of running shells.

### Interrupt and abort semantics - Aligned
OpenCode's revert/edit paths settle work with explicit `session.interrupt` then `experimental.session.wait` calls before staging ([revert.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/session/revert.ts)), and pending inputs can be withdrawn like the TUI ([PR 57561](https://github.com/anomalyco/opencode/pull/57561) grouping work, branch [steer-background](https://github.com/anomalyco/opencode/tree/steer-background)); interrupt correctness itself is server-side (effect-based interruptible turns, [PR 52503](https://github.com/anomalyco/opencode/pull/52503)). TurboSpark Swift documents the mirror-image contract in [AppModel+Cancellation](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppModel+Cancellation.swift): a cooperative `isCancellationPending` flag where an in-flight tool finishes but no further model call starts, `finishCancelled` records partial output as a variant, and `handleEscCancelIntent`/`disarmEscCancel` ([AppModel+SlashParity](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppModel+SlashParity.swift)) guard accidental Esc. **Verdict:** Swift's cooperative stop with partial-output preservation is at parity or better for a local engine; it lacks only OpenCode's explicit wait-for-settle API surface since there is no server round trip.

### Edit, retry, and response variants - Different
OpenCode does not mutate history in place: editing or regenerating means rewinding to the message (revert staging, [revert.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/session/revert.ts)) or forking the session before the prompt with the prompt restored to the composer ([fork.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/session/fork.ts)), exposed from message menus via [PR 58865](https://github.com/anomalyco/opencode/pull/58865) ("rewind and fork from a message") and [PR 60208](https://github.com/anomalyco/opencode/pull/60208). TurboSpark Swift has true in-place variant trees: [AppModel+MessageEditing](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppModel+MessageEditing.swift) keeps `alternates` per message with a timestamp-ordered variant switcher (`stepVariant`, paired prompt+response stepping), plus retry, in-place edit ([MessageEditingViews](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/MessageEditingViews.swift)), and a separate whole-conversation branch operation (`branchConversation`) surfaced in [MessageRowView](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/MessageRowView.swift) with a "n of m" bar. **Verdict:** Swift's per-message variant navigation is a capability OpenCode's UI does not offer, while OpenCode's model preserves the full audit trail server-side and composes rewind/fork from one slash command; the two are structurally different approaches to the same job.

### Revert checkpoints and session fork - Partial
OpenCode rewind stages a server-side revert boundary (`session.revert.stage/clear`) that also restores files, offers an inline undo toast, and treats queued inputs specially ([revert.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/session/revert.ts), [PR 54410](https://github.com/anomalyco/opencode/pull/54410) keeps the instruction baseline, branch [draft/session-timeline-rewind](https://github.com/anomalyco/opencode/tree/draft/session-timeline-rewind)); forking duplicates history into a new session and opens it ([fork.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/session/fork.ts), [PR 60118](https://github.com/anomalyco/opencode/pull/60118) stores forked media as blobs). TurboSpark Swift has transcript-level `rewindTo(anchorMessageID:)` and `branchConversation(titled:)` in [AppModel+SlashParity](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppModel+SlashParity.swift) with a `BranchTarget` preview in [MessageRowView](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/MessageRowView.swift), plus compaction boundaries ([AppChatCompaction](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppChatCompaction.swift)) and a compaction divider view. **Verdict:** Swift covers conversation rewind and branching, but rewind truncates the transcript rather than restoring workspace files, and there is no one-click fork-from-message that re-opens the prompt in a new session composer.

### Agent questions (ask user) - Aligned
OpenCode shows an elicitation dock under the composer with single/multi-select, custom answers, 1-9 shortcuts, and a classic/experimental toggle ([session-question-dock.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/session/requests/session-question-dock.tsx)), refreshed in [PR 54822](https://github.com/anomalyco/opencode/pull/54822) and animated with the composer in [PR 57559](https://github.com/anomalyco/opencode/pull/57559) (motion later made opt-in in [PR 59389](https://github.com/anomalyco/opencode/pull/59389)); requests resolve across child sessions via the request tree ([session-request-tree.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/session/requests/session-request-tree.ts)). TurboSpark Swift parks the turn on an `AskUserQuestion` call and renders [InteractiveQuestionCardView](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/InteractiveQuestionCardView.swift) at the transcript bottom with single-select immediate answer, multi-select plus custom answers submitted as one map, VoiceOver announcements, and `waitForUserAnswers`/`submitUserQuestionAnswers` in [AppModel+Questions](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppModel+Questions.swift). **Verdict:** functionally aligned including multi-select and free text; Swift lacks only keyboard-number shortcuts and multiple stacked question docks from child sessions.

### Composer: editor, prompt history, slash and shell mode - Partial
OpenCode's composer is a contenteditable with a suggestion state machine ([editor.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/composer/editor/editor.tsx), [suggestions/machine.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/composer/suggestions/machine.ts)), persisted draft prompt history ([history/store.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/composer/history/store.ts)), client-side slash commands ([client-slash-command.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/composer/client-slash-command.ts)), an explicit shell mode, and submission that handles delivery mode (steer vs queue) and model switching ([submit.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/composer/submit.ts)); slash commands respect queue follow-up behavior in [PR 48169](https://github.com/anomalyco/opencode/pull/48169) and skills appear in slash in [PR 47247](https://github.com/anomalyco/opencode/pull/47247). TurboSpark Swift's [PromptComposerView](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/PromptComposerView.swift) with [PromptComposerEditor](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/PromptComposerEditor.swift) has up/down draft history recall, an autocomplete engine for slash and `@` mentions including quoted paths ([ComposerAutocompleteEngine](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/ComposerAutocompleteEngine.swift)), local slash commands (/model, /theme, /rename, /branch, /btw, /fork, /recap in [AppModel+LocalCommands](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppModel+LocalCommands.swift)) and `!` shell bang commands ([AppModel+BangCommands](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppModel+BangCommands.swift)). **Verdict:** Swift matches history, slash, mentions, and shell parity, but has no draft persistence across relaunch, no shared rich-text editor (plain text editor), and no model-picker integrated into the composer the way OpenCode's model control is.

### Attachments: images and files in chat - Partial
OpenCode supports drag-drop ([dropzone.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/composer/dropzone.tsx)), clipboard paste, blob-backed draft persistence, and uploads ([attachments.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/composer/attachments/attachments.ts)), with image previews in the timeline overlay ([PR 49111](https://github.com/anomalyco/opencode/pull/49111)), path-delivered attachment previews ([PR 57249](https://github.com/anomalyco/opencode/pull/57249)), and local media bytes for drafts ([PR 59104](https://github.com/anomalyco/opencode/pull/59104)); attachment cards render in messages ([attachment-card.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/session-ui/src/message/attachment-card.tsx)). TurboSpark Swift attaches via file/folder pickers and paste ([AppModel+Paste](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppModel+Paste.swift), [PromptAttachmentsView](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/PromptAttachmentsView.swift)), extracts document text ([DocumentTextExtractor](swift/TurboSparkApp/Sources/TurboSparkApp/Presentation/DocumentTextExtractor.swift)), gates images on the loaded model's vision support with a refusal toast (visible in [AppModel+Queue](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppModel+Queue.swift)), and renders `imagePaths` inline in [MessageRowView](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/MessageRowView.swift). **Verdict:** parity on paste, documents, and inline image rendering; gaps are drag-and-drop onto the composer, zoomable image overlay, and persisted blob-backed drafts.

### Markdown rendering and syntax highlighting - Different
OpenCode renders markdown through a web worker pipeline that streams block-level projections with healing of unterminated fences ([markdown-stream.ts](https://github.com/anomalyco/opencode/blob/dev/packages/session-ui/src/components/markdown-stream.ts), [markdown.worker.ts](https://github.com/anomalyco/opencode/blob/dev/packages/session-ui/src/components/markdown.worker.ts)), uses `@pierre/highlights` for code ([PR 57937](https://github.com/anomalyco/opencode/pull/57937)), renders mermaid ([markdown-mermaid.ts](https://github.com/anomalyco/opencode/blob/dev/packages/session-ui/src/components/markdown-mermaid.ts)), session links and fragment scrolling ([PR 59550](https://github.com/anomalyco/opencode/pull/59550)), and sanitized selection copy ([PR 59151](https://github.com/anomalyco/opencode/pull/59151)). TurboSpark Swift uses MarkdownUI with a custom theme in [ChatMessageMarkdownView](swift/TurboSparkApp/Sources/TurboSparkApp/Presentation/ChatMessageMarkdownView.swift), a hand-rolled tokenizer-based [CodeSyntaxHighlighter](swift/TurboSparkApp/Sources/TurboSparkApp/Presentation/CodeSyntaxHighlighter.swift), interactive tables ([InteractiveMarkdownTableView](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/InteractiveMarkdownTableView.swift)), HTML fence preview into the artifact panel, and ANSI coloring for tool output ([ANSIColorizer](swift/TurboSparkApp/Sources/TurboSparkApp/Presentation/ANSIColorizer.swift)). **Verdict:** Swift covers tables, code color, and HTML preview, but has no incremental streaming markdown projection, no mermaid, and a far smaller language grammar set than the highlighter library OpenCode adopted.

### Diff and tool rendering in the transcript - Partial
OpenCode renders tool parts through a per-tool renderer with collapsed groups and counts ([tool-renderer.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/session-ui/src/tools/tool-renderer.tsx), [tool-count-summary.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/session-ui/src/components/tool-count-summary.tsx)), per-turn file-change summaries ([turn-diffs.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/session/timeline/turn-diffs.ts), [PR 55064](https://github.com/anomalyco/opencode/pull/55064)), and a review side panel with Pierre-based file diffs ([session-review.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/session-ui/src/components/session-review.tsx), [session-diff.ts](https://github.com/anomalyco/opencode/blob/dev/packages/session-ui/src/components/session-diff.ts), [PR 51640](https://github.com/anomalyco/opencode/pull/51640), [PR 57551](https://github.com/anomalyco/opencode/pull/57551)). TurboSpark Swift renders each tool as a [ToolCallCardView](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/ToolCallCardView.swift) with approval dropdown ([ToolApprovalDropdown](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/ToolApprovalDropdown.swift)), diff stats via [ToolCallDiffFormatter](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/ToolCallDiffFormatter.swift), grouped tool rows ([ToolGroupView](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/ToolGroupView.swift)), and git worktree diffs ([WorktreeDiffView](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/WorktreeDiffView.swift)); todos render as [TodoChecklistViews](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/TodoChecklistViews.swift) inside the transcript. **Verdict:** Swift has strong inline tool cards and worktree diffs but no side-by-side unified diff viewer with line commenting, and its todo checklist lives in the transcript rather than OpenCode's persistent composer pill ([PR 59092](https://github.com/anomalyco/opencode/pull/59092), [PR 59979](https://github.com/anomalyco/opencode/pull/59979)).

### Session list, rename, search, and usage display - Partial
OpenCode's home/session list supports inline rename via an `InlineInput`, archive and context menus ([home/sessions/view.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/home/sessions/view.tsx)), server-paginated session listing ([list.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/session/list.ts)), search focus shortcuts ([PR 53761](https://github.com/anomalyco/opencode/pull/53761), [PR 58964](https://github.com/anomalyco/opencode/pull/58964)), auto-generated titles ([title.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/session/title.ts)), and provider quota surfaces: usage-exceeded dialogs with retry-after ([usage-exceeded-dialogs.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/session/usage-exceeded-dialogs.tsx)) and a go-limit tray ([go-limit-tray.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/session/composer/go-limit-tray.tsx)). TurboSpark Swift's [ChatSidebarView](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/ChatSidebarView.swift) covers rename (alert-based), pin, archive, duplicate, and time-bucket grouping, with local full-text search including snippets in [ChatSearch](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/ChatSearch.swift) and `/rename` in [AppModel+SlashParity](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppModel+SlashParity.swift); usage is a context ring in the composer ([ContextUsageRingView](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/ContextUsageRingView.swift)) plus a day-bucketed token dashboard ([AppChatUsage](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppChatUsage.swift), [AppChatStats](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppChatStats.swift)). **Verdict:** session management is at parity or better (Swift pins and duplicates chats), but rename uses a modal alert rather than inline editing, there is no per-message token/cost display in the transcript, and the usage surfaces target opposite domains: local context-window pressure vs OpenCode's hosted provider quotas.

## 3. Settings, providers, models, servers (MCP), and permissions

OpenCode keeps its entire settings surface in one SolidJS package under [packages/app/src/settings](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/settings/shell.tsx), shared by the desktop shell and the web build. Twelve root pages (general, appearance, notifications, shortcuts, projects, workspaces, providers, models, extensions, servers, experimental, about) are declared in [pages.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/settings/pages.ts) and routed as URL-parseable views (app / server / project scopes, per-server pages, plugin-contributed tabs) in [route.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/settings/route.ts) and [surface.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/settings/surface.tsx). Client-side state is a versioned persisted schema in [model.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/settings/model.tsx) (including keybind overrides, per-project auto-approve, and notification/sound channels), while provider credentials, agents, commands, and MCP servers live server-side in config. The whole surface is indexed for search in [search-index.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/settings/search-index.ts).

### Settings shell and page structure - Different
OpenCode renders one settings app with a sidebar of 12 root tabs plus plugin-contributed tabs and per-project views; the shell ([shell.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/settings/shell.tsx), [surface.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/settings/surface.tsx)) resolves the active server so providers, models, projects, and extensions pages are all per-server. The redesign that introduced app/server/project scopes and search shipped in [PR 48174](https://github.com/anomalyco/opencode/pull/48174) (branch [settings-search](https://github.com/anomalyco/opencode/tree/settings-search)), and projects got their own grouped page in [PR 60221](https://github.com/anomalyco/opencode/pull/60221). TurboSpark Swift: a native macOS Settings window with 18 panes in two categories ([SettingsTab.swift](swift/TurboSparkApp/Sources/TurboSparkApp/App/SettingsTab.swift), [AppSettingsView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/App/AppSettingsView.swift)), deep-linkable via a `.openSettingsTab` notification and `requestedSettingsTab`. State persists to a local settings.json with corrupt-file quarantine and Keychain opt-in ([AppModel+Persistence.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppModel+Persistence.swift)). **Verdict:** comparable breadth (TurboSpark has more panes: Memory, Soul, Safety, Hooks, Automation, Browser), but OpenCode's settings are multi-server/multi-project addressable by URL while TurboSpark's are single-user desktop with user-vs-project scopes only.

### Settings search and command palette - Partial
OpenCode builds a search index over pages and individual setting rows ([search-index.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/settings/search-index.ts), [search-catalog.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/settings/search-catalog.ts)) with keyboard navigation, target highlighting, and disambiguation ([PR 48174](https://github.com/anomalyco/opencode/pull/48174), polish in [PR 48210](https://github.com/anomalyco/opencode/pull/48210)); the same rows surface as command-palette entries that open Settings directly at the row ([palette.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/settings/palette.ts), [PR 57651](https://github.com/anomalyco/opencode/pull/57651), ranking fix [PR 57899](https://github.com/anomalyco/opencode/pull/57899)). TurboSpark Swift: the settings sidebar has a search field filtering tab titles plus per-tab keywords, and a control-level catalog ([SettingsControlCatalog.swift](swift/TurboSparkApp/Sources/TurboSparkApp/App/SettingsControlCatalog.swift)) whose results navigate to a pane and highlight a specific control via `.settingsControl(...)` anchors ([AppSettingsView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/App/AppSettingsView.swift)). **Verdict:** row-level search with jump-and-highlight exists in both, but TurboSpark has no global command palette: settings are reachable only from the settings window, while OpenCode finds settings from the same palette that runs commands.

### Provider connect, accounts, and OAuth - Missing in Swift
OpenCode's provider page ([providers.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/settings/providers/providers.tsx)) connects cloud providers (Anthropic, OpenAI, Google, OpenRouter, Copilot, OpenCode Console) through a connect dialog with per-provider methods: API key, OAuth device code with polling and external browser, or command ([dialog.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/providers/connect/dialog.tsx), [controller.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/providers/connect/controller.ts)), with multiple named accounts per provider ([accounts.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/settings/providers/accounts.ts)). Custom providers connect through config ([PR 40761](https://github.com/anomalyco/opencode/pull/40761)), and the Console integration dialog was matched to the TUI in [PR 56877](https://github.com/anomalyco/opencode/pull/56877) (branch [beta-integration-parity](https://github.com/anomalyco/opencode/tree/beta-integration-parity)). TurboSpark Swift: the only provider auth is a Hugging Face token for checkpoint downloads, validated against whoami ([Auth.swift](swift/TurboSpark/Sources/TurboSpark/Auth.swift)) and edited in one canonical card in the Models pane ([ModelsSettingsPaneView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Components/ModelsSettingsPaneView.swift)); the local API daemon's key is a Keychain opt-in ([ServerKeychain.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Server/ServerKeychain.swift)). **Verdict:** there is no remote inference provider concept in the Swift app at all: no OAuth login, no API-key providers, no account switching, because all generation runs on the local engine.

### Model catalog and model management - Different
OpenCode lists every model of every connected provider grouped by provider ([models.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/settings/models/models.tsx)), lets users hide/show models per workspace ([manage.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/providers/models/manage.tsx)), reads config-pinned default models ([configured.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/providers/models/configured.ts)), and picks models with variants from the composer ([selection.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/providers/models/selection.tsx)); config-defined custom models got typed model types in [PR 59388](https://github.com/anomalyco/opencode/pull/59388). TurboSpark Swift: a local catalog of pinned checkpoints (repo plus commit sha in [Catalog.swift](swift/TurboSpark/Sources/TurboSpark/Catalog.swift)) with a browse/install hub ([ModelHubView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Installation/ModelHubView.swift), [ModelInstallView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Installation/ModelInstallView.swift)) including hardware-fit recommendations, probes, storage locations, LM Studio library scanning, and installed-model detail panes. **Verdict:** the two manage disjoint things: OpenCode curates visibility of cloud models, TurboSpark curates downloads and on-disk storage of local weights; TurboSpark has no remote model picker and OpenCode has no install/storage UI.

### MCP server management - Partial
OpenCode's MCP servers are config-defined and surfaced read-only in Extensions: the extensions page lists MCPs with connected/failed/needs_auth/disabled status and per-location toggles ([extensions.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/settings/providers/extensions.tsx)), a searchable MCPs dialog toggles them ([mcp-dialog.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/providers/connect/mcp-dialog.tsx)), and toggling performs connect/disconnect plus OAuth sign-in for `needs_auth` servers via an integration method ([mcp.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/providers/connect/mcp.ts)); row polish and location-correct toggling landed in [PR 58979](https://github.com/anomalyco/opencode/pull/58979) and [PR 59132](https://github.com/anomalyco/opencode/pull/59132), with auth clarity on branch [auth-login-mcp-clarity](https://github.com/anomalyco/opencode/tree/auth-login-mcp-clarity). TurboSpark Swift: a full management pane, [McpSettingsPaneView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Components/McpSettingsPaneView.swift), with Add Server editor sheets, import, per-server connection test, discovered-tool counts, a codemode feature toggle, and user-vs-project scoping ([ExtensionScopePicker.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Components/ExtensionScopePicker.swift)); transports are stdio and SSE with headers ([McpServerSpec.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Tools/MCP/McpServerSpec.swift)). **Verdict:** TurboSpark is stronger on add/edit/test that OpenCode leaves to opencode.json, but has no MCP OAuth: a server requiring auth cannot be signed into from the Swift app the way OpenCode's toggle does.

### Server connections vs in-process server - Different
OpenCode's Servers page ([servers.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/settings/servers/servers.tsx)) manages connections to OpenCode backend servers: add by URL with optional password and live health preview ([management.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/servers/registry/management.ts)), an add menu extensible by plugins ([add-menu.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/servers/registry/add-menu.tsx)), and pairing with the desktop host including QR scan and code redeem ([pairing.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/servers/connect/pairing.ts), [scanner.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/servers/connect/scanner.tsx)). The desktop window also runs its own server's plugin GUIs ([PR 59489](https://github.com/anomalyco/opencode/pull/59489), branch [merge-plugin-settings](https://github.com/anomalyco/opencode/tree/merge-plugin-settings)). TurboSpark Swift: no remote-engine connection UI; instead the Engine pane exposes the local in-process server (port, address, auth key) in [EngineSettingsPaneView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/App/EngineSettingsPaneView.swift), and the Server/ directory ([ServerPaneView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Server/ServerPaneView.swift), [TypeSafeAPIPaneView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Server/TypeSafeAPIPaneView.swift)) is a dashboard for the app's own OpenAI-compatible and TypeSafe daemons. **Verdict:** opposite directions: OpenCode connects out to servers, TurboSpark serves out from the Mac; neither can do the other's model.

### In-session permission prompts - Partial
OpenCode shows each permission request as a dock prompt with Deny / Allow Always / Allow Once, per-action descriptions and resource patterns ([session-permission-dock.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/session/requests/session-permission-dock.tsx)); "always" decisions persist server-side ([saved.ts](https://github.com/anomalyco/opencode/blob/dev/packages/core/src/permission/saved.ts)), and the request flow was reshaped on branches [auto-accept-permissions](https://github.com/anomalyco/opencode/tree/auto-accept-permissions) and [composer-permission-dropdown](https://github.com/anomalyco/opencode/tree/composer-permission-dropdown). TurboSpark Swift: an in-app permission engine classifies every call into allow / ask / deny with a risk classifier and ordered gates ([AppToolPermissionEngine.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Tools/Core/AppToolPermissionEngine.swift), [ToolRiskClassifier.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Tools/Core/ToolRiskClassifier.swift)), and "Always Allow" grants live in a session-scoped actor store for tool names and command prefixes. **Verdict:** conceptually aligned (once / always / deny with risk context), but TurboSpark's session approvals die with the session and its confirmation UI lives in the tool call card rather than a single dedicated prompt surface.

### Permission defaults and per-project policy - Partial
OpenCode makes auto-accept one app-wide default switch in Preferences with per-project overrides (Use default / On / Off) in project settings ([general.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/settings/general/general.tsx), [PR 44608](https://github.com/anomalyco/opencode/pull/44608), [PR 54839](https://github.com/anomalyco/opencode/pull/54839)). TurboSpark Swift: project settings expose per-category permissions (file read/write, terminal, web, browser, MCP, automation), presets, a browser origin allowlist, and a guardrails override ([ProjectPermissionsSectionView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/ProjectPermissionsSectionView.swift)), plus persisted MCP allow/deny rules with `mcp__server__tool` matching ([McpPermissionRules.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Tools/Core/McpPermissionRules.swift)) and a command-classifier veto toggle ([PermissionsInfoSectionsView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Components/PermissionsInfoSectionsView.swift)). **Verdict:** TurboSpark's policy surface is far finer-grained than OpenCode's single auto-accept toggle, but OpenCode's global default-with-override ordering (app switch overridden per project) is a cleaner shape than TurboSpark's per-project-everything, and macOS TCC folder grants ([PermissionsSettingsPaneView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Components/PermissionsSettingsPaneView.swift)) have no OpenCode counterpart.

### Keybind customization - Missing in Swift
OpenCode's Shortcuts page groups every command ([keybinds.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/settings/keybinds/keybinds.tsx)), records new chords, rebinds and unbinds commands including plugin commands, and migrates overrides when command ids rename ([migration.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/settings/keybinds/migration.ts)); unbind-while-recording shipped in [PR 58964](https://github.com/anomalyco/opencode/pull/58964) (branch [shortcuts-search](https://github.com/anomalyco/opencode/tree/shortcuts-search)), registry dedup in [PR 59499](https://github.com/anomalyco/opencode/pull/59499), with panel work on branch [desktop-shortcuts-panel](https://github.com/anomalyco/opencode/tree/desktop-shortcuts-panel). TurboSpark Swift: the Keyboard Shortcuts pane is a read-only catalog derived from the menu commands, and its intro states "Shortcuts are fixed. There is no rebinding in this version." ([KeyboardShortcutsSettingsPaneView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/App/KeyboardShortcutsSettingsPaneView.swift), [KeyboardShortcutCatalog.swift](swift/TurboSparkApp/Sources/TurboSparkApp/App/KeyboardShortcutCatalog.swift)); alternate chords are fixed hidden buttons via [AlternateShortcutBridge.swift](swift/TurboSparkApp/Sources/TurboSparkApp/App/AlternateShortcutBridge.swift). **Verdict:** no rebinding store exists in TurboSpark; any customization would need an override store plus a capture UI from scratch.

### Notification and sound settings - Missing in Swift
OpenCode has a dedicated Notifications page with per-event desktop-notification toggles for agent done, permissions, questions, and errors ([notifications.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/settings/notifications/notifications.tsx)) plus per-event sound pickers wired through persisted sound channels ([controllers.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/settings/general/controllers.ts)); question notifications and sounds shipped in [PR 60358](https://github.com/anomalyco/opencode/pull/60358) (branch [question-notifications](https://github.com/anomalyco/opencode/tree/question-notifications)), with delivery fixes in [PR 60378](https://github.com/anomalyco/opencode/pull/60378) and related branches [notification-audio](https://github.com/anomalyco/opencode/tree/notification-audio), [desktop-notify-click](https://github.com/anomalyco/opencode/tree/desktop-notify-click). TurboSpark Swift: the General pane ([GeneralSettingsPaneView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/App/GeneralSettingsPaneView.swift)) has no notification or sound section, and no App-side UserNotifications usage exists outside automation executors. **Verdict:** TurboSpark has no user-facing control over when the app pings or sounds; background-task and permission events are silent or ad hoc compared to OpenCode's four-event matrix.

### Custom agents and slash commands - Partial
OpenCode treats agents and commands as config-file data on the server: the app cycles agents from the composer and exposes commands as slash entries (/model, /connect, /reload, /agent) in the command registry ([commands.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/composer/commands.tsx)), General only toggles whether custom agents are shown ([general.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/settings/general/general.tsx)), and dynamic agent resolution is in flight on branch [add-dynamic-agents-resolving](https://github.com/anomalyco/opencode/tree/add-dynamic-agents-resolving). TurboSpark Swift: an Agents and Subagents pane manages built-in, user-scope, and project-scope agents with an editor and markdown import ([AgentsSettingsPaneView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Components/AgentsSettingsPaneView.swift), parser in [AgentParser.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/AgentParser.swift), file import in [AgentManager+Files.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/AgentManager+Files.swift)), and slash commands are one shared table feeding autocomplete, the plus menu, and the submit gate ([BuiltInSlashCommand.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/BuiltInSlashCommand.swift)). **Verdict:** TurboSpark edits agents in-app where OpenCode sends you to config files, but OpenCode's slash-command surface includes app-level commands (connect, reload, model) registered with keybinds, while TurboSpark's table is chat dispatch only and project-defined custom slash commands do not exist.

### Tool profiles (per-turn tool sets) - Different
OpenCode has no tool-profile page: the settings route table ([route.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/settings/route.ts)) has no tools tab, and tool availability follows per-agent config rather than a user-managed set. TurboSpark Swift shipped tool profiles in PR #224 (branch feat/tool-profiles-and-call-normalization): a Tools pane where code-defined built-in profiles are read-only and duplicates become editable sets ([ToolsSettingsPaneView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/App/ToolsSettingsPaneView.swift)), surfaced as a composer Tools chip with per-session flips, backed by the same dispatch gate that enforces permissions ([ToolCallDispatchGate.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Tools/Core/ToolCallDispatchGate.swift)). General pane chat-runtime bindings ([ChatRuntimeSettingsBindings.swift](swift/TurboSparkApp/Sources/TurboSparkApp/App/ChatRuntimeSettingsBindings.swift)) further gate tools, microcompact, and native tool calling per chat. **Verdict:** this is a TurboSpark-only capability aimed at small local models ("smaller sets suit smaller local models"); OpenCode's nearest analog is agent-scoped tool config in files, so there is nothing to port in the other direction either.

## 4. GUI plugins (terminal, review, browser, ssh, file, and more)

OpenCode's desktop app has no bespoke features: every surface beyond the core shell is a "built-in GUI plugin" (terminal, review, file, browser, ssh, wsl, pairing, office, debug, btw, goal, context, sources, details, updater) that declares itself through the same `@opencode/plugin/gui` SDK a third-party plugin uses, via `Plugin.define` with `Panel`, `Command`, `MenuItem`, `SettingsPage`, `Slot`, and store registrations. The system was established by [PR 55246 "feat(plugin): add OpenCode Desktop GUI plugins"](https://github.com/anomalyco/opencode/pull/55246) and [PR 52369 "move GUI features into built-in extensions"](https://github.com/anomalyco/opencode/pull/52369), extended with toasts/dialogs/tabs/composer APIs in [PR 59469](https://github.com/anomalyco/opencode/pull/59469) and a per-plugin settings page in [PR 59489 "manage desktop plugins in Extensions > Plugins"](https://github.com/anomalyco/opencode/pull/59489). Two host processes cooperate: the Electron main-process host ([packages/desktop/src/main/plugin/](https://github.com/anomalyco/opencode/tree/dev/packages/desktop/src/main/plugin)) loads `mainEntry` code, owns Ipcs, storage, embeds and menubar items, and bridges everything to windows over typed IPC, while each window's renderer host ([packages/desktop/src/renderer/plugins.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/renderer/plugins.ts)) mounts the plugin's Solid components into the session screen's side panel region and slots. Plugin code is only ever executed through `evaluatePluginBundle` in the host-only `gui/host` module, which shares a fixed module map (effect, plugin SDK, client, schema) and refuses anything else, with enable state persisted in a SQLite table per plugin id ([manager.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/plugin/manager.ts)) and a serialized per-plugin lifecycle with cleanup timeouts ([lifecycle.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/plugin/lifecycle.ts)). The author guide ([packages/gui-plugins/README.md](https://github.com/anomalyco/opencode/blob/dev/packages/gui-plugins/README.md), [AGENTS.md](https://github.com/anomalyco/opencode/blob/dev/packages/gui-plugins/AGENTS.md)) documents pane docking, store migrations, and lifetime rules; the single built-in list lives in [packages/gui-plugins/src/renderer.ts](https://github.com/anomalyco/opencode/blob/dev/packages/gui-plugins/src/renderer.ts) and [main.ts](https://github.com/anomalyco/opencode/blob/dev/packages/gui-plugins/src/main.ts).

### Plugin runtime (discovery, loading, sandboxing, settings) - Missing in Swift
OpenCode's main host ([host.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/plugin/host.ts)) lists built-ins via `compose`, fetches third-party `./gui-experimental` bundles from the app's own server, evaluates them with `evaluateMain` ([module.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/plugin/module.ts)) against a closed module map (window-only modules become inert placeholders, `electron` and Node builtins are real), and exposes enable/disable/reload plus a settings page per plugin through the Extensions > Plugins UI from [PR 59489](https://github.com/anomalyco/opencode/pull/59489). Contributions are withdrawn with their owner: an Ipc going away is a suspend-and-resume state, not a crash, and a plugin restart keeps the caller alive via `lifecycle.restart(handoff)`. TurboSpark Swift: Nothing equivalent exists in the Swift app sources. There is no plugin discovery, no bundle evaluator, no per-feature enable/disable, and no Extensions settings surface; features are compiled into the app and docked by a hardcoded claimant switch in [swift/TurboSparkApp/Sources/TurboSparkApp/App/RootView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/App/RootView.swift) (`rightColumnClaimant`: artifact, filePreview, browser, inspector, projectSummary). The nearest adjacent capability is the tool registry and permission engine in [swift/TurboSparkApp/Sources/TurboSparkApp/Tools/Registry/AppToolRegistry.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Tools/Registry/AppToolRegistry.swift), which gates agent-callable tools but not UI. **Verdict:** OpenCode can load, sandbox, disable and hot-reload UI features at runtime; TurboSpark's feature set is fixed at compile time, so every plugin comparison below is a comparison against a hardcoded view.

### Terminal - Missing in Swift (UI pane); agent-side shell execution is Different
OpenCode's terminal plugin docks one ghostty-web terminal tab per shell into the session side panel ([renderer.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/gui-plugins/src/terminal/renderer.tsx)), with `ctrl+\` toggle, `ctrl+alt+t` new, rename, quote-to-composer ([PR 58420](https://github.com/anomalyco/opencode/pull/58420)), and tab-restore through transient panel tabs. Since [PR 60346 "move the desktop terminal to persistent PTYs"](https://github.com/anomalyco/opencode/pull/60346) (branch `desktop-persistent-pty`; server protocol shared in [PR 60323](https://github.com/anomalyco/opencode/pull/60323)), PTYs live on the server: a snapshot restores scrollback, sessions survive app and server restarts, and terminals are shared with the TUI and other windows, with an ordered replay/resize queue in [connection.ts](https://github.com/anomalyco/opencode/blob/dev/packages/gui-plugins/src/terminal/connection.ts). TurboSpark Swift: There is no embedded terminal pane, no PTY, and no terminal emulator view anywhere in the app (no SwiftTerm/xterm dependency in [swift/TurboSparkApp/Package.swift](swift/TurboSparkApp/Package.swift)). Shell execution exists only as agent tools: [swift/TurboSparkApp/Sources/TurboSparkApp/Tools/Terminal/ShellCommandRunner.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Tools/Terminal/ShellCommandRunner.swift) one-shot runs, [swift/TurboSparkApp/Sources/TurboSparkApp/Tools/Terminal/BackgroundShellManager.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Tools/Terminal/BackgroundShellManager.swift) capped-buffer background shells (`run_in_background`), and a persistent REPL worker under [swift/TurboSparkApp/Sources/TurboSparkApp/Tools/Repl/](swift/TurboSparkApp/Sources/TurboSparkApp/Tools/Repl/). **Verdict:** the user-facing persistent terminal with shared scrollback is a concrete gap; the Swift app's shell story is model-driven only and dies with the tool call.

### SSH (remote server connections) - Missing in Swift
The ssh plugin ([main.ts](https://github.com/anomalyco/opencode/blob/dev/packages/gui-plugins/src/ssh/main.ts), built on [PR 47753 "add SSH server connections"](https://github.com/anomalyco/opencode/pull/47753), fix [PR 48442](https://github.com/anomalyco/opencode/pull/48442)) runs in the Electron main process, saves hosts (`servers` store migrated from the old settings key), boots the OpenCode CLI on the remote over SSH, answers passphrase/2FA challenges through a per-window dialog, and contributes `Server` registry entries so remote projects appear alongside local ones with reconnect, cover states and per-row menus ([renderer.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/gui-plugins/src/ssh/renderer.tsx)). TurboSpark Swift: Nothing equivalent exists in the Swift app sources; the only "ssh" matches are risk-classification regexes protecting `~/.ssh` keys in [swift/TurboSparkApp/Sources/TurboSparkApp/Tools/Core/ToolRiskClassifier.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Tools/Core/ToolRiskClassifier.swift). The app runs one local engine process per model (see the Server section of [swift/TurboSparkApp/Sources/TurboSparkApp/Server/](swift/TurboSparkApp/Sources/TurboSparkApp/Server/)) with no notion of remote hosts or projects. **Verdict:** remote/SSH project hosting is absent; connecting TurboSpark to a remote machine would need both a connection manager and a remote runner, neither of which exists.

### WSL (Windows distro servers) - Missing in Swift (and irrelevant on macOS)
The wsl plugin is gated `os: ["windows"]` ([index.ts](https://github.com/anomalyco/opencode/blob/dev/packages/gui-plugins/src/wsl/index.ts)) and, on Windows, probes distros, installs WSL and a distro, installs the OpenCode CLI inside it, spawns a sidecar server ([main.ts](https://github.com/anomalyco/opencode/blob/dev/packages/gui-plugins/src/wsl/main.ts)), and lists distros as servers with start/retry rows and a "WSL unavailable" degraded state ([renderer.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/gui-plugins/src/wsl/renderer.tsx)); history from [PR 12914](https://github.com/anomalyco/opencode/pull/12914) through [PR 23407](https://github.com/anomalyco/opencode/pull/23407) and [PR 34233](https://github.com/anomalyco/opencode/pull/34233). TurboSpark Swift: Nothing equivalent exists in the Swift app sources and nothing should: the app is macOS-only, and the lone "wsl" grep hit is a false positive (`windowSlice`). **Verdict:** legitimately N/A; record it as an OpenCode-only platform feature rather than a gap.

### Review (per-file diff side panel) - Partial
OpenCode's review plugin registers a `changes` tab in the session side panel that lists every changed file with additions/deletions, renders unified or split diffs through the Pierre diff components (`@opencode/session-ui/pierre`), and supports three modes: git working tree, branch-wide, and per-turn ([renderer.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/gui-plugins/src/review/renderer.tsx), stores for diff style, expand mode and per-session mode/file/open list; earlier increments in [PR 51312](https://github.com/anomalyco/opencode/pull/51312), [PR 51640](https://github.com/anomalyco/opencode/pull/51640), [PR 55015](https://github.com/anomalyco/opencode/pull/55015)). Untracked folders expand on demand and selection is shared with the file tree via a demand counter per screen. TurboSpark Swift: The closest capability is the right-hand worktree inspector: [swift/TurboSparkApp/Sources/TurboSparkApp/Generation/WorktreeView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/WorktreeView.swift) (tabs for changes/commits, non-git card), [swift/TurboSparkApp/Sources/TurboSparkApp/Generation/WorktreeFileListView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/WorktreeFileListView.swift) (hierarchical tree or flat list with search), [swift/TurboSparkApp/Sources/TurboSparkApp/Generation/WorktreeDiffView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/WorktreeDiffView.swift) (unified diff parsing with folded context blocks), backed by [swift/TurboSparkApp/Sources/TurboSparkApp/State/WorktreeModel.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/WorktreeModel.swift). **Verdict:** parity on git working-tree review with a real diff viewer; missing the per-turn "what did this reply change" mode and the split diff style.

### Browser (embedded browser pane) - Different
OpenCode's browser plugin embeds a pane driven over Chrome DevTools Protocol attached to Electron `WebContents` ([cdp.ts](https://github.com/anomalyco/opencode/blob/dev/packages/gui-plugins/src/browser/cdp.ts), main side lazily loaded in [main.ts](https://github.com/anomalyco/opencode/blob/dev/packages/gui-plugins/src/browser/main.ts)), with an address bar, its own tab strip and shortcuts ([PR 57156](https://github.com/anomalyco/opencode/pull/57156), [PR 57935](https://github.com/anomalyco/opencode/pull/57935)), element picking and highlighting, network/CPU/heap profiling, Lighthouse analysis ([lighthouse.ts](https://github.com/anomalyco/opencode/blob/dev/packages/gui-plugins/src/browser/lighthouse.ts)), a navigation policy layer ([policy.ts](https://github.com/anomalyco/opencode/blob/dev/packages/gui-plugins/src/browser/policy.ts)), history, and comment/annotation chips; the separate published package [packages/plugin-browser](https://github.com/anomalyco/opencode/tree/dev/packages/plugin-browser) is the server-side agent browser (tools, skills, proxy, tunnel). TurboSpark Swift: The app genuinely has this through its own engine, so this is Different: [swift/TurboSparkApp/Sources/TurboSparkApp/Browser/BrowserPaneView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Browser/BrowserPaneView.swift) docks a tabbed WebKit pane (claimant `case .browser` in RootView), powered by [swift/TurboSparkApp/Sources/TurboSparkApp/BrowserAutomation/WebKitBrowserEngine.swift](swift/TurboSparkApp/Sources/TurboSparkApp/BrowserAutomation/WebKitBrowserEngine.swift), [swift/TurboSparkApp/Sources/TurboSparkApp/BrowserAutomation/BrowserControlPort.swift](swift/TurboSparkApp/Sources/TurboSparkApp/BrowserAutomation/BrowserControlPort.swift) (versioned navigate/click/type/screenshot command vocabulary), and [swift/TurboSparkApp/Sources/TurboSparkApp/Browser/ElementPickerController.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Browser/ElementPickerController.swift) for element picking; [swift/TurboSparkApp/Sources/TurboSparkApp/Browser/ChromeBookmarkImportPreviewView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Browser/ChromeBookmarkImportPreviewView.swift) imports Chrome bookmarks (the `Chrome/` directory itself is window chrome, not a Chrome extension bridge). **Verdict:** both apps ship an embedded, agent-controllable browser pane; OpenCode's adds devtools-grade profiling and Lighthouse, TurboSpark's WebKit path lacks those diagnostics but has a stricter permission-approval flow ([BrowserPermissionApprovalCoordinator.swift](swift/TurboSparkApp/Sources/TurboSparkApp/BrowserAutomation/BrowserPermissionApprovalCoordinator.swift)).

### File (workspace file tree, viewer tabs, open-in-app) - Partial
The file plugin owns the session's workspace file tree rendered with Pierre tree web components ([pierre-tree.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/gui-plugins/src/file/pierre-tree.tsx)), file/artifact tabs with a code and artifact viewer ([artifact-view.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/gui-plugins/src/file/artifact-view.tsx)), line-range links and reveal, drag-out, an "Open file" launcher tab, open-in-Finder/external app actions ([apps.ts](https://github.com/anomalyco/opencode/blob/dev/packages/gui-plugins/src/file/apps.ts)), and it publishes the `Files`, `FileViewer` and `Browser.openFile` contracts other plugins consume ([renderer.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/gui-plugins/src/file/renderer.tsx); polish in [PR 59657](https://github.com/anomalyco/opencode/pull/59657)). TurboSpark Swift: There is no persistent workspace file-tree pane. What exists is fragmented: [swift/TurboSparkApp/Sources/TurboSparkApp/Files/ProjectFileIndex.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Files/ProjectFileIndex.swift) is a bounded cached listing that only feeds the `@` autocomplete, [swift/TurboSparkApp/Sources/TurboSparkApp/Files/FilePreviewView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Files/FilePreviewView.swift) previews attachments in the right column, [swift/TurboSparkApp/Sources/TurboSparkApp/Generation/WorktreeFileListView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/WorktreeFileListView.swift) trees only changed files, and [swift/TurboSparkApp/Sources/TurboSparkApp/Generation/ArtifactPanelView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/ArtifactPanelView.swift) renders generated artifacts. **Verdict:** no user-browsable whole-project tree and no multi-tab file viewer; the pieces exist but are scattered across autocomplete, attachments and worktree views.

### Details (session/server details popover) - Different
OpenCode's details plugin puts a header slot in the session screen ([renderer.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/gui-plugins/src/details/renderer.tsx)) opening a popover whose [server-panel.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/gui-plugins/src/details/server-panel.tsx) shows the session's server, directory, plugins, LSP servers ([configured-lsp.ts](https://github.com/anomalyco/opencode/blob/dev/packages/gui-plugins/src/details/configured-lsp.ts)) and config file ([config-file.ts](https://github.com/anomalyco/opencode/blob/dev/packages/gui-plugins/src/details/config-file.ts)), plus a narrow-screen drawer and workspace/location menus. TurboSpark Swift: Different shape, similar purpose: the right-column inspector [swift/TurboSparkApp/Sources/TurboSparkApp/Diagnostics/InspectorView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Diagnostics/InspectorView.swift) exposes model, memory and power, steering, sampling, telemetry and runner diagnostics sections, [swift/TurboSparkApp/Sources/TurboSparkApp/Server/ServerInspectorView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Server/ServerInspectorView.swift) edits server settings, and [swift/TurboSparkApp/Sources/TurboSparkApp/Diagnostics/ContextSelectionPopover.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Diagnostics/ContextSelectionPopover.swift) is a popover over context. **Verdict:** the information is available but spread over an inspector column and section switches instead of one per-session details popover anchored to the session header.

### Goal (/goal pill and loop) - Aligned
OpenCode's goal plugin is a renderer-only composer pill ([renderer.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/gui-plugins/src/goal/renderer.tsx)) that subscribes to the server goal plugin's RPC (`Goal.Definition`), shows active/paused/met status with pause/resume/clear actions, added on top of [PR 59437 "add /goal with a client-side done check"](https://github.com/anomalyco/opencode/pull/59437) and the pill-popover API of [PR 59764](https://github.com/anomalyco/opencode/pull/59764) (branch `goal-desktop`). TurboSpark Swift: The Swift app has a full local implementation, not just an indicator: [swift/TurboSparkApp/Sources/TurboSparkApp/State/AppModel+Goal.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppModel+Goal.swift) owns `/goal` state, [swift/TurboSparkApp/Sources/TurboSparkApp/State/AppModel+GoalLoop.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppModel+GoalLoop.swift) implements the stop-seam evaluation, deferral and check-in arms, [swift/TurboSparkApp/Sources/TurboSparkApp/Generation/GoalEvaluator.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/GoalEvaluator.swift) is the model-judged verdict, and [swift/TurboSparkApp/Sources/TurboSparkApp/Generation/GoalBannerView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/GoalBannerView.swift) is the always-visible banner doubling as the stop button. **Verdict:** capability parity, with TurboSpark running the goal loop in-process where OpenCode delegates it to a server plugin; OpenCode's pill-in-composer placement is the only UI nuance TurboSpark lacks.

### Context (context usage tab) - Partial
OpenCode's context plugin contributes a `first`/`fallback` side tab with a usage indicator in its trigger, a per-session header slot indicator, and a full tab body with the context breakdown, format/catalog tables and export ([renderer.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/gui-plugins/src/context/renderer.tsx), [export.ts](https://github.com/anomalyco/opencode/blob/dev/packages/gui-plugins/src/context/export.ts)). TurboSpark Swift: The always-visible part is well covered: [swift/TurboSparkApp/Sources/TurboSparkApp/Generation/ContextUsageRingView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/ContextUsageRingView.swift) is the composer ring with a click-open breakdown popover over [swift/TurboSparkApp/Sources/TurboSparkApp/State/AppContextUsage.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppContextUsage.swift), plus [swift/TurboSparkApp/Sources/TurboSparkApp/Installation/ContextLadderView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Installation/ContextLadderView.swift) for ladder diagnostics. **Verdict:** meter and popover parity, but no dedicated full-size context pane with exportable breakdown; the data pipeline already exists, only the pane and export are missing.

### Sources (per-turn web sources panel) - Missing in Swift
OpenCode's sources plugin is the side panel of the web-sources experiment ([PR 58307 "show the web sources a reply used"](https://github.com/anomalyco/opencode/pull/58307)): a transient tab per turn opened from the timeline's sources chip via a `LinkHandler`, listing the citations that reply used with counts in the tab label ([renderer.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/gui-plugins/src/sources/renderer.tsx)). TurboSpark Swift: Nothing equivalent exists in the Swift app sources as a pane; web search exists as an agent tool ([swift/TurboSparkApp/Sources/TurboSparkApp/Tools/Web/WebSearchExecutor.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Tools/Web/WebSearchExecutor.swift), [swift/TurboSparkApp/Sources/TurboSparkApp/Tools/Web/WebTools.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Tools/Web/WebTools.swift)) whose results surface only through the tool-call presentation in [swift/TurboSparkApp/Sources/TurboSparkApp/Generation/ToolPresentation.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/ToolPresentation.swift). **Verdict:** per-turn citation collection and a dedicated sources view are absent; linking search results to the reply that used them would need new message metadata, not just a view.

### Pairing (QR pairing with mobile/remote) - Missing in Swift
OpenCode's pairing plugin ([renderer.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/gui-plugins/src/pairing/renderer.tsx), built on [PR 55306 "pair devices through remote access"](https://github.com/anomalyco/opencode/pull/55306) and the QR encoder of [PR 59056](https://github.com/anomalyco/opencode/pull/59056)) renders a settings page with a QR SVG of the server's pairing code ([page.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/gui-plugins/src/pairing/page.tsx)), a remote-access toggle that runs `opencode service set remote` and restarts the service in main ([main.ts](https://github.com/anomalyco/opencode/blob/dev/packages/gui-plugins/src/pairing/main.ts)), and a keep-screen-awake `powerSaveBlocker` option. TurboSpark Swift: Nothing equivalent exists in the Swift app sources: no QR generation, no pairing protocol, no LAN/remote companion story (grep for QR/pairing/remote access returns only tool-gating files). The app is single-device by construction. **Verdict:** phone/remote companion control is a whole feature axis absent from TurboSpark, including the server-side pairing endpoint it depends on.

### Microsoft Office (in-app document viewers) - Different
OpenCode's office plugin registers `FileViewer` implementations for document, spreadsheet and presentation kinds ([renderer.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/gui-plugins/src/microsoft-office/renderer.tsx), preview support from [PR 53305](https://github.com/anomalyco/opencode/pull/53305)), validating magic bytes (zip PK vs Compound File) before downloading multi-megabyte wasm engines per format, then paginating real Word/Excel/PowerPoint layout in workers (`@betteroffice/docx` layout kernel in [document.worker.ts](https://github.com/anomalyco/opencode/blob/dev/packages/gui-plugins/src/microsoft-office/document.worker.ts), sheet painting, slide text), with CJK font bundles and link scheme whitelisting ([links.ts](https://github.com/anomalyco/opencode/blob/dev/packages/gui-plugins/src/microsoft-office/links.ts)). TurboSpark Swift: Different approach, lower fidelity: attachments of Office formats are text-extracted, not rendered: [swift/TurboSparkApp/Sources/TurboSparkApp/Presentation/OfficeArchive.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Presentation/OfficeArchive.swift) (resource-bounded unzip with decompression-bomb budgets), [swift/TurboSparkApp/Sources/TurboSparkApp/Presentation/OfficeXMLParsers.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Presentation/OfficeXMLParsers.swift), and [swift/TurboSparkApp/Sources/TurboSparkApp/Presentation/DocumentTextExtractor.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Presentation/DocumentTextExtractor.swift) feed normalized text into the prompt, with previews via [swift/TurboSparkApp/Sources/TurboSparkApp/Files/FilePreviewView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Files/FilePreviewView.swift). **Verdict:** TurboSpark reads Office documents for the model but cannot display a paginated spreadsheet or slide deck to the user; OpenCode's wasm rendering pipeline has no Swift counterpart.

### Debug (dev diagnostics bar) - Different
OpenCode's debug plugin offers a command-toggled bar ([renderer.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/gui-plugins/src/debug/renderer.tsx), remembered per [PR 57332](https://github.com/anomalyco/opencode/pull/57332)) with text-rendering controls ([PR 57326](https://github.com/anomalyco/opencode/pull/57326)), TUI turn metrics ([PR 57934](https://github.com/anomalyco/opencode/pull/57934)), motion tuning on dev/beta only, and a main-process `MemoryDiagnostics` Ipc ([main.ts](https://github.com/anomalyco/opencode/blob/dev/packages/gui-plugins/src/debug/main.ts)) that records heap samples from the app and the server ([server-heap.ts](https://github.com/anomalyco/opencode/blob/dev/packages/gui-plugins/src/debug/server-heap.ts)) into exportable snapshots. TurboSpark Swift: Different and always user-visible rather than dev-only: the inspector's telemetry, usage-dashboard and runner-diagnostics sections ([swift/TurboSparkApp/Sources/TurboSparkApp/Diagnostics/InspectorView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Diagnostics/InspectorView.swift), [RunnerDiagnosticsSection.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Diagnostics/RunnerDiagnosticsSection.swift), [UsageDashboardSection.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Diagnostics/UsageDashboardSection.swift)), plus [swift/TurboSparkApp/Sources/TurboSparkApp/Diagnostics/MetricFormat.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Diagnostics/MetricFormat.swift). **Verdict:** TurboSpark has richer always-on telemetry of its own runtime, but no heap-snapshot capture/comparison tooling and no dev-only overlay bar; OpenCode's server-heap sampling is the concrete missing piece.

### btw (one-shot side questions) - Different
OpenCode's btw plugin ([PR 49750 "add /btw side question panel"](https://github.com/anomalyco/opencode/pull/49750), refinements in [PR 53270](https://github.com/anomalyco/opencode/pull/53270) and [PR 55708](https://github.com/anomalyco/opencode/pull/55708)) adds a hidden `/btw <question>` slash command that opens one transient side-panel tab per question and answers it with a tool-less, no-action generate call whose instructions forbid tools ([model.ts](https://github.com/anomalyco/opencode/blob/dev/packages/gui-plugins/src/btw/model.ts)), persisting each Q/A in a per-session store until the tab closes. TurboSpark Swift: Same command, different delivery: [swift/TurboSparkApp/Sources/TurboSparkApp/State/BuiltInSlashCommand.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/BuiltInSlashCommand.swift) registers `/btw` and [swift/TurboSparkApp/Sources/TurboSparkApp/State/AppModel+SlashParity.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppModel+SlashParity.swift) (`runBtwCommand`) launches a background subagent that answers without disturbing the running turn, with the result delivered back into the originating chat (sibling `/fork` continues the conversation in background). **Verdict:** both answer side questions off-thread, but OpenCode keeps each answer in its own inspectable, closable side tab while TurboSpark collapses them into background task notifications.

### Updater - covered in section 1
OpenCode ships auto-update as a built-in plugin with a host-rendered crash-page recovery path; TurboSpark's Swift app has its own update/install flow under [swift/TurboSparkApp/Sources/TurboSparkApp/Installation/](swift/TurboSparkApp/Sources/TurboSparkApp/Installation/), detailed in the report's update section.

Summary of verdicts from the TurboSpark perspective: the plugin runtime, SSH, WSL, pairing, sources, and the terminal pane are Missing in Swift; review, file, and context are Partial against existing Swift views; browser, details, debug, office, and btw are Different (same capability, other mechanism or fidelity); goal is the one clear Aligned case. The single largest architectural difference is that OpenCode's panes are live, disable-able, reload-able plugin instances in a sandboxed SDK, while every TurboSpark pane is a hardcoded SwiftUI view selected by the claimant switch in [swift/TurboSparkApp/Sources/TurboSparkApp/App/RootView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/App/RootView.swift).

## 5. Workspaces, git integration, usage, and sharing

OpenCode structures everything around a server-side project: a project is a canonical git checkout (`project.worktree`) plus any linked git worktrees the server manages as "workspaces" or sandboxes. The server exposes `worktree.list/create/remove/refresh` ([worktree handler](https://github.com/anomalyco/opencode/blob/dev/packages/server/src/handlers/worktree.ts)) over a strategy registry whose only strategy is git ([strategies.ts](https://github.com/anomalyco/opencode/blob/dev/packages/core/src/worktree/strategies.ts)), and every session carries a location directory, so sessions, permissions, and usage are all scoped per project/worktree. The desktop app layers a workspace picker, per-project worktree inventories ([inventory.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/workspaces/inventory.ts)), a settings projects page ([projects.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/settings/workspaces/projects.tsx)), and a cloud-tied Usage dialog for OpenCode Go and Console budgets ([usage dialog](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/usage/dialog.tsx)). Session sharing to opencode.ai was retired outright (PR 55716, PR 55718), and the app instead connects to remote opencode servers by URL or QR pairing ([connect dialog](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/servers/connect/dialog.tsx)). TurboSpark is a local-engine app: projects are local folder bindings, git is read through hardened `git`/`gh` processes, and usage is a local token ledger with no cloud component.

### Multi-project management - Aligned
OpenCode discovers projects from opened directories, and its settings page lets you add several at once via a native picker (`multiple: true` in [projects.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/settings/workspaces/projects.tsx)), groups added projects (PR [60221](https://github.com/anomalyco/opencode/pull/60221)), generates default project avatars (PR [57871](https://github.com/anomalyco/opencode/pull/57871)), and overrides permissions per project such as per-project auto-accept (PR [54839](https://github.com/anomalyco/opencode/pull/54839)). TurboSpark: [AppProject.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppProject.swift) defines a project as `rootDirectoryPath` plus agent profile, rule preference, custom instructions, a granular `AppProjectPermissions` matrix, and `maxAutonomousSteps`; chats bind to projects via `AppChat.projectID` and the sidebar groups them ([AppModel+Projects.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppModel+Projects.swift)). **Verdict:** both have multi-project scoping with per-project permissions; OpenCode adds a searchable settings page and avatar generation, TurboSpark keeps project management in the sidebar and adds fields OpenCode does not have (agent profile, autonomous step cap).

### Worktree workspaces (server inventory, picker, safe deletion) - Different
OpenCode treats each worktree as a first-class session destination: the app caches per-project worktree inventories invalidated by `worktree.updated` events ([inventory.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/workspaces/inventory.ts)), a new session can target "main" or "create" with a default-destination setting of local/new/last-used ([paths.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/workspaces/paths.ts)), the picker opens from the new-session branch control (PR [60263](https://github.com/anomalyco/opencode/pull/60263)) with separate project and worktree triggers (PR [60486](https://github.com/anomalyco/opencode/pull/60486)), and the settings workspaces page inspects deletions for active sessions, linked sessions, and dirty state before removing ([workspaces.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/settings/workspaces/workspaces.tsx)). TurboSpark: worktrees exist only as an agent tool ([WorktreeExecutor.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Tools/Projects/WorktreeExecutor.swift) creates under `.turbospark/worktrees/<branch>`) and a read-only pane listing (`worktree list --porcelain` parsing in [WorktreeModel+Tree.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/WorktreeModel+Tree.swift), cards in [WorktreeWorktreeListView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/WorktreeWorktreeListView.swift)); selecting a worktree explicitly "shows this worktree in the Git pane only" and does not move the agent. **Verdict:** TurboSpark has no workspace concept, no worktree picker for new sessions, no per-workspace settings, and no deletion safety dialog; its worktrees are never session destinations.

### Agent-callable worktree tools - Partial
OpenCode ships `worktree_create`, `worktree_list`, and `worktree_remove` as built-in Code Mode tools in the `opencode` plugin, with removal gated behind the `edit` permission and the tool output suggesting `session_move` to make the new worktree the session's working directory ([opencode.ts](https://github.com/anomalyco/opencode/blob/dev/packages/core/src/tool/plugin/opencode.ts)); the move-to-worktree flow was formalized in PR [53981](https://github.com/anomalyco/opencode/pull/53981) and `opencode run --worktree` (PR [60703](https://github.com/anomalyco/opencode/pull/60703)) extends it to the CLI. TurboSpark: [ArtifactWorktreeTools.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Tools/Projects/ArtifactWorktreeTools.swift) defines `EnterWorktree`/`ExitWorktree` (registered in [AppToolRegistry+Vocabulary.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Tools/Registry/AppToolRegistry+Vocabulary.swift)), but EnterWorktree deliberately never changes the tool root: its output states "The working root is UNCHANGED" after an incident where the model believed it was isolated, and ExitWorktree remove requires an explicit `path` plus `discard_changes` for `--force`, all through `HardenedGit`. **Verdict:** both expose agent worktree tools, but OpenCode's relocate the session while TurboSpark's sandbox the effect to a subdirectory path; TurboSpark lacks a `session_move` equivalent and branch-targeted creation (its `-b <name>` always branches from HEAD).

### Sessions bound to a directory, per-workspace session lists - Different
OpenCode sessions record `session.location.directory`, so the app can list sessions per workspace (`sessionsForWorkspace` filters by directory containment in [paths.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/workspaces/paths.ts)) and warn when a location's folder went missing ([location.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/workspaces/location.tsx)). TurboSpark: chats bind to an `AppProject` by UUID, not to a movable working directory; the tool root is derived from the project's `rootDirectoryPath` at invocation time (`workingDirectoryURL` in [AppModel+Tools.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppModel+Tools.swift)). **Verdict:** equivalent scoping at project granularity, but TurboSpark has no sub-project directory rebinding: a chat cannot follow the agent into a worktree, and there is no missing-folder detection per chat.

### Git review pane (status, per-file diffs, timeline) - Aligned
OpenCode renders a session review panel with unified/split diff styles, collapsible non-diff lines, and a stats slot ([session-review-v2.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/session-ui/src/v2/components/session-review-v2.tsx)) fed by the VCS provider's status/diff and per-turn snapshot diffs. TurboSpark: [WorktreeView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/WorktreeView.swift) is a right-hand inspector with Changes/Timeline/Worktrees tabs, [WorktreeModel+Git.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/WorktreeModel+Git.swift) runs `git status --porcelain` and numstat parsing into `WorktreeFileChange` (M/A/D/R/untracked with per-file additions/deletions), and [WorktreeDiffView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/WorktreeDiffView.swift) renders a unified diff with hunk headers, line numbers, and folded context blocks keyed on a parse cache. **Verdict:** feature parity in the common path (status list plus per-file diff viewer); OpenCode adds split-diff mode and direct file-preview navigation from the review panel, TurboSpark's diff targets are manual selection and commit/branch comparison modes (`WorktreeComparisonMode`: uncommitted, against branch, single commit).

### Branch switching and worktree listing in the UI - Partial
OpenCode exposes branch data through the VCS `branches` interface ([vcs.ts](https://github.com/anomalyco/opencode/blob/dev/packages/core/src/vcs.ts)) and routes the user to worktrees rather than in-place checkouts; branch switching in-place is not a primary app surface. TurboSpark: [WorktreeView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/WorktreeView.swift) offers branch checkout via `WorktreeModel.switchBranch` with an explicit guard comment that a checkout "swaps file contents under the agent mid-edit, so mirror the workspace-root guard", plus recent-commit browsing ([WorktreeCommitListView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/WorktreeCommitListView.swift), `queryRecentCommits` limited to 25). **Verdict:** TurboSpark is actually more aggressive here (in-app branch checkout and commit timeline that OpenCode's app does not offer), but it has no worktree creation from the UI, only listing and pane retargeting.

### Snapshot-based revert and file restore - Different
OpenCode captures content-addressed git snapshot trees per turn ([snapshot.ts](https://github.com/anomalyco/opencode/blob/dev/packages/core/src/snapshot.ts)) with capture/files/diff/restore, and session revert stages and restores files across a turn range ([revert.ts](https://github.com/anomalyco/opencode/blob/dev/packages/core/src/session/revert.ts)), including a fix to preserve renamed files when undoing (PR [45383](https://github.com/anomalyco/opencode/pull/45383)); per-turn file diffs are queryable ([session/diff.ts](https://github.com/anomalyco/opencode/blob/dev/packages/core/src/session/diff.ts)). TurboSpark: [FileSnapshotStore.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Tools/File/FileSnapshotStore.swift) keeps a single-slot pre-edit backup per file for `undo_edit`, valid only while the file still matches the post-edit hash, capped and trimmed oldest-first. **Verdict:** OpenCode has whole-turn time travel with structured diffs and rename handling; TurboSpark can only undo the last edit to one file, with no turn-level checkpoint, no "what did this turn change" query, and no multi-file restore.

### Git plumbing and VCS adapter layer - Different
OpenCode's core wraps git in a typed service ([git.ts](https://github.com/anomalyco/opencode/blob/dev/packages/core/src/git.ts)): repo discover/clone/create, remotes, HEAD/branch/default-remote-branch/rootCommits, fetch remotes and branches, worktree create/remove/list, write_tree, diff, restore, and pack, with tagged errors carrying `forceRequired`; VCS itself is a pluggable adapter interface (info/base/branches/status/diff) so non-git providers can hook in ([vcs.ts](https://github.com/anomalyco/opencode/blob/dev/packages/core/src/vcs.ts)). TurboSpark: all git access shells out through `HardenedGit.run` (repo config treated as attacker-influenceable, 15-second timeout) inside [WorktreeModel+Git.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/WorktreeModel+Git.swift) and [WorktreeExecutor.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Tools/Projects/WorktreeExecutor.swift), with no clone/fetch/pack layer and no VCS abstraction beyond git. **Verdict:** OpenCode can clone, fetch, and manage repositories programmatically (needed for worktree provisioning and cloud flows); TurboSpark assumes an existing local checkout and hardens the shell boundary instead, but has no path to non-git VCS providers.

### Commit and PR flows - Partial
OpenCode has no dedicated commit or PR UI; the agent commits and opens PRs through its shell tool, and the only PR-adjacent core code is a prompt that asks a summarizer to "write like a pull request description" ([plugin/agent.ts](https://github.com/anomalyco/opencode/blob/dev/packages/core/src/plugin/agent.ts)). TurboSpark: [AppModel+GitParity.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppModel+GitParity.swift) implements qwen-code parity local commands `/diff`, `/log`, and `/prs`, where `/prs` runs `gh pr list --json` and [ChatGitSheets.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/ChatGitSheets.swift) renders a three-tab sheet with parsed PR states (Open/Merged/Closed). **Verdict:** TurboSpark has read-only PR visibility OpenCode's app lacks, but neither side has agent-driven commit/PR-creation tooling beyond the shell; TurboSpark's agent is steered away from `git add`/`git commit` in Bash prompts rather than given a structured commit tool.

### Cloud usage and budget dialog - Missing in Swift
OpenCode's Usage dialog shows the signed-in workspace's OpenCode Go rolling/weekly/monthly allowance plus Console budgets with per-model, per-vendor, and money-denominated limits, reached states, reset countdowns, a switch-model suggestion when a budget is exhausted, and a deep link to `workspace.usageURL` ([dialog.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/usage/dialog.tsx), view model in [limits.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/usage/limits.ts)); core fetches these from the Console and classifies budget refusals (PR [58694](https://github.com/anomalyco/opencode/pull/58694)), and the usage-exceeded composer surfaces are covered elsewhere in this doc. TurboSpark: there is no account, workspace, quota, or credit concept anywhere in the app; the nearest surface is the local usage dashboard ([UsageDashboardSection.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Diagnostics/UsageDashboardSection.swift)). **Verdict:** absent by design since TurboSpark runs local checkpoints with no metered provider; nothing to port unless a cloud tier is ever added.

### Token and cost accounting per session/model - Partial
OpenCode stores tokens and a USD `cost` on each assistant message and aggregates them per session and per model through `SessionStats` ([stats.ts](https://github.com/anomalyco/opencode/blob/dev/packages/core/src/session/stats.ts)), exposed on the experimental `session.stats` endpoint ([session.ts](https://github.com/anomalyco/opencode/blob/dev/packages/protocol/src/groups/session.ts)), with money formatting utilities in [format.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/usage/format.ts). TurboSpark: [AppChatUsage.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppChatUsage.swift) keeps a per-chat `AppChatUsageLedger` with day-bucketed prompt/decode tokens and turn counts recorded from the engine's own `GenerationResult`, surfaced in `/stats` ([AppModel+LocalCommands.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppModel+LocalCommands.swift)), a 12-week heatmap, and a 30-day output chart; [AppChatStats.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppChatStats.swift) deliberately refuses to fabricate token totals. **Verdict:** token accounting is at parity or better on the Swift side (day heatmap, per-chat ledger); the gap is dollar cost, which OpenCode computes from provider pricing and TurboSpark does not attempt for local models.

### Session sharing, remote servers, and sync - Different
OpenCode retired public session sharing entirely: the backend was removed in PR [55716](https://github.com/anomalyco/opencode/pull/55716), the feature discontinued in PR [55718](https://github.com/anomalyco/opencode/pull/55718), remaining share endpoints and legacy storage deleted in PR [57328](https://github.com/anomalyco/opencode/pull/57328) and PR [57548](https://github.com/anomalyco/opencode/pull/57548) (only a vestigial `share_url` column survives in the session schema). Its cross-device story is instead connecting the desktop app to remote opencode servers by URL or QR-camera pairing over OpenTunnel ([connect dialog](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/servers/connect/dialog.tsx), PR [53837](https://github.com/anomalyco/opencode/pull/53837)), with per-server settings pages, health indicators, and unreachable-session-tab states (PR [56248](https://github.com/anomalyco/opencode/pull/56248)). TurboSpark: "Share" is a local export menu (Markdown, Word, HTML with optional tool details) in [ChatShareButton.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/ChatShareButton.swift) and [AppChatShareDocument.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppChatShareDocument.swift); there is no server registry, no URL/QR pairing, no CloudKit or iCloud sync anywhere in the app, and chats persist only in local JSON stores. **Verdict:** neither app publishes share links anymore, so that is aligned-by-absence; TurboSpark has no equivalent of OpenCode's remote-server sessions and multi-machine sync, so conversations are trapped on one Mac.

## 6. Design system, theming, i18n, motion, and accessibility

OpenCode ships a dedicated headless UI package ([packages/ui/src/](https://github.com/anomalyco/opencode/tree/dev/packages/ui/src)) containing a theme engine (35 preset JSON themes plus a V2 token system), a spring physics motion library, a typed 63-locale i18n layer, an inline SVG icon catalog, and roughly 60 primitive components (buttons, selects, dialogs, menus, spinners, text-reveal/typewriter effects) each with its own CSS file and storybook stories. Its i18n architecture is two-host: the Solid renderer resolves typed dictionary keys through a language API with `Intl.PluralRules` plural categories, while the Electron main process consumes typed native-translation bundles through `nativeT(...)` so native menus and dialogs never inspect locales themselves. The [packages/desktop/AGENTS.md](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/AGENTS.md) enforces a strict translation governance policy (Unicode CLDR, Microsoft/Apple/Mozilla style guides, no hardcoded English). TurboSpark's counterpart is a 32-file `Theme/` layer (token resolution, WCAG contrast math, motion vocabulary, appearance persistence) plus automated enforcement tooling (design-check script, token ratchet tests, locale parity gates) that OpenCode has no equivalent of, though OpenCode is far ahead on locale coverage, preset theme count, and motion tuning depth.

### Theme engine and preset gallery - Different
OpenCode resolves themes from 35 JSON files following a published schema ([packages/ui/src/theme/themes/](https://github.com/anomalyco/opencode/tree/dev/packages/ui/src/theme/themes), e.g. dracula, catppuccin, nord, gruvbox), each declaring light/dark palettes plus syntax-token overrides, converted to CSS variables by [theme/resolve.ts](https://github.com/anomalyco/opencode/blob/dev/packages/ui/src/theme/resolve.ts) with OKLCH color math in [theme/color.ts](https://github.com/anomalyco/opencode/blob/dev/packages/ui/src/theme/color.ts). A "V2" system ([theme/v2/resolve.ts](https://github.com/anomalyco/opencode/blob/dev/packages/ui/src/theme/v2/resolve.ts)) generates primitive scales (background/text/icon/border roles) from seed colors, with migration PRs [laying V1 themes onto V2 steps](https://github.com/anomalyco/opencode/pull/59996) and [registering a native V2 opencode theme](https://github.com/anomalyco/opencode/pull/49846); the renderer theme picker is wired in [settings/general/controllers.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/settings/general/controllers.ts). TurboSpark instead has one editable theme pair plus user-created saved themes: [Theme/ThemeLibrary.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Theme/ThemeLibrary.swift) validates `SavedTheme` records (accent/background/foreground hex per mode plus a contrast slider) stored in `appearance.json` by [Theme/AppearanceStore.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Theme/AppearanceStore.swift), rendered by [Components/ThemeGalleryView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Components/ThemeGalleryView.swift). **Verdict:** OpenCode offers 35 curated presets and a two-generation token pipeline with no user-authored themes; TurboSpark offers arbitrary user-authored themes with zero presets and no shareable theme file format.

### Light/dark/system color scheme - Aligned
OpenCode's [appearance.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/settings/appearance/appearance.tsx) exposes a `system | light | dark` select persisted via the ThemeProvider in [theme/context.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/ui/src/theme/context.tsx), which tracks `prefers-color-scheme`, sets `color-scheme` and the window meta theme-color, and supports live preview before commit; the main process reads the resolved color in [windows/defaults.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/windows/defaults.ts). TurboSpark's [Theme/AppAppearance.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Theme/AppAppearance.swift) defines the identical `system/light/dark` enum mapping to `.preferredColorScheme`, persisted through the archive. A documented defect class OpenCode does not address appears in [Theme/TurboSparkTheme.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Theme/TurboSparkTheme.swift): application-level `NSApp.effectiveAppearance` disagrees with SwiftUI's `.preferredColorScheme`, so all chrome accessors take explicit `isDark:`. **Verdict:** parity in user-facing behavior; TurboSpark additionally documents and works around the macOS-specific forced-scheme pitfall.

### Fonts and text scaling - Aligned
OpenCode's appearance page offers three font-role text inputs (UI, code, terminal) with live font-family preview, plus a desktop zoom select ([appearance.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/settings/appearance/appearance.tsx)); fonts are loaded from the package ([assets/fonts/](https://github.com/anomalyco/opencode/tree/dev/packages/ui/src/assets/fonts) ships Inter and JetBrains Mono) and [packages/desktop/AGENTS.md](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/AGENTS.md) forbids adding font files or literal families outside the design system roles. TurboSpark has [Theme/AppFontCatalog.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Theme/AppFontCatalog.swift) (offered UI/code families, bundled Hack, separate ui/code point sizes) and a four-step readability scale in [Theme/AppTextSize.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Theme/AppTextSize.swift) (0.875x to ~1.3x) that also multiplies Dynamic Type in theme resolution. **Verdict:** near parity; OpenCode has terminal font and window zoom, TurboSpark has a discrete text-size accessibility scale OpenCode lacks.

### Motion library and motion vocabulary - Different
OpenCode vendored a real spring-physics library as [packages/ui/src/motion/](https://github.com/anomalyco/opencode/tree/dev/packages/ui/src/motion) (closed-form damped-harmonic springs with SwiftUI's duration/bounce mapping, retargeting that keeps velocity, a shared frame loop, WAAPI adapter, velocity tracking, per-surface reduced-motion settling), introduced in [PR 56917](https://github.com/anomalyco/opencode/pull/56917) and refined on the [desktop-motion](https://github.com/anomalyco/opencode/tree/desktop-motion) and [timeline-motion](https://github.com/anomalyco/opencode/tree/timeline-motion) branches with later distance-scaled sidebar motion ([PR 58520](https://github.com/anomalyco/opencode/pull/58520)). TurboSpark's equivalent, [Theme/TurboSparkMotion.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Theme/TurboSparkMotion.swift), is a named-vocabulary enum (`TSMotion.hover/select/press/pane/sweep/breathe`) of native SwiftUI animations, chosen because the platform animates for free; it adds hover-lift and entrance modifiers that skip layout thrash in `LazyVStack`. **Verdict:** OpenCode built cross-platform spring infrastructure with retargetable velocity; TurboSpark relies on AppKit/SwiftUI animation primitives and standardizes naming rather than physics.

### Reduce motion - Aligned
OpenCode added a `system | on | off` Reduce motion appearance setting ([PR 57103](https://github.com/anomalyco/opencode/pull/57103)): the app resolves it onto a `data-motion="reduce|full"` root attribute, which [motion/reduced.ts](https://github.com/anomalyco/opencode/blob/dev/packages/ui/src/motion/reduced.ts) reads through a MutationObserver ahead of the `prefers-reduced-motion` media query, so active WAAPI jobs settle mid-animation. TurboSpark's `TSMotionContext` in [Theme/TurboSparkMotion.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Theme/TurboSparkMotion.swift) does the same two-source resolution (`AppearanceManager` preference first, `\.accessibilityReduceMotion` as system fallback), and the preference is persisted in the archive ([Theme/AppearanceStore.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Theme/AppearanceStore.swift)); about 19 files gate animated sites on it. **Verdict:** parity, including the same override-system-fallback semantics, reached independently.

### Motion tuning system - Missing in Swift
OpenCode has a developer-facing motion tuning subsystem: [motion-tuning.ts](https://github.com/anomalyco/opencode/blob/dev/packages/ui/src/motion-tuning.ts) registers typed knobs (spring/easing/mode/toggle/number/choice) per surface with shipped defaults, global speed (0.25-4x) and slow-motion multipliers, localStorage persistence with schema-versioned keys, replay actions, and design-experiment flags; [motion-tuning-features.ts](https://github.com/anomalyco/opencode/blob/dev/packages/ui/src/motion-tuning-features.ts) indexes them and both have dedicated test files ([motion-tuning.test.ts](https://github.com/anomalyco/opencode/blob/dev/packages/ui/src/motion-tuning.test.ts)). PRs [57692](https://github.com/anomalyco/opencode/pull/57692) and [58151](https://github.com/anomalyco/opencode/pull/58151) show the workflow: designers tune sidebar springs live, then ship the winning values as defaults. TurboSpark has nothing comparable; animation curves are compile-time constants in `TSMotion` and the only tuning loop is editing source. **Verdict:** an entire design-iteration tool category is absent from the Swift app; the closest analogue is shipping tuned constants by hand.

### Localization architecture and coverage - Different
OpenCode's renderer resolves ~1,206 typed English keys ([runtime/i18n/en.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/runtime/i18n/en.ts)) across 63 locale modules per host ([runtime/i18n/](https://github.com/anomalyco/opencode/tree/dev/packages/app/src/runtime/i18n)), with plural categories from `Intl.PluralRules`, `Intl.ListFormat` list joining, and locale-aware number formatting (see [context/i18n.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/ui/src/context/i18n.tsx)); coverage completion and locale additions landed as PRs [50204](https://github.com/anomalyco/opencode/pull/50204), [42475](https://github.com/anomalyco/opencode/pull/42475) (Hebrew), and [40985](https://github.com/anomalyco/opencode/pull/40985) (native locale names). TurboSpark's [Theme/AppLanguage.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Theme/AppLanguage.swift) offers 21 picker languages backed by a catalog with 4,384 keys across 29 locales in [swift/TurboSparkApp/Localization/Localizable.xcstrings](swift/TurboSparkApp/Localization/Localizable.xcstrings), with plurals expressed as xcstrings `variations`; the in-app picker re-resolves via `\.locale` without relaunch. **Verdict:** OpenCode covers roughly 3x the locales and centralizes plural/list grammar in code; TurboSpark delegates plural rules to the xcstrings toolchain but ships 8 catalog locales (ca, cs, da, el, fi, no, pt-PT, th) the picker does not expose.

### Native surface localization (menus, dialogs) - Different
OpenCode's main process gets typed translation bundles pushed from the renderer: [runtime/i18n/desktop-native.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/runtime/i18n/desktop-native.ts) defines `DESKTOP_NATIVE_KEYS` and 63 locale tags, and [native/translations.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/native/translations.ts) serves `nativeT(key)` with placeholder formatting, `nativePluralCategory`, and `Intl.DisplayNames`-sorted language menus; [native/menu.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/native/menu.ts) labels every Electron menu item through it, per the rule in [packages/desktop/AGENTS.md](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/AGENTS.md) that native code must never choose plural categories or assemble fragments. TurboSpark solves the same problem with [Theme/AppStrings.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Theme/AppStrings.swift): `String(localized:)` follows process languages rather than the in-app picker, so `AppStrings` manually resolves the compiled `.lproj` bundle (handling `pt-br` vs `pt-BR` casing) for toasts, `NSAlert`/`NSOpenPanel` titles, and stored status strings. **Verdict:** same requirement, inverted mechanism: OpenCode pushes data to a typed main-process API, TurboSpark reaches back into the bundle per call; OpenCode's compile-time key typing has no Swift equivalent outside code generation.

### Translation governance rules - Missing in Swift
The desktop [AGENTS.md](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/AGENTS.md) is a 31-line translation policy: never hardcode user-visible English, preserve English byte-for-byte as designer source, verify terminology against Unicode CLDR, Microsoft and Mozilla corpora and Firefox l10n with two independent corpora, consult official dictionaries (RAE, Duden, TDK, etc.), and record corpora used in review notes; enforcement shows in fixes like [PR 40977](https://github.com/anomalyco/opencode/pull/40977) (correcting Chinese "token" terminology). TurboSpark's equivalent guidance is one line in the root AGENTS.md (every UI string through `Text` or `AppStrings.localized`) plus the parity gates; there is no documented corpus or terminology policy for its 29 locales. **Verdict:** OpenCode treats translation quality as an engineering contract with named authorities; TurboSpark validates structure and completeness but not translation provenance.

### Component library - Different
OpenCode's [packages/ui/src/](https://github.com/anomalyco/opencode/tree/dev/packages/ui/src) is a portable kit of about 60 headless-ish primitives with co-located CSS and stories: 10 form controls (checkbox, radio, select, switch, text-input, textarea, typeahead, search-list), actions (button, icon-button, split-button), overlays (dialog, tooltip), navigation (menu, tabs, segmented-control), data-display (badge, avatar, keybind, diff-changes, line-comment), feedback (loader, toast, progress-circle, activity-ring), plus expressive components (text-reveal, typewriter, rolling-number, animated-number) and a storybook scaffold ([storybook/](https://github.com/anomalyco/opencode/tree/dev/packages/ui/src/storybook)). TurboSpark's 67-file [Components/](swift/TurboSparkApp/Sources/TurboSparkApp/Components/) is nearly all feature composites (settings panes, sheets, cards), with the actual primitive vocabulary living in [Theme/AppControls.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Theme/AppControls.swift) (thin wrappers that deliberately keep native `Button`/`Menu`/`TextField` keyboard, focus and VoiceOver semantics), [Theme/AppSurfaces.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Theme/AppSurfaces.swift), and [Theme/AppPillPicker.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Theme/AppPillPicker.swift). **Verdict:** OpenCode owns and renders every control for cross-platform consistency; TurboSpark wraps AppKit/SwiftUI natives to inherit accessibility for free, trading component inventory for platform correctness.

### Icons - Different
OpenCode builds icons from an inline SVG catalog ([icons/catalog.ts](https://github.com/anomalyco/opencode/blob/dev/packages/ui/src/icons/catalog.ts)) plus app/provider icon sets and a sprite, each artwork centered in its viewBox for currentColor theming. TurboSpark uses SF Symbols throughout (e.g. appearance icons in [Theme/AppAppearance.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Theme/AppAppearance.swift)) with a renderer for the dynamic Dock icon in [Theme/AppDockIconRenderer.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Theme/AppDockIconRenderer.swift). **Verdict:** no gap to close; system symbol integration is the idiomatic macOS choice, but it means no custom brand icon set like OpenCode's.

### Accessibility: labels, contrast, and platform settings - Partial (TurboSpark ahead on verification)
OpenCode spreads `aria-*` attributes and `focus-visible` styling through its primitives ([components/list.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/ui/src/components/list.tsx), [components/text-field.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/ui/src/components/text-field.tsx), forms/), labels Electron menus accessibly via i18n keys, and respects contrast only insofar as themes are designed well. TurboSpark has 163 files emitting `accessibilityLabel` (139 with elements/hints/values), and [Theme/ResolvedAppTheme.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Theme/ResolvedAppTheme.swift) folds `isHighContrast`, `reduceTransparency`, and `DynamicTypeSize` into resolved colors and opacities, with WCAG math in [Theme/AppContrast.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Theme/AppContrast.swift) tested by [AppStatusColorTests.swift](swift/TurboSparkApp/Tests/TurboSparkAppTests/AppStatusColorTests.swift) and theme accessibility pinned in [LocalizationAndAccessibilityTests.swift](swift/TurboSparkApp/Tests/TurboSparkAppTests/LocalizationAndAccessibilityTests.swift). **Verdict:** TurboSpark verifies accessibility (contrast ratios, high-contrast resolution, dynamic type scaling) with automated tests OpenCode lacks; OpenCode's keyboard/focus work in a DOM world has no listed TurboSpark counterpart beyond native control inheritance.

### Automated design enforcement - Missing in OpenCode (TurboSpark ahead)
TurboSpark gates its design system in CI three ways: [scripts/check-design.py](scripts/check-design.py) scans app sources against [swift/TurboSparkApp/Tests/TurboSparkAppTests/DesignRules.json](swift/TurboSparkApp/Tests/TurboSparkAppTests/DesignRules.json) ratchet baselines (system-color and literal-hex counts may only go down), [docs/design-system/](docs/design-system/README.md) derives `tokens.json`/`tokens.css` from Swift source via [docs/design-system/tools/derive_tokens.py](docs/design-system/tools/derive_tokens.py) with a checked table, and [LocalizationParityTests.swift](swift/TurboSparkApp/Tests/TurboSparkAppTests/LocalizationParityTests.swift) walks every picker language against the source catalog. OpenCode's ui package enforces conventions through per-package AGENTS.md prose, typed i18n keys (a key typo is a compile error), and component tests ([motion/core.test.ts](https://github.com/anomalyco/opencode/blob/dev/packages/ui/src/motion/core.test.ts), scroll-view, spin-phase), plus a lint-like cleanup PR [58235](https://github.com/anomalyco/opencode/pull/58235) deleting dead primitives, but has no cross-cutting token ratchet, contrast gate, or locale-parity job. **Verdict:** this is TurboSpark's clearest lead; OpenCode's type system catches missing keys, but nothing in it prevents a hardcoded color, a rogue font-family, or a locale silently dropping keys.

## 7. Voice, onboarding, service daemon, and diagnostics

OpenCode's desktop app ships an experimental voice-call mode where a hosted GPT-Live model talks to the user over WebRTC while a tool-calling "delegator" model drives desktop sessions ([PR 58249](https://github.com/anomalyco/opencode/pull/58249), branch [voice-console](https://github.com/anomalyco/opencode/tree/voice-console)). Its renderer has a dedicated first-run flow: a gated onboarding ([PR 34930](https://github.com/anomalyco/opencode/pull/34930)) and an animated wordmark splash ([PR 49408](https://github.com/anomalyco/opencode/pull/49408), branch [app/startup-splash](https://github.com/anomalyco/opencode/tree/app/startup-splash)). The Electron main process manages a versioned background opencode server service with staged CLI installs ([PR 57321](https://github.com/anomalyco/opencode/pull/57321), branch [authenticated-service-stop](https://github.com/anomalyco/opencode/tree/authenticated-service-stop)) and can zip desktop, server, and crashpad logs into one debug export. Two side packages round out the area: `packages/process-daemon` is a standalone Rust PTY service (opencode-pty), and `packages/http-recorder` is a cassette-based HTTP/WebSocket test recorder. TurboSpark has deep local audio (streaming STT, TTS, voice cloning) and a menu-bar-managed server daemon, but no voice-call UX, no onboarding or splash, no diagnostics bundle export, no crash reporting, and no HTTP recording.

### Voice call mode (talk to the agent by voice) - Missing in Swift
OpenCode adds a Call button, mute, live captions, End and manual Rejoin beside the composer, behind a Knobs experiment toggle and only on non-prod channels ([composer.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/voice/composer.tsx)). [transport.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/voice/transport.ts) checks the server offers `gpt-live-1` over WebRTC (endpoint from [PR 55951](https://github.com/anomalyco/opencode/pull/55951), [PR 57194](https://github.com/anomalyco/opencode/pull/57194)), negotiates SDP, opens mic capture with echo cancellation, and runs the call on the server's own OpenAI/Console key ([PR 58468](https://github.com/anomalyco/opencode/pull/58468)). A delegator model receives the viewed session, recent transcript tail, and tool definitions ([spec.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/voice/spec.ts)) and acts on desktop sessions via `send_message`, `open_session`, `search_sessions`, `wait_for_session`, and `switch_model` ([tools.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/voice/tools.ts)); turn-taking is throttled by [gates.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/voice/gates.ts) and the floating panel is draggable ([PR 58587](https://github.com/anomalyco/opencode/pull/58587)). TurboSpark Swift: mic capture ([AudioCapture.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Audio/AudioCapture.swift)), live streaming STT ([AudioLiveTranscriber.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Audio/AudioLiveTranscriber.swift)), and TTS jobs ([Qwen3TTSSpeechJob.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Audio/Qwen3TTSSpeechJob.swift)) all exist, but nothing sends a transcript to the chat agent or speaks its reply; there is no call state machine, mic-mute handshake, or caption surface in the chat UI. **Verdict:** the call UX is absent; the underlying capture, STT, and TTS primitives exist and are stronger than OpenCode's (local, offline), so wiring a call loop is integration work rather than new capability.

### Live transcription and captions - Different
OpenCode transcription is entirely server-side inside the hosted GPT-Live session; the renderer only receives transcript events over the WebRTC data channel ([protocol.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/voice/protocol.ts)) and keeps the last four utterances as captions ([context.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/voice/context.tsx)). TurboSpark Swift: live text is fully on-device - [AudioLiveTranscriber.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Audio/AudioLiveTranscriber.swift) drains capture through a mixer into an `AudioStreamSession` on the Neural Engine with a bounded backlog, and it feeds the meeting-notes/live workspace ([AudioWorkspaceLive.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Audio/AudioWorkspaceLive.swift)) rather than a chat call. Speaker intelligence ([AudioSpeakerLabels.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Audio/AudioSpeakerLabels.swift), [AudioSpeakerMemory.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Audio/AudioSpeakerMemory.swift)) has no OpenCode counterpart. **Verdict:** TurboSpark's live transcription is deeper but aimed at recordings, not a conversation; there is no caption path tied to an agent chat.

### TTS playback of agent replies - Different
OpenCode speech output is the hosted GPT-Live voice (`marin`) arriving as a WebRTC audio track pulled through a media element ([transport.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/voice/transport.ts)); there is no local TTS engine. TurboSpark Swift: real local TTS with voiceover, voice design, and consent-gated cloning (MegaTTS3 via Rust sessions, Qwen3-TTS cloning natively in the Swift MLX provider per [AudioWorkspaceSpeech.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Audio/AudioWorkspaceSpeech.swift)), played through the Audio workspace. **Verdict:** TurboSpark has the stronger TTS stack but it is not wired to chat replies; OpenCode's is hosted and only exists inside the call.

### First-run onboarding - Missing in Swift
OpenCode's [onboarding/index.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/renderer/onboarding/index.tsx) triggers only when the initial URL is `/`, the route is home, zero tabs exist, and only the builtin sidecar server is registered; it then prefetches provider/model state and opens a draft session tab before the splash dismisses, so the composer never flashes (flag itself is desktop-lifecycle owned, gated in [PR 34930](https://github.com/anomalyco/opencode/pull/34930)). A separate [migration-status.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/renderer/migration-status.tsx) surfaces server-side data-migration progress as localized toasts. TurboSpark Swift: there is no persisted first-launch flag, tour, or checklist; the first-run surface is the empty-state hero (mascot plus composer) in [WelcomeCharacterView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Components/WelcomeCharacterView.swift), and model acquisition onboarding is install gating in [ModelInstallGate.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Installation/ModelInstallGate.swift). **Verdict:** no equivalent of a sequenced first-run flow or migration-progress UI; only a static welcome hero.

### Animated splash and startup screens - Missing in Swift
OpenCode's [splash.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/renderer/startup/splash.tsx) shows a pulsing logo for returning users and, on first launch, an animated 1 px outline wordmark that waits for window focus and visibility, respects `prefers-reduced-motion`, and matches the titlebar inset per OS (36 px on macOS, `env(titlebar-area-height)` on Windows) ([PR 49408](https://github.com/anomalyco/opencode/pull/49408)). TurboSpark Swift: no splash file exists anywhere under the app sources; the main window appears directly with no branded loading state. **Verdict:** entirely absent; OpenCode also uses the splash as the onboarding hand-off boundary, which TurboSpark has no need for yet.

### Managed background server service - Partial
OpenCode's [background-service.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/service/background-service.ts) ensures an `opencode serve --service` process through `Service.ensure` with a registration file and version pinning, retries downgrades to the CLI's version ([cli-version.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/service/cli-version.ts)), adopts an already-running compatible service via [sidecar-probe.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/service/sidecar-probe.ts), and stages/cleans versioned CLI copies ([desktop-cli.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/service/desktop-cli.ts), [PR 57321](https://github.com/anomalyco/opencode/pull/57321)); the renderer gets a URL but never the basic-auth password - the main process injects Authorization ([initialization.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/renderer/startup/initialization.ts), [sidecar-credentials.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/service/sidecar-credentials.ts)). TurboSpark Swift: daemon lifecycle exists end to end - [Daemon.swift](swift/TurboSpark/Sources/TurboSpark/Daemon.swift) wraps `ts_daemon_status/start/stop/restart`, the menu bar section in [ServerMenuBarView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Server/ServerMenuBarView.swift) starts/stops/restarts, copies the endpoint, and opens the log, with arguments pinned in [ServerDaemonLaunch.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Server/ServerDaemonLaunch.swift) (port, guardrails, API key moved into the child's environment); the endpoint is surfaced via [AppModel+MenuBar.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppModel+MenuBar.swift). **Verdict:** TurboSpark manages a daemon but with no launchd/LaunchAgent registration, no versioned staged installs or old-stage cleanup, no adoption handshake for an externally started daemon, and no renderer-side credential shielding (the key is generated and shown to the user).

### process-daemon (opencode-pty PTY service) - Missing in Swift
OpenCode's [process-daemon](https://github.com/anomalyco/opencode/blob/dev/packages/process-daemon/README.md) is a standalone Rust service core: `portable-pty` children with authoritative terminal state from `libghostty-vt`, one token-authenticated owner connection over a Unix socket or Windows named pipe, and handoff tickets with 120-second expiry so a successor can adopt the daemon ([SPEC.md](https://github.com/anomalyco/opencode/blob/dev/packages/process-daemon/SPEC.md)). It backs persistent terminal features, not the opencode server itself. TurboSpark Swift: no PTY daemon; the nearest pieces are [AgentTerminalLaunch.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Server/AgentTerminalLaunch.swift), which opens a real terminal app for agent runs (working around launchd's minimal GUI PATH), and [ProcessExecutor.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Tools/Core/ProcessExecutor.swift) for tool child processes. **Verdict:** no persistent terminal-state service; TurboSpark deliberately spawns foreground processes instead.

### Diagnostics collection and export - Missing in Swift
OpenCode's `exportDebugLogs` in [logging.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/native/logging.ts) pauses net-log, collects per-launch desktop log run directories, per-server logs, and crashpad dumps into `~/Downloads/opencode-debug-<stamp>.zip` with a `manifest.json` listing truncated files, then restarts net-log and reveals the file in Finder; the Electron crash reporter starts early, the renderer stacks console traces ([diagnostics.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/renderer/diagnostics.ts)), and heap capture is opt-in via signal ([PR 58317](https://github.com/anomalyco/opencode/pull/58317), branch [cache-diagnostics](https://github.com/anomalyco/opencode/tree/cache-diagnostics)). TurboSpark Swift: [Diagnostics/](swift/TurboSparkApp/Sources/TurboSparkApp/Diagnostics/InspectorView.swift) is a live inspector UI (model essentials, memory/power, sampling, runner diagnostics, stream-recovery events), not a bundle; there is no debug zip, no net-log, and no crashpad integration. **Verdict:** TurboSpark shows diagnostics inline but has no one-click support bundle, which is the concrete gap.

### Telemetry and analytics - Different
OpenCode has no product analytics instrumentation in the desktop main or renderer (a search for telemetry/analytics finds nothing); its only outbound observability is Sentry when a `VITE_SENTRY_DSN` is configured, with prod builds stripping the global-handler integrations ([sentry.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/renderer/startup/sentry.ts)). TurboSpark Swift: none by design; "Session Telemetry & Introspection" in [InspectorTelemetrySection.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Diagnostics/InspectorTelemetrySection.swift) is local runtime metrics for the selected session, kept on device. **Verdict:** aligned on shipping no product telemetry; OpenCode additionally has opt-in DSN-gated crash reporting that TurboSpark lacks entirely.

### HTTP recording (cassettes) - Missing in Swift
OpenCode's [http-recorder](https://github.com/anomalyco/opencode/blob/dev/packages/http-recorder/README.md) is a published npm test utility (v2.2.5) that records real Effect HTTP and WebSocket traffic once into deterministic JSON cassettes, with secret redaction ([secrets.ts](https://github.com/anomalyco/opencode/blob/dev/packages/http-recorder/src/redaction/secrets.ts)) and offline replay with request matching ([matching.ts](https://github.com/anomalyco/opencode/blob/dev/packages/http-recorder/src/http/matching.ts)); it is developer test tooling, not an app feature. TurboSpark Swift: no HTTP record/replay machinery exists anywhere in the app or the TurboSpark framework; provider fixtures live on the Rust side instead. **Verdict:** nothing to compare on the Swift side; if deterministic provider tests are ever wanted in Swift, this is the reference design.

## 8. Backend architecture (server, protocol, SDK) vs the Rust FFI

OpenCode is a client/server system: a single `opencode` CLI binary hosts an Effect-based HTTP API server ([packages/server/src/api.ts](https://github.com/anomalyco/opencode/blob/dev/packages/server/src/api.ts)) whose routes are typed by a shared contract package ([packages/protocol/src/api.ts](https://github.com/anomalyco/opencode/blob/dev/packages/protocol/src/api.ts)) and consumed by generated/typed clients ([packages/sdk](https://github.com/anomalyco/opencode/blob/dev/packages/sdk/README.md), [packages/client/src/service.ts](https://github.com/anomalyco/opencode/blob/dev/packages/client/src/service.ts)). The desktop Electron app does not embed the agent: its main process ensures a versioned `opencode serve --service` sidecar is running, discovers it via a registration file plus basic auth ([packages/desktop/src/main/service/background-service.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/service/background-service.ts), [packages/desktop/src/main/service/desktop-cli.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/service/desktop-cli.ts)), and the renderer speaks an Effect RPC over Electron MessagePorts to main ([packages/desktop/src/main/ipc-transport.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/ipc-transport.ts), [packages/desktop/src/renderer/ipc-client.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/renderer/ipc-client.ts)). All agent state (sessions, messages, compaction, instructions) lives server-side in SQLite, so the desktop is a re-connectable view, not the source of truth. The same server also exposes the agent to other frontends: a TUI, an in-process SDK, and an ACP stdio adapter ([packages/cli/src/acp/service.ts](https://github.com/anomalyco/opencode/blob/dev/packages/cli/src/acp/service.ts)).

### Out-of-process versioned server sidecar - Different
OpenCode's desktop main process resolves a staged CLI binary, then `client.Service.ensure` spawns `opencode serve --service` as a detached sidecar, registers it in an XDG state file, and reconnects/replaces it on version mismatch; a compatible already-running server is adopted via a probe ([packages/desktop/src/main/service/background-service.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/service/background-service.ts), [packages/client/src/service.ts](https://github.com/anomalyco/opencode/blob/dev/packages/client/src/service.ts)), with stage cleanup and beta-server recovery in [cli-stages.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/service/cli-stages.ts) and PRs [57309](https://github.com/anomalyco/opencode/pull/57309), [57321](https://github.com/anomalyco/opencode/pull/57321), [52013](https://github.com/anomalyco/opencode/pull/52013). Because the server is a separate process, app updates can swap engines without dropping the running service. TurboSpark Swift: the chat agent runs in-process against the Rust engine over the C ABI - [TurboSparkSession.swift](swift/TurboSpark/Sources/TurboSpark/TurboSparkSession.swift) wraps a `ts_*` handle on a serial queue, and [TurboSparkServer.swift](swift/TurboSpark/Sources/TurboSpark/TurboSparkServer.swift) can attach sessions to an in-process HTTP server. The only out-of-process shape the app spawns is the user-initiated background daemon ([ServerDaemonLaunch.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Server/ServerDaemonLaunch.swift), [Daemon.swift](swift/TurboSpark/Sources/TurboSpark/Daemon.swift)), which serves OpenAI-compatible HTTP but is not the agent host. There is no version probe, registration file, or adopt-running-server flow. **Verdict:** OpenCode's desktop survives app restarts and engine upgrades through a versioned, adoptable sidecar; TurboSpark's agent lifetime is bound to the app process, and its daemon is a serving endpoint rather than a session host.

### Server-side session persistence in SQLite vs app-side JSON - Different
Sessions and messages are rows in a Drizzle/SQLite database inside the server ([packages/core/src/session/store.ts](https://github.com/anomalyco/opencode/blob/dev/packages/core/src/session/store.ts), [packages/core/src/database/database.ts](https://github.com/anomalyco/opencode/blob/dev/packages/core/src/database/database.ts)), with search, ordering, archiving, and parent/child session queries implemented server-side; any client (desktop, TUI, ACP editor, SDK) sees the same durable history and can reconnect to a live session. TurboSpark: chat history persists app-side through `AppJSONStore`-backed files with quarantine-on-corruption semantics ([AppChat.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppChat.swift), [AppModel+Persistence.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppModel+Persistence.swift)), and the engine holds KV-cache state only for the process lifetime. The OpenAI-compatible server in `crates/server` keeps no comparable session store that the app reads back. **Verdict:** OpenCode's source of truth is a multi-client server database; TurboSpark's is per-app JSON archives, so sessions cannot be shared with or resumed by another frontend.

### Event bus and SSE streaming - Partial
The server fans a typed event bus out over `GET /event` as `text/event-stream` with per-subscriber type filtering, a 15s heartbeat, and bounded subscriber queues ([packages/server/src/event-feed.ts](https://github.com/anomalyco/opencode/blob/dev/packages/server/src/event-feed.ts), [packages/server/src/handlers/event.ts](https://github.com/anomalyco/opencode/blob/dev/packages/server/src/handlers/event.ts)); the desktop renderer instead receives events over the MessagePort RPC bridge, and the protocol defines the full event vocabulary in [packages/protocol/src/groups/event.ts](https://github.com/anomalyco/opencode/blob/dev/packages/protocol/src/groups/event.ts). This is what lets the UI update from background work (subagents, compaction precompute) it did not itself start. TurboSpark Swift: streaming is direct Swift callbacks/AsyncSequence from the in-process FFI generate call ([QueuedGenerationStream.swift](swift/TurboSpark/Sources/TurboSpark/QueuedGenerationStream.swift)), and app state updates happen through `AppModel` extensions rather than a serialized event feed. The app's Server/ surfaces do show live server history and charts ([ServerLiveHistory.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Server/ServerLiveHistory.swift), [ServerMetricsStore.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Server/ServerMetricsStore.swift)) but via polling of the OpenAI-compatible endpoint, not a typed event protocol. **Verdict:** TurboSpark has no cross-process event protocol; everything works in-process but there is no way for a second client or a restarted window to resubscribe to agent progress.

### Typed protocol contract, versioned SDK, and in-process SDK host - Missing in Swift
The wire contract is one Effect `HttpApi` definition shared by server and clients ([packages/protocol/src/client.ts](https://github.com/anomalyco/opencode/blob/dev/packages/protocol/src/client.ts), groups from [session.ts](https://github.com/anomalyco/opencode/blob/dev/packages/protocol/src/groups/session.ts) to [mcp.ts](https://github.com/anomalyco/opencode/blob/dev/packages/protocol/src/groups/mcp.ts)), the promise-style SDK is generated against it ([packages/httpapi-codegen](https://github.com/anomalyco/opencode/blob/dev/packages/httpapi-codegen/src/index.ts), [packages/sdk/src/opencode.ts](https://github.com/anomalyco/opencode/blob/dev/packages/sdk/src/opencode.ts)), and the SDK can also host the whole server in memory with no network hop ([packages/sdk/README.md](https://github.com/anomalyco/opencode/blob/dev/packages/sdk/README.md)). Sidecar compatibility is enforced by exact version predicates at discovery time ([packages/client/src/service-version.ts](https://github.com/anomalyco/opencode/blob/dev/packages/client/src/service-version.ts)). TurboSpark Swift: the app's "contract" with the engine is the generated C header plus hand-written Decodable wrappers ([SessionTypes.swift](swift/TurboSpark/Sources/TurboSpark/SessionTypes.swift), [ChatTypes.swift](swift/TurboSpark/Sources/TurboSpark/ChatTypes.swift), [Capabilities.swift](swift/TurboSpark/Sources/TurboSpark/Capabilities.swift)); capability questions are answered by the engine at runtime (`ts_family_capabilities_json`) rather than by protocol versioning. There is no schema-shared IDL, no generated Swift client, and no version handshake with the daemon. **Verdict:** TurboSpark's FFI binding is compile-time-coupled and runtime-unguarded; OpenCode gets schema-checked evolution and mixed-version tolerance that a C ABI alone does not provide.

### LSP diagnostics feeding the agent - Missing in Swift
OpenCode documents built-in LSP integration for 30+ servers with diagnostics fed back to the agent ([packages/web/src/content/docs/lsp.mdx](https://github.com/anomalyco/opencode/blob/dev/packages/web/src/content/docs/lsp.mdx)); in the v2 dev tip the config schema ([packages/schema/src/config/lsp.ts](https://github.com/anomalyco/opencode/blob/dev/packages/schema/src/config/lsp.ts)), app settings UI ([packages/app/src/settings/workspaces/project-lsp.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/settings/workspaces/project-lsp.ts)), and core config normalization ([packages/core/src/config/normalize.ts](https://github.com/anomalyco/opencode/blob/dev/packages/core/src/config/normalize.ts)) exist, but the runtime is being rebuilt - [file-mutation.ts](https://github.com/anomalyco/opencode/blob/dev/packages/core/src/file-mutation.ts) reads `TODO: Notify LSP and collect diagnostics after LSP runtime exists`, with active work on branches `facade/lsp`, `kit/lsp-effect-refactor`, and `kit/ns-lsp`. TurboSpark Swift: there is no LSP client, no language-server process management, and no diagnostics channel into the agent loop; a repo-wide search finds only unrelated matches ([PluginModels.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/PluginModels.swift)). Post-edit verification is left to the agent's own shell/tool usage. **Verdict:** even on OpenCode's dev tip (where LSP is mid-port), the plumbing is far ahead of TurboSpark, which has nothing; this is the clearest agent-quality gap in the comparison.

### Rules and context files (AGENTS.md discovery and injection) - Partial
A core plugin discovers a global `~/.config/opencode/AGENTS.md`, walks every ancestor directory from the working file up to the project root for nested `AGENTS.md`, supports configured and remote instruction URLs, watches the files for changes, and republishes them through a hashed composable instruction system ([instruction.ts](https://github.com/anomalyco/opencode/blob/dev/packages/core/src/config/plugin/instruction.ts), [instruction-discovery.ts](https://github.com/anomalyco/opencode/blob/dev/packages/core/src/instruction-discovery.ts), [instructions/index.ts](https://github.com/anomalyco/opencode/blob/dev/packages/core/src/instructions/index.ts)); reading a file also injects its nested AGENTS.md at session time, and edge cases get dedicated fixes like [PR 52576](https://github.com/anomalyco/opencode/pull/52576), [PR 52364](https://github.com/anomalyco/opencode/pull/52364), [PR 53349](https://github.com/anomalyco/opencode/pull/53349). TurboSpark Swift: [ProjectRuleDetector.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/ProjectRuleDetector.swift) detects AGENTS.md vs CLAUDE.md in the project root with a user preference (agents-first, claude-first, merge-both) and symlink/conflict handling, and [AppModel+Tools.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppModel+Tools.swift) re-reads them live each turn into `resolvedProjectInstructions()`. There is no ancestor-directory walk, no global home-level rules file, no remote instruction URLs, and no file watcher (liveness comes from re-reading per turn). **Verdict:** TurboSpark covers the common single-root AGENTS.md/CLAUDE.md case with a nicer preference model, but lacks OpenCode's hierarchical discovery, global file, remote instructions, and change-notification pipeline.

### Formatters run over agent edits - Missing in Swift
The core formatter service resolves configured formatters per file extension, checks executable availability, and formats files after agent writes ([packages/core/src/formatter.ts](https://github.com/anomalyco/opencode/blob/dev/packages/core/src/formatter.ts)) with built-in support for prettier, oxfmt, biome, clang-format, ruff, air, ocamlformat, pint and more ([builtins.ts](https://github.com/anomalyco/opencode/blob/dev/packages/core/src/formatter/builtins.ts)); config merging across files has its own fix ([PR 52739](https://github.com/anomalyco/opencode/pull/52739)). TurboSpark Swift: no formatter pipeline exists - the only "formatter" hits are output display helpers ([ShellOutputFormatting.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Tools/Terminal/ShellOutputFormatting.swift)) and the terminal command classifier merely recognizes `prettier`/`rustfmt` as known commands ([TerminalCommandClassifier.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Tools/Terminal/TerminalCommandClassifier.swift)). Formatting happens only if the model chooses to run a tool. **Verdict:** OpenCode guarantees a formatting pass after edits; TurboSpark leaves style enforcement entirely to model discretion.

### Symbols / code intelligence tools - Missing in Swift
OpenCode's docs describe LSP-backed symbol tools (go-to-definition style lookups, diagnostics, and symbol-aware edits) as part of the same integration ([packages/web/src/content/docs/lsp.mdx](https://github.com/anomalyco/opencode/blob/dev/packages/web/src/content/docs/lsp.mdx)), and the v2 tree keeps a ripgrep service ([packages/core/src/ripgrep.ts](https://github.com/anomalyco/opencode/blob/dev/packages/core/src/ripgrep.ts)) for fast text-level code search while symbol-level work rides the LSP rebuild branches. TurboSpark Swift: `AppFileSymbol` maps file extensions to SF Symbol icons for UI chips, not code symbols ([AppFileSymbol.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppFileSymbol.swift)); there is no AST, ctags, or workspace-symbol tool exposed to the agent. Code navigation is grep/read only. **Verdict:** no symbol intelligence on either the Swift tool surface or the engine; OpenCode has at least the text-search substrate plus an LSP path to symbols.

### Compaction and summarization: server-side with background precompute vs app-side - Partial
OpenCode compacts sessions inside the server: configurable `auto`, a `buffer` (token count or percentage share, default 15 percent and at least 16k free), `keep` recent tokens verbatim beside the summary, and `precompute`/`background_compaction` that summarizes ahead of the threshold so the result can be swapped in ([packages/core/src/session/compaction.ts](https://github.com/anomalyco/opencode/blob/dev/packages/core/src/session/compaction.ts), PRs [57444](https://github.com/anomalyco/opencode/pull/57444), [58294](https://github.com/anomalyco/opencode/pull/58294), [60647](https://github.com/anomalyco/opencode/pull/60647), [58996](https://github.com/anomalyco/opencode/pull/58996)). Because it is server-side, a compacted session is consistent for every attached client. TurboSpark Swift: the app implements its own compaction ([AppChatCompaction.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppChatCompaction.swift): fires at four fifths of the usable window, model-written boundary summary in `contextSummary`, rows never deleted) plus a separate microcompact that projects stale tool output before fitting ([AppChatMicrocompact.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppChatMicrocompact.swift), [AppModel+Microcompact.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppModel+Microcompact.swift)). It has no background/precompute mode; summarization happens synchronously on the triggering turn. **Verdict:** feature parity on threshold compaction and keep-recent summaries; OpenCode adds background precompute and percentage buffers, TurboSpark adds microcompact of tool output, and the two live on opposite sides of the process boundary.

### Codemode: interpreter vs JavaScriptCore worker - Different (same idea, opposite isolation)
OpenCode's [packages/codemode](https://github.com/anomalyco/opencode/blob/dev/packages/codemode/README.md) is a from-scratch pure interpreter for a JavaScript-like language where programs reach the world only through host tools (no network, fs, timers, or imports), with REPL-style results and `UnsupportedSyntax` diagnostics; core wires it as an `execute` tool over a searchable catalog of MCP tools ([instructions.ts](https://github.com/anomalyco/opencode/blob/dev/packages/core/src/codemode/instructions.ts), [tool.ts](https://github.com/anomalyco/opencode/blob/dev/packages/core/src/codemode/tool.ts)), enabled per MCP server via a `codemode` config flag ([packages/schema/src/mcp.ts](https://github.com/anomalyco/opencode/blob/dev/packages/schema/src/mcp.ts)); active PRs include [60140](https://github.com/anomalyco/opencode/pull/60140), [57172](https://github.com/anomalyco/opencode/pull/57172), [59126](https://github.com/anomalyco/opencode/pull/59126). TurboSpark Swift: [Tools/Codemode/README.md](swift/TurboSparkApp/Sources/TurboSparkApp/Tools/Codemode/README.md) documents a port of pi's codemode onto a JavaScriptCore worker substrate - one `codemode` tool, one process per execution, memory watchdog, deadline kill, and script-issued MCP calls re-routed through hooks and approval ([CodemodeNestedRunner.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Tools/Codemode/CodemodeNestedRunner.swift)), gated by the `codemode.enabled` setting ([CodemodeToolDefinitions.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Tools/Codemode/CodemodeToolDefinitions.swift)). The separate [Tools/Repl/](swift/TurboSparkApp/Sources/TurboSparkApp/Tools/Repl/REPLWorkerProcess.swift) worker is the general JS REPL. **Verdict:** same product idea, opposite isolation strategies: OpenCode's hand-written interpreter cannot touch real JS semantics (safer, more limited), while TurboSpark runs real JavaScriptCore in a killed-per-run OS process (fuller language, heavier per call); both gate it behind an opt-in flag and batch MCP calls to save context turns.

### ACP (Agent Client Protocol) support - Missing in Swift
ACP is the open JSON-RPC-over-stdio protocol that lets editors like Zed embed an agent ([packages/web/src/content/docs/acp.mdx](https://github.com/anomalyco/opencode/blob/dev/packages/web/src/content/docs/acp.mdx)); OpenCode ships `opencode acp` as a full adapter with its own session registry, turn lifecycle, permission and elicitation bridging, and compaction reporting ([sessions.ts](https://github.com/anomalyco/opencode/blob/dev/packages/cli/src/acp/sessions.ts), [turn.ts](https://github.com/anomalyco/opencode/blob/dev/packages/cli/src/acp/turn.ts)), with heavy recent work on branches `acp-sessions`, `acp-command-lifecycle`, `acp-subagent-events`, and merged PRs [52488](https://github.com/anomalyco/opencode/pull/52488), [52503](https://github.com/anomalyco/opencode/pull/52503), [52511](https://github.com/anomalyco/opencode/pull/52511), [52485](https://github.com/anomalyco/opencode/pull/52485). Desktop relevance: the same server instance that the desktop uses can simultaneously serve an ACP editor, because the agent core is frontend-agnostic. TurboSpark Swift: no ACP adapter exists anywhere in the Swift tree or the FFI; the nearest outward-facing surfaces are the OpenAI-compatible HTTP server (`crates/server`, exposed in the app via [ServerConnectionView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Server/ServerConnectionView.swift)) and inbound reads of other agents' MCP configs ([ExternalAgentMcpReader.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Tools/MCP/ExternalAgentMcpReader.swift)). Neither lets an editor drive a TurboSpark agent session. **Verdict:** OpenCode can be embedded in third-party editors today; TurboSpark has no equivalent protocol surface beyond OpenAI-compatible completion serving, which carries no sessions, tools, or permissions.

### Rendering libraries for math and diagrams (latex, merman) - Different (presentation-layer only)
OpenCode maintains two rendering packages consumed by the TUI: [packages/latex](https://github.com/anomalyco/opencode/blob/dev/packages/latex/src/parser.ts) (LaTeX math parsing and layout) and [packages/merman](https://github.com/anomalyco/opencode/blob/dev/packages/merman/src/detect.ts) (mermaid-style flowchart, gantt, and gitgraph rendering with diagnostics), both declared in [packages/tui/package.json](https://github.com/anomalyco/opencode/blob/dev/packages/tui/package.json) so terminal users see rendered math and diagrams inline in agent output. TurboSpark Swift: the app has no LaTeX or mermaid rendering pipeline; matches for those words are slash-command/preset text only ([BuiltInSlashCommand.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/BuiltInSlashCommand.swift)), and rich content surfaces (artifacts, presentations) are separate app features rather than inline renderings of model output. **Verdict:** cosmetic rather than architectural, but OpenCode renders structured model output in its own frontend; TurboSpark would need an equivalent pass before model-authored math or diagrams display faithfully.

## 9. Swift-only capabilities

The comparison direction reverses here. TurboSpark is a local-model, multimodal macOS app: it installs weights, runs Metal/MLX/ANE inference, and captures real-world signals (microphone, screen audio, camera-free documents) on device. OpenCode desktop is a coding-agent frontend: nearly everything it has wraps a cloud provider session, so whole subsystems of TurboSpark have no counterpart at all.

### 9.1 Offline speech-to-text workspace (mic + system audio capture, streaming and batch STT, VAD) - Swift-only
TurboSpark's Audio/ directory (80+ files) is a full recording studio: [AudioCapture.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Audio/AudioCapture.swift) and [RecordingPermissions.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Audio/RecordingPermissions.swift) capture microphone and system-audio tracks (the latter via ScreenCaptureKit, gated behind the screen-recording grant), [AudioLiveTranscriber.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Audio/AudioLiveTranscriber.swift) drains the capture feed into a streaming STT model on a dedicated thread with a bounded backlog, and [SpeechToTextModels.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Audio/SpeechToTextModels.swift) lets each job (live, final, diarization) pick its own locally installed model, including Whisper-family and Parakeet profiles run by the Rust engine. A vendored [FluidAudio/](swift/TurboSparkApp/Sources/TurboSparkApp/Audio/FluidAudio/FluidAudioVAD.swift) engine adds on-device VAD, plus custom vocabulary ([AudioCustomVocabulary.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Audio/AudioCustomVocabulary.swift)) and offline model installs. ### 9.2 Local TTS, consent-gated voice cloning, and music generation - Swift-only
TurboSpark synthesizes speech on device: [Qwen3TTSSpeechJob.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Audio/Qwen3TTSSpeechJob.swift) runs the Qwen3-TTS MLX pipeline with producer draining and reference-asset expiry, and the Voice Cloning page ([VoiceCloneWorkspaceView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Audio/VoiceCloneWorkspaceView.swift), takes list, script composer, live progress) builds a cloned voice from one consented reference region (MegaTTS3, consent never carried over by reusing or recording a reference). ### 9.4 Local image generation (MLX diffusion pipelines) - Different

### 9.6 Embedded, evidence-backed memory ledger - Swift-only
TurboSpark has two memory layers: project MEMORY.md directories in Claude Code's memdir taxonomy ([MemoryStore.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/MemoryStore.swift)) and a claims ledger ([MemoryLedger.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/MemoryLedger.swift)) where every claim carries chat/message evidence with source hashes and a lifecycle (pending, active, superseded, retracted, dismissed). ### 9.7 Encrypted profile vault versus plaintext sqlite - Swift-only
TurboSpark's private state lives behind [ProfileUnlockView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/App/ProfileUnlockView.swift), a lock screen shown while the profile is sealed; the store is SQLCipher ([ProfileDatabase.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/ProfileDatabase.swift)), with chat attachments migrated into an encrypted asset store before protection strips plaintext ([AppModel+ProfileVault.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppModel+ProfileVault.swift)). Workflows/ is a 15-file interpreter stack for a user-scripted automation language: lexer, parser, semantic and type validation, and a manifest compiler ([WorkflowScriptSemanticValidation.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Workflows/WorkflowScriptSemanticValidation.swift), [WorkflowScriptChecker.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Workflows/WorkflowScriptChecker.swift)), executed by a run engine with explicit states (checking, awaitingApproval, declined, running, ...) ### 9.9 Model installation with hardware-fit probing and disk management - Swift-only
Installation/ (48 files) is a local model shop: [ModelHardwareFitCardView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Installation/ModelHardwareFitCardView.swift) renders probed memory-fit verdicts for the running machine (with an explicit "unknown means zeros, not measurements" rule), [ModelProbeSheet.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Installation/ModelProbeSheet.swift) probes arbitrary Hugging Face repos (GGUF plus sidecar repos) before install, [ModelLocationPicker.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Installation/ModelLocationPicker.swift) manages install disks, [DownloadETAEstimator.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Installation/DownloadETAEstimator.swift) estimates large downloads, and the manager deduplicates rows scanned out of an existing LM Studio library ([AppModel+Models.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppModel+Models.swift)). ### 9.10 Text-engine extras: OCR, embeddings, streaming STT, read-aloud, and persona - Swift-only
Three FFI surfaces in the shared TurboSpark package have no OpenCode equivalent: [Ocr.swift](swift/TurboSpark/Sources/TurboSpark/Ocr.swift) runs a vision OCR model that returns page-separated text with layout markup (document attachment extraction points scanned PDFs at it when selectable text is missing, [DocumentTextExtractor.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Presentation/DocumentTextExtractor.swift)); [Embedding.swift](swift/TurboSpark/Sources/TurboSpark/Embedding.swift) batch-encodes text with a local encoder for vector search; [Speech.swift](swift/TurboSpark/Sources/TurboSpark/Speech.swift) opens streaming PCM STT sessions over the C ABI. ### Window tab strip: session tabs, draft tabs, and closed-tab restore - Missing in Swift
Every OpenCode window runs a browser-style tab model over sessions. Tabs are persisted per window as a mix of session tabs and unsent draft tabs ([tabs/schema.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/shell/tabs/schema.ts)), the strip is drag-reorderable with unread/attention badges and rename/close ([titlebar/tab-strip.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/shell/titlebar/tab-strip.tsx)), a draft tab promotes into a session tab in place while carrying the composer text through the transition (`promoteDraft`/`prepareSession` in [tabs/tabs.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/shell/tabs/tabs.tsx)), per-tab composer and pane-open state is remembered via a per-tab memory and region store, and the last active URL is saved per window and validated on restore ([route-storage.ts](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/renderer/window/route-storage.ts)). User-closed session tabs go onto a closed-tab stack with a searchable Recently Closed menu and reopen ([tabs/closed.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/shell/tabs/closed.ts), [recently-closed-tabs-menu.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/shell/titlebar/recently-closed-tabs-menu.tsx), [PR 57863](https://github.com/anomalyco/opencode/pull/57863), [PR 57269](https://github.com/anomalyco/opencode/pull/57269)); option+arrow cycles tabs ([PR 54277](https://github.com/anomalyco/opencode/pull/54277)), and the strip renders horizontal (titlebar) or vertical (sidebar) per a layout preference, with per-server tab cleanup and active-tab follow-ups on branches `child-tab-close`, `external-session-tabs`, and `desktop-tab-notify`. TurboSpark Swift: one chat per window pane; `selectedChatID` restores the last active chat at launch ([AppModel+Persistence.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppModel+Persistence.swift)) and [SplitChatPanes.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/SplitChatPanes.swift) shows several chats at once, but those are split panes, not tabs: there is no persisted open-tab set, no draft tab, no closed-tab stack or reopen, and no per-tab pane-state memory. [ChatSidebarView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/ChatSidebarView.swift) is a session list, and previous/next chat shortcuts exist ([AlternateShortcutBridge.swift](swift/TurboSparkApp/Sources/TurboSparkApp/App/AlternateShortcutBridge.swift) Cmd+Shift+[ / Cmd+Shift+], `selectPreviousChat` in [AppModel+Chat.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppModel+Chat.swift)). **Verdict:** TurboSpark has the session list and cycling halves, but the whole keep-many-sessions-open-in-one-window model (persistence, drafts-in-tabs, closed-tab restore) is absent.

### Global command palette over commands, sessions, files, and settings - Missing in Swift
OpenCode's shell commands module is an app-wide command registry: every surface (sessions, panels, plugins, settings rows) registers a `CommandOption` with a keybind ([commands/command.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/shell/commands/command.tsx)), and one palette on mod+k / mod+shift+p searches across commands, workspace files, sessions, and settings rows with categories, featured commands, and live previews ([commands/palette.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/shell/commands/palette.ts), [commands/dialog.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/shell/commands/dialog.tsx)). Settings results jump straight to the row ([PR 57651](https://github.com/anomalyco/opencode/pull/57651)), the palette opens from anywhere including the home screen ([PR 57933](https://github.com/anomalyco/opencode/pull/57933)), search and command palettes were unified into one view ([PR 59604](https://github.com/anomalyco/opencode/pull/59604)), commands rank above sessions ([PR 60616](https://github.com/anomalyco/opencode/pull/60616)), and the same registry feeds keybind rebinding and menu enabled state ([PR 59499](https://github.com/anomalyco/opencode/pull/59499)). TurboSpark Swift: no command palette exists anywhere in the app sources (grep finds nothing); the settings sidebar search plus the control catalog ([SettingsControlCatalog.swift](swift/TurboSparkApp/Sources/TurboSparkApp/App/SettingsControlCatalog.swift)) reach only settings rows, [KeyboardShortcutCatalog.swift](swift/TurboSparkApp/Sources/TurboSparkApp/App/KeyboardShortcutCatalog.swift) is a read-only listing, and chat search ([ChatSearchOverlayView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/ChatSearchOverlayView.swift)) is transcript-scoped. **Verdict:** the passing note in section 3 undersells this: a single searchable entry point that runs commands and jumps to sessions and files is an entire interaction layer TurboSpark lacks; its menu shortcuts are undiscoverable except through the static shortcuts pane.

### Session unread and needs-attention state, with an inbox triage mode - Missing in Swift
OpenCode derives a per-session unread model from server-side viewed watermarks: the client reports `session.view` with exponential backoff when it sees a finished run ([notifications/notification.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/shell/notifications/notification.tsx), [PR 54780](https://github.com/anomalyco/opencode/pull/54780)), tabs and the sidebar show unread and attention dots fed by a shared signal ([PR 53570](https://github.com/anomalyco/opencode/pull/53570)), and desktop notifications with per-event sounds fire only when no window is focused, deduplicated across windows via Web Locks plus a persisted claimed-event ledger ([notifications/coordinator.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/shell/notifications/coordinator.ts), [sound.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/shell/notifications/sound.ts); the settings page for these is section 3's notification finding). An experimental Inbox mode replaces the tab sidebar with sessions grouped into needs-input/approval, working, finished, and archived sections with archive and delete flows ([titlebar/inbox-model.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/shell/titlebar/inbox-model.ts), [titlebar/inbox.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/shell/titlebar/inbox.tsx), [PR 57281](https://github.com/anomalyco/opencode/pull/57281), branches `app-inbox-beta-only`, `inbox-keys`, `inbox-reorder`). TurboSpark Swift: there is no unread or viewed model at all (the only "unread" source match is a comment about quarantined archives), no sound assets or playback anywhere in the app, UserNotifications only inside automation executors ([AutomationExecutors.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Tools/Automation/AutomationExecutors.swift)), and no dock badge or `requestUserAttention` on turn completion; [AppAttention.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Theme/AppAttention.swift) is an in-window attention edge for blocking cards, not a session-level state. **Verdict:** for an app whose agent runs locally and unattended, "tell me when a background chat needs me" is absent end to end; only in-pane visual nudges exist today.

### Back and forward navigation history - Missing in Swift
The OpenCode titlebar keeps a 100-entry history over home, session, and settings URLs with `common.goBack` / `common.goForward` commands on mod+[ / mod+], collapsing consecutive settings hops so palette jumps do not spam the stack ([titlebar/history.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/shell/titlebar/history.ts), wired as commands in [titlebar/titlebar.tsx](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/shell/titlebar/titlebar.tsx); keybinds from [PR 12880](https://github.com/anomalyco/opencode/pull/12880)). ### Sidebar hover peek - Missing in Swift
With the sidebar closed, resting the pointer on the window's leading edge or the sidebar toggle slides the real sidebar in over the content on a faster spring without reflowing the layout: dwell timers (40 ms edge, 500 ms toggle), pointer-corridor tracking with a grace period, drag/dialog/menu suppression, keyboard-focus handling, and a handoff that docks from the peek's mid-flight pose ([shell/sidebar-peek.ts](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/shell/sidebar-peek.ts), [PR 58156](https://github.com/anomalyco/opencode/pull/58156)). What TurboSpark should consider porting first, ordered by user value for a local-model macOS chat/agent app:

1. Global command palette over commands, sessions, files, and settings (9a, extends section 3) - one searchable entry point makes every existing menu command and pane discoverable.
2. Per-event desktop notifications and sounds with unfocused-only delivery (section 3) - the app's agents already run unattended; nothing tells the user when they finish or block.
3. Session unread and needs-attention state with inbox triage (9a) - pairs with the above to make background chat state glanceable and resumable.
4. Session tab strip with persisted tabs, draft tabs, and closed-tab restore (9a) - cheap multi-session workflows inside the single window TurboSpark already commits to.
5. LSP diagnostics fed back into the agent (section 8) - the clearest agent-quality gap; compile-lint feedback after edits beats model self-review.
6. First-run onboarding flow (section 7) - sequenced install-to-first-prompt guidance instead of the static welcome hero.
7. Back and forward navigation history (9a) - small, familiar, and missing entirely.
8. Voice call mode wired to the existing local STT/TTS stack (section 7) - TurboSpark owns capture, transcription, and speech; only the call loop and delegation tools are missing.
9. Formatter pass over agent edits (section 8) - a guaranteed style pass per write is small and high-leverage for coding use.
10. One-click diagnostics and support bundle export (section 7) - zipped logs with a manifest would replace manual reproduction for bug reports.
11. Persistent terminal pane with shared PTY state (section 4) - the largest build, but a real surface for a coding agent once worktrees and shells mature.
12. Deep link protocol handler (section 1) - unlocks OAuth round-trips and external automation entry points for a fully local app.
