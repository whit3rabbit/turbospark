# ZCODE_COMPARISON.md

ZCode desktop vs the TurboSpark Swift app: a feature-by-feature comparison.

- ZCode reference: https://github.com/zai-org/ZCode (Z.ai's coding agent harness and
  workspace: Electron desktop, web client, server, and the `zcode-cli` agent runtime),
  default branch `main`. Reviewed at `/tmp/zcode-ref` at commit `a60ba6a7`
  ("chore: sync ZCode source", v3.17.1, synced 2026-10-30). The desktop app lives in
  `packages/desktop` (main, host, preload, renderer, scheduler), shared app UI in
  `packages/ui`, the agent runtime in `apps/zcode-cli`, and the web/server/share stack
  in `packages/web`, `packages/server`, `packages/web-share`, `packages/share-ui`.
- Relationship to opencode: ZCode is not a GitHub fork, but parts of it carry opencode
  lineage: `THIRD-PARTY-NOTICES.md` includes "Copyright 2025 Anomaly" (opencode's
  vendor), `docs/model-provider-opencode-config.md` documents importing opencode
  provider configs, and a legacy-session restore plugin references the ACP era. The
  separate opencode-desktop comparison is [OPENCODE2_COMPARISON.md](OPENCODE2_COMPARISON.md).
- TurboSpark side: `swift/TurboSparkApp/Sources/TurboSparkApp/` (the macOS app) and
  `swift/TurboSpark/Sources/TurboSpark/` (the Swift wrapper over the Rust FFI); the
  model runtime is Rust under `crates/`.
- Status vocabulary:
  - **Aligned**: TurboSpark has a comparable feature with comparable behavior.
  - **Partial**: TurboSpark has some of it, with material gaps.
  - **Different**: both sides have the feature, but the design or scope differs.
  - **Missing in Swift**: ZCode has it, TurboSpark does not.
  - **Swift-only**: the reverse direction; consolidated in the last sections.
- Provenance: the public ZCode repo is a source-sync mirror with 7 commits and no
  public PR history, so per-feature provenance here links the design docs the ZCode
  team ships under `docs/` (roughly 400 spec and analysis files) instead of PRs. The
  one public feature branch, `feat/ui-plugin` (commit `662c30be`, "feat: add UI
  plugins and Gen UI", 426 files), is cited for the plugin UI/Gen UI features it
  landed before v3.15.x integrated them. Every ZCode finding also links the exact
  source files on GitHub `main`; every Swift finding links the repo-relative source
  files in this repository.

Method: nine investigation passes (three subagents per wave, three waves), each pass
reading the ZCode sources and design docs for its feature domains and the
corresponding Swift sources, then reporting findings that were folded into this
document, followed by a mechanical link-verification sweep over the assembled text.
Audited 2026-10-31.

## 1. Desktop shell, windowing, storage, lifecycle, updates, and background automation

### 1.1 Scheduled cron automations - Different
Both apps let users and the model create cron-driven prompt automations, but the engines differ in class. ZCode runs a dedicated utilityProcess scheduler that polls every 20s, transactionally claims due jobs from a SQLite tasks-index (BEGIN IMMEDIATE single-flight claims), keeps an automation_runs ledger, handles misfires (5 minute grace, skip-and-reschedule with one-shot finalization), retries with backoff, enforces a 20-job cap serialized in SQLite, and dispatches into workspace hosts with per-run model selection; a session-level CronCreate tool writes into the same store. Swift runs an in-process 20s Timer over a JSON-file store (`cron_jobs.json`), fires the prompt into the originating chat only (a deleted chat records a "missed"), offers CronCreate/CronList/CronDelete/ScheduleWakeup tools plus a "Scheduled Tasks" settings pane, and has no retry/backoff, no run ledger beyond a 10-entry history, no job cap, and no misfire semantics; it only fires while the app is running.
ZCode: [packages/desktop/src/scheduler/index.ts](https://github.com/zai-org/ZCode/blob/main/packages/desktop/src/scheduler/index.ts)
Swift: [swift/TurboSparkApp/Sources/TurboSparkApp/Tools/Automation/CronScheduler.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Tools/Automation/CronScheduler.swift), [swift/TurboSparkApp/Sources/TurboSparkApp/State/AppModel+LocalCommands.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppModel+LocalCommands.swift)
Provenance: [docs/automation-create-limit.md](https://github.com/zai-org/ZCode/blob/main/docs/automation-create-limit.md)

### 1.2 Off-peak (idle-time) background tasks - Missing in Swift
ZCode has a whole second automation domain: server-ticketed idle tasks (queued via POST /ticket, server-side FIFO admission, schedulable=true gating, 3102/3106 ticket expiry handling), stored in a dedicated off_peak SQLite table, dispatched by the same scheduler process with recovery of interrupted tasks on startup and a powerSaveBlocker keep-awake driven by active-count reports. Swift has nothing comparable: searches for "offpeak", "off-peak", IOPMAssertion, and beginActivity across TurboSparkApp sources all return nothing, and there is no server ticket concept at all.
ZCode: [packages/desktop/src/scheduler/index.ts](https://github.com/zai-org/ZCode/blob/main/packages/desktop/src/scheduler/index.ts), [packages/ui/src/store/offPeakTaskStore.ts](https://github.com/zai-org/ZCode/blob/main/packages/ui/src/store/offPeakTaskStore.ts)
Swift: absent (searched: offpeak/off-peak/IOPMAssertion/beginActivity greps over swift/TurboSparkApp/Sources)
Provenance: [docs/off-peak-task/spec.md](https://github.com/zai-org/ZCode/blob/main/docs/off-peak-task/spec.md)

### 1.3 Auto-update - Aligned
Both ship a real automatic updater with scheduled background checks, a manual "Check for Updates" entry, in-app download and install-and-relaunch, and dedicated smoke coverage. ZCode uses electron-updater with a manifest provider, 15 minute background / 2 minute visible poll intervals, release channels, release-notes payloads delivered post-update, Windows Authenticode verification, and feed overrides via env/switch plus a dev-app-update.yml placeholder. Swift uses Sparkle 2.9.6 with the GitHub Releases appcast and EdDSA trust, a settings toggle mirroring Sparkle's automatic-check preference, a "Check for Updates..." menu item deliberately kept outside the profile vault gate, and a silent AutoInstallUserDriver plus TURBOSPARK_UPDATE_FEED_URL override used by a two-version download-verify-install-relaunch smoke.
ZCode: [packages/desktop/src/main/autoUpdater.ts](https://github.com/zai-org/ZCode/blob/main/packages/desktop/src/main/autoUpdater.ts), [packages/desktop/dev-app-update.yml](https://github.com/zai-org/ZCode/blob/main/packages/desktop/dev-app-update.yml)
Swift: [swift/TurboSparkApp/Sources/TurboSparkApp/App/Updates/SparkleUpdateController.swift](swift/TurboSparkApp/Sources/TurboSparkApp/App/Updates/SparkleUpdateController.swift), [swift/TurboSparkApp/Package.swift](swift/TurboSparkApp/Package.swift)
Provenance: no dedicated spec doc; behavior taken from the two implementations

### 1.4 Mobile/web remote control relay - Missing in Swift
ZCode's desktop pairs with phone/web clients: the web-remote-relay module owns device WebSocket transport, HTTP push notification eligibility, non-sensitive device storage, and renderer action requests, so a paired device can drive desktop sessions and receive push updates. Swift has no pairing or remote-control surface; the closest analog is its loopback HTTP API server (127.0.0.1, optional API key, guardrails reported at start) which serves OpenAI-style inference clients, and nothing that lets another device control the app.
ZCode: [packages/desktop/src/main/web-remote-relay/CONTRACT.md](https://github.com/zai-org/ZCode/blob/main/packages/desktop/src/main/web-remote-relay/CONTRACT.md)
Swift: [swift/TurboSparkApp/Sources/TurboSparkApp/State/AppModel+Server.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppModel+Server.swift) (local API server only; no remote control)
Provenance: relay-v2-pairing.md referenced from the CONTRACT.md above

### 1.5 Single-instance lock and deep links - Missing in Swift
ZCode takes app.requestSingleInstanceLock with serialized deep-link data, and a second launch forwards zcode:// URLs (hosts: oauth/callback, payment, workspace, share) and --open-workspace paths to the running instance, which focuses/restores the window, gates external workspace opens behind a confirmation dialog, and rejects both while a force-update gate is active; Linux registers the scheme separately. Swift has no URL scheme at all: CFBundleURLTypes is absent from the app Info.plist set and no onOpenURL or custom scheme appears anywhere in TurboSparkApp sources; macOS LaunchServices enforces one instance per bundle and applicationShouldHandleReopen just re-fronts the window.
ZCode: [packages/desktop/src/main/desktopSecondInstanceDeepLink.ts](https://github.com/zai-org/ZCode/blob/main/packages/desktop/src/main/desktopSecondInstanceDeepLink.ts), [packages/desktop/src/main/desktopDeepLinkUrl.ts](https://github.com/zai-org/ZCode/blob/main/packages/desktop/src/main/desktopDeepLinkUrl.ts), [packages/desktop/src/main/index.ts](https://github.com/zai-org/ZCode/blob/main/packages/desktop/src/main/index.ts)
Swift: [swift/TurboSparkApp/Sources/TurboSparkApp/App/TurboSparkApp.swift](swift/TurboSparkApp/Sources/TurboSparkApp/App/TurboSparkApp.swift) (reopen handling; deep links absent, searched onOpenURL/CFBundleURLTypes/scheme greps)
Provenance: no dedicated spec doc

### 1.6 Workspace tabs inside one window - Missing in Swift
ZCode's single desktop window hosts a per-window tab system: workspace tabs with persisted availability, pane session restore, remote session identity rekeying, and a reserved settings tab id, all persisted through the setting service. Swift is deliberately single-window: one main Window scene backed by a chat/project sidebar, plus a separate Settings scene and a MenuBarExtra window; no tab strip, tab store, or tab persistence exists.
ZCode: [packages/ui/src/store/tabStore.ts](https://github.com/zai-org/ZCode/blob/main/packages/ui/src/store/tabStore.ts)
Swift: [swift/TurboSparkApp/Sources/TurboSparkApp/App/TurboSparkApp.swift](swift/TurboSparkApp/Sources/TurboSparkApp/App/TurboSparkApp.swift)
Provenance: no dedicated spec doc

### 1.7 System tray - Different
ZCode builds an Electron Tray only on Windows and Linux (context menu: open, new task, open workspace, check for updates on production, about, export logs, quit), composites a 1x/2x unread-count badge into the tray bitmap, and documents close-to-tray as Windows default-on with a one-time settings migration; on macOS it has no tray and relies on the Dock badge (app.setBadgeCount) instead. Swift has no NSStatusItem-based tray icon, but its MenuBarExtra scene is the macOS equivalent presence: a bolt/bolt.fill status item whose window dashboard shows live server state, gated behind a showMenuBarItem setting, with the icon reflecting whether the server is running.
ZCode: [packages/desktop/src/main/desktopTray.ts](https://github.com/zai-org/ZCode/blob/main/packages/desktop/src/main/desktopTray.ts)
Swift: [swift/TurboSparkApp/Sources/TurboSparkApp/App/TurboSparkApp.swift](swift/TurboSparkApp/Sources/TurboSparkApp/App/TurboSparkApp.swift)
Provenance: [docs/windows-tray.md](https://github.com/zai-org/ZCode/blob/main/docs/windows-tray.md)

### 1.8 Close-button background behavior - Different
ZCode on macOS converts a close click into hide() (exiting full screen first to avoid a black Space), and on Windows hides to tray by default; quitting is centralized in before-quit with host cleanup. Swift makes the decision a policy: applicationShouldTerminateAfterLastWindowClosed returns false when keepServerRunningInBackground or showMenuBarItem is set (both default true), so the app stays resident in the menu bar after the last window closes, otherwise it quits; quit runs the AppShutdownCoordinator.
ZCode: [packages/desktop/src/main/desktopDarwinCloseBehavior.ts](https://github.com/zai-org/ZCode/blob/main/packages/desktop/src/main/desktopDarwinCloseBehavior.ts)
Swift: [swift/TurboSparkApp/Sources/TurboSparkApp/App/TurboSparkApp.swift](swift/TurboSparkApp/Sources/TurboSparkApp/App/TurboSparkApp.swift), [swift/TurboSparkApp/Sources/TurboSparkApp/State/MacAppSettings.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/MacAppSettings.swift)
Provenance: [docs/windows-tray.md](https://github.com/zai-org/ZCode/blob/main/docs/windows-tray.md)

### 1.9 App state storage layout - Different
ZCode keeps a redirectable data root (default ~/.zcode, overridable via setting.json dataBaseDir / ZCODE_DATA_BASE_DIR and bootstrapped before logging starts) holding a SQLite tasks-index, per-workspace session databases prepared by utility processes, and a documented policy confining temp/persistent writes to named subdirectories under the root. Swift keeps everything under one machine root in ~/Library/Application Support/TurboSpark (TURBOSPARK_STATE_DIR override and per-pid temp redirection for tests), with per-profile SQLCipher-encrypted ProfileDatabase instances (chats, projects, workflows, audio index) plus versioned JSON archives written through AppJSONStore, which quarantines a corrupt or unreadable file beside the archive instead of overwriting it.
ZCode: [packages/desktop/src/main/desktopDataBaseDirBootstrap.ts](https://github.com/zai-org/ZCode/blob/main/packages/desktop/src/main/desktopDataBaseDirBootstrap.ts), [docs/tmpdir-storage-paths-spec.md](https://github.com/zai-org/ZCode/blob/main/docs/tmpdir-storage-paths-spec.md)
Swift: [swift/TurboSparkApp/Sources/TurboSparkApp/State/AppStorageRoot.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppStorageRoot.swift), [swift/TurboSparkApp/Sources/TurboSparkApp/State/ProfileDatabase.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/ProfileDatabase.swift)
Provenance: [docs/tmpdir-storage-paths-spec.md](https://github.com/zai-org/ZCode/blob/main/docs/tmpdir-storage-paths-spec.md)

### 1.10 Remote force-update kill switch - Missing in Swift
ZCode reads forceUpdate.minimalVersion from a remote client-configs endpoint at startup and, when the local semver is lower, blocks main window creation entirely, focuses a gate window instead, and rejects second-instance workspace and deep-link requests until upgrade; the check is documented to fail open when the remote config cannot be read. Swift's updater has no remote gate of any kind: SparkleUpdateController exposes only an automatic-checks toggle and a feed override, and nothing compares a minimum version or blocks the UI.
ZCode: [packages/desktop/src/main/desktopSecondInstanceDeepLink.ts](https://github.com/zai-org/ZCode/blob/main/packages/desktop/src/main/desktopSecondInstanceDeepLink.ts) (force-update interplay), [docs/force-update-client-config.md](https://github.com/zai-org/ZCode/blob/main/docs/force-update-client-config.md)
Swift: [swift/TurboSparkApp/Sources/TurboSparkApp/App/Updates/SparkleUpdateController.swift](swift/TurboSparkApp/Sources/TurboSparkApp/App/Updates/SparkleUpdateController.swift) (no kill switch present)
Provenance: [docs/force-update-client-config.md](https://github.com/zai-org/ZCode/blob/main/docs/force-update-client-config.md)

### 1.11 Quit and shutdown management - Different
ZCode formalizes shutdown as a policy object: per-platform force-kill delays and wait timeouts, a monotonically upgrading "update-install" shutdown kind, host process tree cleanup, and a logout flow that counts running sessions, confirms, then reuses the quit path to restart the app. Swift's AppShutdownCoordinator is an ordered flush inside the app process: stop the HTTP server and TypeSafe daemon, cancel generation while preserving an in-flight reply as an interrupted row for Continue/Retry, kill background shells and agent task trees, cancel memory/title/goal timers, restore the fan controller, stop the volume monitor, and purge the vault's decrypted attachment cache.
ZCode: [packages/desktop/src/main/appShutdownPolicy.ts](https://github.com/zai-org/ZCode/blob/main/packages/desktop/src/main/appShutdownPolicy.ts), [docs/desktop-logout-confirm-restart.md](https://github.com/zai-org/ZCode/blob/main/docs/desktop-logout-confirm-restart.md)
Swift: [swift/TurboSparkApp/Sources/TurboSparkApp/State/AppModel+Persistence.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppModel+Persistence.swift) (AppShutdownCoordinator), [swift/TurboSparkApp/Sources/TurboSparkApp/App/TurboSparkApp.swift](swift/TurboSparkApp/Sources/TurboSparkApp/App/TurboSparkApp.swift)
Provenance: [docs/desktop-logout-confirm-restart.md](https://github.com/zai-org/ZCode/blob/main/docs/desktop-logout-confirm-restart.md)

### 1.12 Storage/database startup gating and progress - Different
ZCode coordinates database startup as a first-class startup phase: a coordinator publishes preparing_host_storage / preparing_session_storage states (with migration names) to the renderer, samples disk latency against a 250 ms baseline budget, and prepares tasks-index and per-workspace session DBs before the window boots its host utility process. Swift has no storage-startup phase or telemetry; its startup gate is the profile vault unlock view (SQLCipher key entry) plus a one-time maximize-to-visible-frame adoption, with the database opened as part of model construction.
ZCode: [packages/desktop/src/host/database-startup/hostDatabaseStartup.ts](https://github.com/zai-org/ZCode/blob/main/packages/desktop/src/host/database-startup/hostDatabaseStartup.ts), [packages/desktop/src/main/desktopWindowLifecycle.ts](https://github.com/zai-org/ZCode/blob/main/packages/desktop/src/main/desktopWindowLifecycle.ts)
Swift: [swift/TurboSparkApp/Sources/TurboSparkApp/App/TurboSparkApp.swift](swift/TurboSparkApp/Sources/TurboSparkApp/App/TurboSparkApp.swift) (ProfileUnlockView gate)
Provenance: no dedicated spec doc

### 1.13 Window geometry persistence - Aligned
Both persist user window geometry across launches with a sensible first-launch default. ZCode attaches window size persistence to the main window lifecycle and keeps a generator script for macOS window bounds fixtures. Swift maximizes the window to the screen's visible frame exactly once (a UserDefaults-guarded one-time adoption), after which AppKit autosave restores the user's frame; the Settings window gets a first-open default size via an explicit autosave name, and a minimum size is enforced on the real NSWindow, clamped to the screen so contentMinSize cannot push it off screen.

### 1.14 Window chrome and caption controls - Different
On macOS both use native system chrome: ZCode's frame component explicitly treats macOS as the vibrancy case and only Windows/Linux get the opaque root and custom treatment. ZCode additionally ships its own shell chrome on Windows/Linux: frameless windows with custom caption buttons, a caption help menu button, per-platform rounded-corner/clip-path handling, and documented drag-region coordination for the Automations view; Swift, being macOS-only, has no custom-drawn caption or drag-region code at all.

## 2. Tasks, composer, and conversation UI

ZCode calls chat sessions "tasks"; the findings below use each side's own name.

### 2.1 Concurrent background tasks vs one active chat - Different
ZCode's core model is many live tasks: the sidebar lists tasks per workspace, tasks keep running in the background while the user browses others, background terminal completion raises unread signals, and a CLI-side idle/LRU pool loads and unloads session runtimes under the user. TurboSpark is strictly single-active: `selectChat`, `createChat`, `deleteChat` and even prev/next navigation all `guard !generating, !submitting, pendingToolCall == nil`, and sidebar rows are explicitly disabled with "Cannot switch chats while generation is running"; work for other chats is parked in per-chat queues (`pendingUserMessages`) and drains only when that chat is selected and idle.
ZCode: [packages/ui/src/TaskList.tsx](https://github.com/zai-org/ZCode/blob/main/packages/ui/src/TaskList.tsx), [docs/session-idle-deactivation.md](https://github.com/zai-org/ZCode/blob/main/docs/session-idle-deactivation.md), [docs/task-list-refresh-semantics.md](https://github.com/zai-org/ZCode/blob/main/docs/task-list-refresh-semantics.md)
Swift: [swift/TurboSparkApp/Sources/TurboSparkApp/State/AppModel+Chat.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/AppModel+Chat.swift) (guards at `selectChat`/`createChat`/`selectPreviousChat`), [swift/TurboSparkApp/Sources/TurboSparkApp/Generation/ChatSidebarChatRowView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/ChatSidebarChatRowView.swift)
Provenance: [docs/session-idle-deactivation.md](https://github.com/zai-org/ZCode/blob/main/docs/session-idle-deactivation.md)

### 2.2 Session list organization (groups, pin, archive) - Partial
Both pin sessions and group the rest, and both keep an archive surface. ZCode groups by workspace with Project/Timeline/Pinned/Archived/Grouped persistent views, manual/created/updated sort modes, show-more pagination, drag of session rows to projects or workbench groups, and a bulk "delete all archived" flow with per-workspace transactional deletes. TurboSpark pins first with recency inside day-boundary buckets (Today / Yesterday / Previous 7 Days / Older, deliberately not 24-hour based), colors chats with a deterministic per-project accent dot, and keeps archived chats behind one disclosure with per-row Restore and Delete; it has no pagination, no drag re-grouping, and no delete-all-archived.
ZCode: [packages/ui/src/TaskListItem.tsx](https://github.com/zai-org/ZCode/blob/main/packages/ui/src/TaskListItem.tsx), [docs/task/delete-all-archived-tasks.md](https://github.com/zai-org/ZCode/blob/main/docs/task/delete-all-archived-tasks.md), [docs/v4-session-workbench-groups.md](https://github.com/zai-org/ZCode/blob/main/docs/v4-session-workbench-groups.md)
Swift: [swift/TurboSparkApp/Sources/TurboSparkApp/Generation/ChatSidebarView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/ChatSidebarView.swift), [swift/TurboSparkApp/Sources/TurboSparkApp/State/ChatSidebarOrganizer.swift](swift/TurboSparkApp/Sources/TurboSparkApp/State/ChatSidebarOrganizer.swift)
Provenance: [docs/task/pinned-task-workspace-scope.md](https://github.com/zai-org/ZCode/blob/main/docs/task/pinned-task-workspace-scope.md)

### 2.3 Unread and pending-interaction badges on list rows - Missing in Swift
ZCode task rows carry a leading indicator slot with priority error > unread > spinner, an unread dot driven by a persisted `unreadAt` with compare-and-set read semantics across desktop and paired web clients, and a pending-interaction pill ("permission" / "user input") with a countdown progress fill and click-to-snooze for auto-resolving questions. TurboSpark has no unread concept at all (searching `unread` in app sources only hits MCP/background-shell plumbing, never the sidebar); its only row status cue is a progress flame icon replacing the bubble icon on the selected, running chat, and pending tool approvals surface only as in-transcript cards.
ZCode: [packages/ui/src/TaskInteractionBadge.tsx](https://github.com/zai-org/ZCode/blob/main/packages/ui/src/TaskInteractionBadge.tsx), [packages/ui/src/TaskListItem.tsx](https://github.com/zai-org/ZCode/blob/main/packages/ui/src/TaskListItem.tsx)
Swift: [swift/TurboSparkApp/Sources/TurboSparkApp/Generation/ChatSidebarChatRowView.swift](swift/TurboSparkApp/Sources/TurboSparkApp/Generation/ChatSidebarChatRowView.swift) (`rowIcon`); searched `unread` across swift/TurboSparkApp/Sources/TurboSparkApp with no sidebar hits
Provenance: [docs/task-list-refresh-semantics.md](https://github.com/zai-org/ZCode/blob/main/docs/task-list-refresh-semantics.md)

### 2.4 Session search and in-conversation find - Partial
Both have Cmd+K search over past sessions with snippets, and neither scores results (recency order). ZCode backs it with a Command Center that also searches commands, task bodies (a `searchable_text` column in tasks-index SQLite, backfilled for old sessions, capped at 200k chars), and files; it additionally has a Cmd/Ctrl+F in-conversation find with data-level match indexing over the virtualized timeline, automatic older-history backfill up to 1200 rows, and stable anchoring during streaming. ## 3. Agent runtime: permissions, plan mode, subagents, bots, hooks, skills, MCP, workflows

### 3.1 Permission modes and the decision ladder - Different
Both sides run a central, mode-driven permission engine with allow/ask/deny verdicts, but the vocabularies and rule systems do not match. ZCode has five collaboration modes (build, edit, plan, yolo, guarded; auto is "reserved but not implemented" and denies), decided by tool capability flags (readOnly, destructive, sideEffectScope, riskLevel, alwaysAsk) plus project rulesets whose rule content matches command/url/path subjects with prefix and wildcard forms; headless runs default to yolo. Swift has six modes (ask, auto, agentAuto, permissive, fullAccess, readOnly) decided by a per-call risk classifier over a fixed ladder: category deny, persisted MCP deny rule, high-risk always asks fresh (a session grant can never cover a later high-risk call), permissive/auto trailing allows carry an MCP "annotations unknown" guard, and a cloned repo `.mcp.json` server asks until explicitly auto-approved. ZCode orders yolo/guarded ahead of disallowedTools (a documented quirk in its own comments); Swift puts explicit denies and the risk ceiling ahead of every auto-allow including permissive.

### 3.2 Plan mode enforcement - Different
