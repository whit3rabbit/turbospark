# Prefill Batching steps 2+3: the batched routed-expert MoE pair (PF-02)

## What and why

ROADMAP.md's top "startable now" item is **Prefill Batching (PF-02 tile kernels)**. `docs/BATCHED_PREFILL.md` is the plan of record: step 1 (chunked-prefill driver, command-buffer batching only) landed 2026-08-16 and measured **1.22x**. The next prescribed increment is **steps 2 and 3: batched forms of the routed-expert pair** (`moe_phase1_gate_up_act_u16load` + `moe_phase2_down_reduce_k8`), which the doc says exist "to replace [the 0.287 c(16) proxy] with a measurement" — the routed pair is 23.5% of prefill GPU work and the single largest projected saving (16.4% -> ~4.7% of prefill). Full program projection is 1.55x-1.97x; this change takes step 1's 14.70 ms/token toward ~12 ms/token.

Out of scope (later steps, per the doc's order of work): batching the resident GEMVs via `encode_gemm_any` (q/k/v/o/shared), step 4 batched attention, step 5 GGUF pairs.

## Design

### Kernels — port-local, two of them, in a new `crates/gpu/src/shaders/moe_prefill_batch.metal`

SOURCE is concatenated after `moe.metal` (precedent: `moe_gguf/mod.rs`:54-60) so the file reuses `ExpertOffsets`, `moe_int4_gate_up_rows_simd_dev_vec_u16load`, `moe_int4_gemv_row_simd_dev_vec`, and `moe_hidden_activation` — the same math helpers the decode pair calls, which is what makes bit-identity provable rather than hoped for.

- **`RoutedBlobsWide`**: `device const uint8_t* blob[32]` argument-buffer struct (32 = max `ALLOWED_CACHE_SLOTS`). The vendored `RoutedBlobs` is fixed at 8, which is why Swift's DSV4 prefill kernels tile the route list 8 experts at a time and split phase 2 into down + reduce. Our slot cache holds all union experts resident at once, so a wide binding gives **one dense dispatch per kernel** (the doc's stated goal) and lets phase 2 stay fused. `kMaxPrefillExperts = 32` is a port-local constant.
- **`moe_prefill_phase1_routes_int4`** (DSV4 `dsv4_prefill_moe_phase1_pairs_int2`'s route-list shape, INT4 helpers, Gemma activation, no swiglu clamp): grid `(route_count * F) / 8` threadgroups x 256 threads; `routes[i] = (token, rank, slot, _)`; reads `routed_x[token*D]`, writes `acts[(token*top_k + rank)*F + f]`. Host sorts routes by cache slot for blob locality (order is numerically irrelevant in phase 1 — each route is independent).
- **`moe_prefill_phase2_fused_int4`**: decode's `moe_phase2_down_reduce_k8` with a token axis — grid `D * tokens` threadgroups, threadgroup `(t, d)`, SIMD group `r` computes `routing_w[t*top_k+r] * down_d(acts[pair])` from `blob[route_of(pair).slot]`, threadgroup-reduce in **rank order 0..top_k-1, residual-first from exactly 0.0f** (what `zero_hidden` provides today), `y[t*D+d] = half(acc)`. This makes the Gotcha 27 constraint (reduce order = router ranking, per token, independent of chunk boundary) hold by construction. No partials buffer, no third kernel — the DSV4 down/reduce split existed only to fit its 8-pointer tiles.

Runtime arguments (D, F, top_k, route_count) like the decode pair; `constants_key` stays the 1-byte `use_silu` key. Nothing new is baked into function constants.

### Host — new `crates/gpu/src/moe_prefill_batch.rs`

`RoutedBlobsWideBuffer` (argument encoder over the new kernel, binds up to 32 `(buffer, offset)` slot entries), `MoePrefillRoute` (4x u32) encoding, and the two `encode_*` wrappers following `moe_decode.rs`'s shape (including `pass.use_read_buffer` for every bound slot buffer). Export from `crates/gpu/src/lib.rs`.

### Runtime — `crates/runtime/src/families/gemma4/`

- **Scratch** (new fields in `RealGemmaState`, allocated at open, gemma4-only): `batch_acts [M*top_k*F] f16`, `batch_y [M*D] f16`, `batch_h1 [M*D] f16`, `batch_routing_w [M*top_k] f16`, `batch_routes [M*top_k]` routes. ~180 KB + ~90 KB + ~90 KB at M=16 (the fused phase 2 needs no FP32 partials). Plus one `RoutedBlobsWideBuffer` beside the existing `routed_blobs`.
- **`encode_shared_expert_branch`**: gains an output-row offset so token t writes `batch_h1[t*D]` (it already reads `dense_x[t]`). Still its own committed CB per token, still overlapping the pread. `h1` must become M-row because the batched routed tail consumes all M tokens' shared outputs after they all run.
- **New `moe_batch.rs`** (`encode_gemma4_layer_routed_moe_batched`): after the cb1 wait — readback of all M router rows, host top-k per token, **greedy sub-batching while `union(sub-batch) <= slot_count`** (union computed on host from the top-k lists, so `plan_if_possible`'s `experts.len() <= slot_count` assert can never fire; at 32 slots this lands at ~M=8 per the doc's measured union table, at 16 slots ~M=2), one `plan_experts_cached` + `execute_expert_cache_plan` per sub-batch, one wide bind from `slot_buffers[layer]`, host-write routes + routing weights, encode phase 1 then fused phase 2, then the **per-token sandwich tail** (unchanged `rms_norm_bf16w` / `residual_add` / `scalar_mul` kernels, per-token offsets into `batch_y` / `batch_h1` / `x`). Phase counters keep accumulating per sub-batch (requests/hits now count union experts per sub-batch — noted in a comment).
- **Driver** (`prefill_micro_batch_gemma4_inner`, mod.rs:264-294): the per-token routed loop is replaced by the batched encoder **behind a seam**: `MFERENCE_ROUTED_BATCH` env var, unset = today's per-token path (status quo, default), `1` = batched — read runtime-side like `MtpDraftPolicy` reads `MFERENCE_MTP_DRAFT`. This is the A/B axis the step-2/3 measurement needs, mirroring `MFERENCE_SHARED_CB` / `MFERENCE_ROUTED_PIPELINE`. Banks: a single bank of the host-written resources suffices because the driver already retires the previous layer's routed CB right after the cb1 wait (mod.rs:260), before any host write for this layer's routed half; `protect` is therefore empty and `plan_if_possible` always succeeds when union <= slots.
- **Layout gate**: the batched path requires both phases `RoutedBlobLayout::Affine` and **refuses by name** otherwise (GGUF gemma installs keep the per-token path under the default seam; batched+GGUF is a named error, not a silent loop — the `encode_gemm_any` doctrine).

### Correctness bar

Byte-identity against the sequential path, not coherence. Per route, the math is the decode kernel's math on identical inputs (same helpers, same lane layout, same f16 weight conversion); phase 2's slot-ordered reduce becomes rank-ordered per token, which is the same order because dispatch slots are in router ranking (Gotcha 27 fix); top_k=8 for gemma4 so no padded-rank edge cases.

## Tests and gates

1. **GPU parity** (`moe_prefill_batch_parity.rs`, macOS): the two kernels vs **M sequential decode-pair calls on the same blobs** — bit-exact f16 outputs; ragged routes (experts shared across tokens, union > 8 to exercise the wide binding, some experts used by multiple ranks/tokens); plus the `turbospark_compute` CPU reference for value sanity (the `moe_decode.rs` habit). Mutation-checked during development: temporarily permuting the reduce's rank order, dropping a route, or mis-indexing the token row must each flip the test red before trusting it.
2. **Runtime byte-identity** (extend `real_forward_gemma4_chunked.rs`): batched routed half on, vs `produce_prefill`/`produce` reference, several chunk spans; the existing 4-slot fixture exercises sub-batch shrinking; add a case with slots >= union to exercise a genuine multi-token sub-batch.
3. **Real-install gates** (pinned `~/models/gemma4.gturbo`, macOS): greedy + sampled smokes with the frozen digests at chunk spans 32/128/512 (step 1's protocol), `memory_oracle` (the ~0.4 MB of new scratch against the frozen ceilings), `quality_gate`.
4. **Standard verification**: `cargo fmt --check`, `cargo clippy --workspace --tests`, `cargo test -p turbospark-gpu -p turbospark-runtime`, the cross-target `cargo check --target x86_64-unknown-linux-gnu` set (gpu crate is touched).

## Risks / notes

- Footprint: new scratch is allocated at open for every gemma4 open (~0.4 MB); oracle ceilings (2,250/2,300 MiB) have ample headroom but the oracle run is the proof.
- At 16 slots (the frozen protocol's pinned count) the batched half lands at ~M=2 where c(2) > 1 — which is why the seam defaults to the per-token path and why the measurement runs at 32 slots (`auto` on this machine). Output is byte-identical either way (slot count is a throughput-only axis since Gotcha 27).
- The prefill union at M=16 is ~41.5 distinct experts vs 32 slots, so sub-batches cap near 8 — expected, and exactly the doc's stated constraint.
